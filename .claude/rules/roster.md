# Setting a race up: numbering, imports, the wizard, the weight limit

Part of the Trusty Track agent guide; the index is in [`CLAUDE.md`](../../CLAUDE.md). Read this before touching car numbering, `domain/roster_import.py`, `crud.create_practice_race`, `raceSetup.ts` or `weight_limit_oz`.

---

### Car numbering

`PER_GROUP` fills within each racing group's range; `GLOBAL` numbers sequentially from `global_start_number`; `MANUAL` disables auto-numbering.

### Importing a roster from another derby program

`domain/roster_import.py` is the vocabulary, `domain/gprm.py` the GrandPrix Race Manager mapping, `domain/derbynet.py` the DerbyNet one, `services/importers/` the files ([#618](https://github.com/dknowles2/trusty-track/issues/618), then [#661](https://github.com/dknowles2/trusty-track/issues/661) for DerbyNet). A pack switching from either arrives with years of rosters, car numbers and den assignments in its database, and the only door in used to be the CSV importer — export tables by hand, reshape the columns.

**`ParsedRoster` is the seam every importer plugs into.** `ImportedGroup`, `ImportedRacer` (fields mirror `schemas.RacerCreate`, `group` names a group by *name*), `ImportProblem` (a sentence, `blocking` or not — `csvMapping.ts`'s `line === 0` as one field) and `RosterImportError` (the file is not readable at all). A parser returns the value; the preview, the confirmation and the write path are built against it once, not per program — `crud.write_imported_roster` and `crud.existing_car_number_holders` never learned DerbyNet's name, because they never needed to. `duplicate_number_problems` is the one home for the in-file duplicate rule (#60's), and it is in the shared module for that reason.

**#661 confirmed the premise #618 left as a prediction: DerbyNet's file is the same table family, and reading it needed almost no DerbyNet-specific rule at all.** `domain/derbynet.py` does not duplicate `gprm.roster_from_tables` — it calls it. The one thing DerbyNet's schema adds, a `Partitions` table (the operator's own den list, under whatever word DerbyNet's own settings call it), turns out to need no branch in the shared mapping either: reading DerbyNet's own source shows a partition is created alongside a same-named rank, and under DerbyNet's own default grouping rule its class gets that same name too — so `roster_from_tables`'s existing "a rank named for its class gets no category" rule (written for GPRM's own analogous default) already lands on the right answer. What `Partitions` earns is a narrower fix: its `name` and `sortorder` are independent columns from the `Ranks` row it rides on, not guaranteed to stay in step, so `domain/derbynet.py` wraps the incoming `TableSet` in `_PartitionNamedTables`, which renames a `Ranks` row to its `Partitions` name before `gprm.roster_from_tables` ever sees it — one seam, no second mapping. `gprm.roster_from_tables` gained exactly one additive parameter for this work, `program_name` (default `"GrandPrix Race Manager"`), threaded into the one problem message that named a program by hand; `_decode_upload` in `api/schema.py` got the identical parameter for its own too-large-file message, for the identical reason. Both default to the GPRM string, so every existing GPRM test and behaviour is unchanged.

**The rule and the file are split at `TableSet`** — a `Protocol` with `has_table` and `rows`, both case-insensitive. `domain/gprm.py` reads plain rows and imports no `sqlite3`; `services/importers/sqlite_tables.py` opens the file **read-only** (`mode=ro` through a URI — the operator is handing over the only copy, and `test_parsing_leaves_the_file_byte_for_byte_unchanged` checks no journal appears beside it) and sniffs the kind from the header, not the extension. The two refusals carry different sentences because the operator's next move differs: an Access `.mdb` is what GPRM wrote before v18 and a current GPRM re-saves it as SQLite; anything else is not a GPRM database.

**Where the schema knowledge came from, stated plainly: DerbyNet, not GPRM.** No GPRM file was available. DerbyNet's own format was designed to be shared with GPRM — its "Sharing a Database With GPRM" and "Advanced Database Set-Up" guides document pointing DerbyNet at the GPRM file (Access before v18/2018, SQLite from v18) — and its `website/sql/{access,sqlite}/schema.inc` is the GPRM-compatible schema. Which columns GPRM itself fills, against those DerbyNet added later, is inferred; every optional column (`Exclude` → `excluded_from_standings`, a weight column, `SortOrder`, `Constituents`) is read as absent-means-absent. `backend/tests/roster_imports/gprm-v18.sql` is **synthesised from that schema, not recorded** — `NOTICE.md` there says so, and says why a real file from a pack that ran GPRM would be the first evidence not written by us, the same distinction `timer_recordings/` draws.

**The mapping: a racing group per GPRM rank, categorised by its class.** GPRM's class is what races together and its rank is the subgroup within one — which is where a den lives, and den assignments are the thing the issue names as worth carrying over. `RacingGroup.division` takes the class name as free text (#496 stage 2 — no enum is reintroduced). Two adjustments, each a way of getting it wrong: a rank named for its own class (GPRM's default) gets no category, since "Wolves" under "Wolves" classifies nothing; and a rank name shared across classes ("Den 1" under Wolves and Bears) is prefixed with its class on *both* holders, because `importRacers` matches racing groups by name and a merge would be silent. A class with no ranks is a group of its own, and a racer whose rank is gone falls back to their class.

**One departure from the issue's list: stages 1 and 2 (parser; unit tests with fixtures) landed together** — a parser without its tests is not a stage.

**The mutation is preview-then-confirm, and both re-parse the same upload rather than trusting a session on the server — for GPRM and for DerbyNet alike.** `previewGprmImport(raceId, fileData)` writes nothing and returns a `GprmImportPreview` (`groups`, `racers`, `problems`, `canImport`) — `fileData` is a base64 data URL, the same shape `uploadImage`'s `dataUrl` already takes. `confirmGprmImport(raceId, fileData)` decodes and parses the identical bytes a second time and writes them through `crud.write_imported_roster` (the one door: an existing racing group is matched by name and reused, same as `importRacers`' CSV loop; a new one is created grey, `#808080`, for the same reason that loop's auto-created groups are), then calls `_admit_late_racers` once for the whole batch — #343's fix, since a GPRM roster can carry already-checked-in racers (`PassedInspection`) and per-racer admission would regenerate an unraced round once per racer over a desk queue — and publishes `RaceChangeKind.ROSTER`. There is deliberately no server-side session holding the upload between the two calls: re-sending the (small — GPRM keeps photos as separate files, never in the database) file on confirm means what gets written can never drift from what the preview showed, at the cost of decoding it twice. `sqlite3` opens files, not buffers, so both calls write the decoded bytes to a temporary file (`_parse_gprm_upload`, removed in a `finally`) before `parse_gprm_database` sees them — the same shape `services/backup.py`'s restore uses for an uploaded archive. `RosterImportError` is re-raised as a plain `ValueError`, so a file the parser refuses reaches the operator the same way `importRacers`' "Race not found" does. `previewDerbynetImport`/`confirmDerbynetImport` (#661) are the identical shape over `_parse_derbynet_upload` and `parse_derbynet_database`, returning `DerbynetImportPreview` — **a sibling mutation pair, not a `source` argument added to the GPRM one.** #618's own docstring left that choice open; a discriminator would mean renaming an already-shipped, documented mutation (`docs/design.md`, this file, `test_auth_policy.py`'s classification in both directions, `race_lock.py`, `demo_policy.py`, every generated frontend type) to add a second importer, where a sibling pair costs one more `@strawberry.mutation` and one more set of Strawberry types with nothing existing to touch. The three classification lists (below) simply grew a second, near-identical entry each.

**Duplicate prevention against the roster already in the race is `domain.roster_import.existing_number_problems`**, the pure counterpart to `duplicate_number_problems` that the docstring on the latter promised: it takes `{car_number: "First Last"}` as data rather than a session, fed by `crud.existing_car_number_holders` — the query half stays in `crud`, same rule/I-O split as everywhere else, and neither function nor its DerbyNet call site needed to change. Only the *first* file holder of a number is checked against the existing roster; a later file holder sharing that number is already reported by `duplicate_number_problems` against the first, and checking it again here would say the same collision twice. The preview's `problems` list is the in-file duplicates followed by these — the reader has no reason to care which rule found a given line.

**Classified `CHECKIN`, the same bucket as `importRacers` and for the same reason: importing a roster is desk work**, not scheduling or a race's own settings — a pack that registers everyone by spreadsheet and then walks in with their old GPRM or DerbyNet file at the check-in table should not need to find the operator. `confirmGprmImport` and `confirmDerbynetImport` are both in `race_lock.py`'s `LOCKED_MUTATION_RESOLVERS` (`_direct_locked`, same as `importRacers`) since each writes racers into a race; `previewGprmImport`/`previewDerbynetImport` are deliberately absent there, since neither writes anything and both are exactly the kind of read-shaped mutation the module's own docstring says stays reachable on a locked race. The demo's denylist (`api/demo_policy.py`) refuses both confirm mutations for the same reason it refuses `importRacers` — bulk row creation from caller-supplied data, one visitor's file ruining the demo for everyone else until the reset — and leaves both preview mutations reachable, since parsing an upload into a temporary file that is deleted before the response returns costs the demo nothing an ordinary read does not.

**The modal is one component reading a `source` prop, not two modals.** `RosterImportModal.tsx` (renamed from `GprmImportModal.tsx` when DerbyNet arrived) sits beside **Import from CSV** in the roster's Add Racer split button, offered twice — **Import from GrandPrix Race Manager** and **Import from DerbyNet** — each opening the same component with `source="gprm"`/`source="derbynet"`. Unlike the CSV path there is no client-side column mapping — the file is a database, not a spreadsheet, and the mapping already happened server-side — so the modal's job is the same for either source: pick a file, read it as a data URL (`FileReader.readAsDataURL`, no server round trip until the mutation), call that source's preview mutation, render the groups/racers/problems it comes back with, and call its confirm mutation with the same data URL on **Import**. A per-source config object (title, help paragraph, file input id, which two mutation documents and which two result field names) is the whole of what varies; everything else — the preview table, the warnings list, the success/error banner — is one render path. A file the parser does not recognise surfaces the preview mutation's `ValueError` as the sentence the parser wrote (GPRM's Access refusal names the fix: open it in a current GPRM, which re-saves as SQLite; DerbyNet has no such refusal, having never written a pre-SQLite format), not a generic "could not be read."

**Duplicating the modal was the cost this design was chosen to avoid; two more Strawberry types and two more mutations were the cost it accepted instead.** `DerbynetImportGroup`/`DerbynetImportRacer`/`DerbynetImportProblem`/`DerbynetImportPreview` in `api/schema.py` mirror the four `GprmImport*` types field for field — a sibling type rather than a shared one, so the schema names which program a caller is previewing (`previewDerbynetImport: GprmImportPreview` would read as a typo, not a deliberate sharing). `frontend/src/api/graphqlClient.ts`'s `EMBEDDED_TYPES` grew the same four names beside the GPRM ones, for the identical reason (a preview parsed fresh on every call, never fetched independently).

### The practice race

`crud.create_practice_race`, behind the `createPracticeRace` mutation and the **Try a practice race** button on Home ([#201](https://github.com/dknowles2/trusty-track/issues/201)). The operator is a parent volunteer who uses this app once a year, and the night before is when they want to know what race day feels like. Everything needed already existed — `populate` builds a believable roster, the fake timer runs heats without hardware — but reaching it meant creating a race, adding racing groups, populating, checking everybody in and running the round wizard, which is most of the thing being rehearsed.

**One mutation, not five round trips.** A rehearsal that fails half way leaves the operator with a broken race to tidy up, which is the opposite of the confidence it exists to give.

**It reuses a fake-timer track and only creates one if there is none.** An operator who rehearses three times must not end up with three tracks in System Settings — a track is global state, which is the same fact the e2e conventions are built around. It never picks a real one: arming a heat on a real timer sends a signal to a device in a room somebody may be standing in.

**It includes a championship round.** Advancement is the part of race day that surprises people; a rehearsal that stops before the final leaves out the bit worth practising.

**The name counts up.** `races.name` is unique, so a second rehearsal would otherwise fail at the point the operator is least equipped to understand why — and a counter reads better than a timestamp on the Home page.

There is deliberately no "is a practice race" column. The name is what tells an operator, and a flag would be a schema change for something cosmetic that nothing else branches on.

**Clicking the button twice must not leave two rehearsals in the list** ([#588](https://github.com/dknowles2/trusty-track/issues/588)). With no stored flag, "is there one already?" has to be answered from the name, and `domain/practice.py` is where that rule lives — pure, so both ends of the app can ask it without disagreeing (#48's lesson about a rule answered twice): `crud.existing_practice_race` reads it to decide whether `createPracticeRace` should build anything, and `Query.practiceRace` reads it so Home can offer "Resume practice race" without re-deriving the naming rule itself from the race list. **Resuming beats duplicating**: the mutation returns the most recently created rehearsal (highest id — `PRACTICE_RACE_NAME`'s own counter does not survive a deletion in the middle, so name order and creation order can disagree) rather than building another, and `startNew: Boolean` is the deliberate escape hatch for an operator who really does want to start over, offered on Home as a small "Start new" action beside the primary button rather than a second confirm dialog — the simplest honest shape for "I know, start a fresh one anyway."

**The frontend closes its own half of the race independently of the backend's.** `disabled={practiceResult.fetching}` already existed and stays, but urql's `fetching` flag only becomes true once a render has caught up with the mutation having started — two clicks landing in the same tick can both fire before that happens. `Home.tsx`'s `handlePractice` therefore also holds a synchronous `useRef` guard, set before the `await` and cleared in a `finally`, so a genuine double click cannot send two requests regardless of render timing. Belt and braces: the backend's resume behaviour is what actually prevents cruft even if this guard is ever removed, and the guard is what keeps a rapid double click from being two round trips instead of one.

### The race setup wizard

Rules in `frontend/src/features/management/raceSetup.ts`, wiring in `components/RaceSetupWizard.tsx`, storage through `createRace` ([#662](https://github.com/dknowles2/trusty-track/issues/662)). **Most of what the issue asked for already existed under other names, and building it again was the failure mode to avoid.** "Race type" (Pinewood / Space Derby / Raingutter Regatta) is the vehicle word and its artwork key, whose recognised vocabulary was already exactly `("car", "rocket", "boat")` (#551); "organization type" is the organization and racing-group words (#496 stage 3); "one install serving several kinds of event at once" is the per-race override those already have, resolved server-side by `resolve_terminology`; and the ready-made den names are `categoryPresets.ts`. What was genuinely new is the *questions* — a handful of answers a volunteer can give in a sentence, each turned into the seven words and a scaffolded list of groups — and copying a previous race's structure into a new one. There is no race-type enum, no organization-type column and no `Rank` enum reintroduced: an answer resolves to the same seven nullable columns `updateRace` has accepted since #496, plus ordinary `RacingGroupInput` rows.

**`createRace` takes `racingGroups` and the seven terminology fields, and writes them in one transaction.** `crud.create_race` flushes the race, adds the group rows in the order given (`get_racing_groups` orders by id, so creation order is display order), and commits once — #201's "one mutation, not five round trips" reasoning: a setup that fails half way must not leave a half-built race. `test_create_race_setup.py` pins that a refused race creates no groups either. There is no `clearTerminology` on `RaceInput`, since a race being created has nothing set yet to clear.

**The last step of the wizard *is* the flat create form**, unchanged (#587's reasoning still holds: a first-timer should meet every field once, in order). The wizard only adds what that form could not ask — what is being raced, who is holding it, which groups to start with — in front of it. So there are not two competing ways to create a race: `RaceForm` in create mode is rendered by exactly one caller now, the wizard, and `Home.tsx` and `Navigation.tsx` both mount the wizard. The form stays mounted (hidden) once reached, so going Back to fix a group's name does not lose a race name already typed; it is keyed on what it was prefilled with, so an answer that *would* change the prefill remounts it rather than showing stale words. The Words and names section stays off the create form — the wizard's questions are where a new race's words come from, and the raw seven boxes beside them would be two controls for one thing.

**Only the words that differ from the install default are stored** (`raceOverrideFor`). A pack's Pinewood Derby on an ordinary install resolves to Pack/Den/Car already; writing that as an explicit override would open every wizard-made race's edit form with **Use different words for this race** ticked for no reason, and a later change to the install-wide words would never reach it. All seven or none, because that is the shape the edit form reads. **The baseline is `initialConfig.terminology`, fetched by the wizard's own query — never `useTerminology()`.** Inside a race route that context already holds *that race's* override (`RaceTerminologyGate`), so from "New Race…" on a Space Derby's nav, a Pinewood answer would have looked like a change and a Space Derby answer like no change. `raceSetup.test.ts` pins the comparison against a rocket-default install.

**The Cub Scout scaffold is the six ranks in their rank colours — the same six `backend/db/populate.py` hands a test roster.** Not a shared constant (populate is a test-data generator, the preset is the product), but deliberately equal, and the reason is the docs: the race-day screenshot spec creates its race through the wizard and then runs Populate Test Data, which reuses existing groups rather than inventing its own, so every roster and standings picture downstream keeps the content it had. A district derby scaffolds the same six but calls them **Ranks** under a **District** — groups at a district are rank-level, not dens, and "Rank" is a starting word the operator can change. Awana gets Cubbies/Sparks/T&T/Trek/Journey as **Groups** under a **Club**; a school and "something else" start with an empty list, since their groups are their own. Each scaffolded group takes the number block Manage Dens would have offered it in turn (`numberRanges.suggestedRange`, extracted from `RacingGroupManager` so there is one rule, not a second copy free to drift).

**Copying a previous race copies raw, not resolved.** `prefillFromRace` carries the source's seven terminology *columns* as they are — null stays null — so a race that inherited the install's words still inherits when copied, rather than freezing whatever they resolved to that day. It copies the groups exactly (names, colours, categories, number ranges, minus ids), the scoring/tie/drop-worst/trophy/numbering/weight settings and the location, and deliberately not the name or date (what makes it a *new* race), the roster or anything downstream of it, the QR-code text (that day's vote), or the update-only controls. Copying skips the questions step entirely: the previous race is the answer, and asking again invites a second answer that disagrees with the groups just copied.

**The start step exists only once there is a race to copy from** (`stepsFor`). That makes its presence in the docs screenshot specs depend on whether another spec's race exists at that moment — they run at once — so `e2e/docs/support.ts`'s `passSetupStart` steps past it when it is there, and the picture of the copy option is taken by the `first-run` setup project, the one place that can promise exactly one race exists and that it is its own.

**The option labels name the built-in words on purpose** ("Packs and dens — the words the app uses out of the box"), for the same reason `SystemSettings.tsx`'s terminology labels are allowlisted by `terminologyGuard.test.ts`: an option that *chooses* a vocabulary has to say which one it chooses. They live in `raceSetup.ts` as data, by the usual pure-rule/React-wiring split, not to sidestep the guard — the wizard's own JSX reads every group word off the chosen terminology, so a district derby's groups step says "Rank 1 name" and "Add rank".

### The weight limit

`Race.weight_limit_oz`, and the rule is on the frontend in `features/management/weightCheck.ts` ([#205](https://github.com/dknowles2/trusty-track/issues/205)). Check-in had recorded a weight "for documentation purposes", which misses the reason anybody weighs a car: the dispute happens at the scale with a queue behind it, and the app should back up the volunteer holding the car.

**It is a warning, never a refusal.** Nothing on the server rejects an overweight car, and the save is not blocked. The inspector decides; the app makes the rule visible at the moment it matters. That is also why the rule lives on the client — it is shown while somebody types, not enforced at a boundary.

**A column of its own, not a key in `rules_configuration`.** That column is a free-text string nothing reads and nothing writes, and a number in a string column is the shape [#5](https://github.com/dknowles2/trusty-track/issues/5) spent a release removing. The issue proposed reusing it; don't.

**Null means no check, and there is deliberately no server default.** Every race that existed before this has null, and giving them a limit at migration time would suddenly flag cars a person had already passed at the inspection table. New races are offered 5.0 by `RaceForm` instead — the near-universal pack rule — which keeps the data model honest about what "no limit" means.

**`clearWeightLimit` is why the check can be turned off.** `update_race` drops every null from its payload, so absent means "leave alone" — which is what lets a screen re-submit a whole race without wiping the fields it does not offer, and also means no field can be set *back* to null. Without the explicit flag the weight check could be switched on and never off again. Same shape and same reasoning as the PIN's removal control ([#192](https://github.com/dknowles2/trusty-track/issues/192)).

**`TOLERANCE_OZ` is half a scale division, not a fudge.** Scales disagree in the last place, and refusing a car that reads 5.001 is a rule about the equipment rather than about the car. `0.005` is chosen so a car *displaying* 5.00 always passes a 5.0 limit and one displaying 5.01 never does.

**Zero is "not weighed", not "very light".** An empty number input hands back `0`, and a green tick against a car nobody has put on the scale is worse than no answer at all.

# The race-day operator screen

Part of the Trusty Track agent guide; the index is in [`CLAUDE.md`](../../CLAUDE.md). Read this before touching `raceFlow.ts`, `heatSession`, `RaceExecution.tsx`, `RaceControl.tsx`, shortcuts or the chime.

---

### Race-day keys and the finish sound

`features/racing/shortcuts.ts` and `features/racing/chime.ts`, wired in `RaceExecution` ([#207](https://github.com/dknowles2/trusty-track/issues/207), [#208](https://github.com/dknowles2/trusty-track/issues/208)). Both are pure rules with the doing in the component, the same split as `raceFlow.ts`.

**Three keys, and each is printed on the button it mirrors.** Space advances, E opens the editor, Escape cancels the countdown. A screen somebody uses once a year cannot amortise a cheat sheet, so a fourth key is a cost rather than a feature.

**Space does not start a heat.** On a real timer the gate is released by hand, and on the fake one the control is a debugging panel rather than part of the flow — so there is no "start" for a key to mean.

**Nothing fires while typing, with a dialog open, or with a modifier held**, and `preventDefault` is called *only* once an action has been decided. Space scrolls a page and Escape closes things; taking either away from a keystroke we are going to ignore is worse than having no shortcut.

**The hooks sit above `RaceExecution`'s two early returns** — no heat, and a round whose field is undecided. A hook after them does not run on every render, which is what `react-hooks/rules-of-hooks` catches.

**The chime is an edge, not a state.** `RECORDED` persists for as long as the operator leaves the heat on screen and a payload arrives for every lane time and every check-in, so `shouldChime` compares the previous phase. A null previous phase is a page load, which is not a heat finishing.

**Off by default, remembered per device**, like the PIN: the operator's laptop wants it and a wall display does not. Switching it on plays it once — the only way to find out whether the machine is muted without waiting for a heat. It is two WebAudio oscillators rather than an asset, because these machines have no internet.

**The corner checkbox described above is gone ([#1074](https://github.com/dknowles2/trusty-track/issues/1074)); Sound options is the one control left.** `features/audio/soundEffects.ts` holds a `master` flag plus five per-event effects (`stagingReady`, `gateRelease`, `finish`, `recordBreak`, `awardFanfare`), edited from the **Sound options** panel (`SoundSettingsSection.tsx`) that both `RaceExecution` and System Settings embed — the panel's own "Heat Finish" row is what used to be duplicated by the checkbox's `onChange` writing both `setChimeEnabled` and `writeSoundSettings`. `RaceExecution`'s effect now plays the finish chime only through that richer per-event path, gated on `master` the same as every other effect. One fallback survives, read-only: `chimeEnabled` (`chime.ts`'s own legacy `trustytrack.finishChime` flag) is still checked when `master` is off, purely so a device that had the removed checkbox on keeps chiming without the operator ever opening Sound options. A one-time migration of stored settings was considered and rejected: `master: false, finish: true` is also exactly what an operator gets by trying Sound options and then deliberately turning `master` back off, and storage cannot tell the two apart, so promoting it once would refight that operator's own choice on the very next load.

**`writeSoundSettings` must not touch the legacy flag at all, and a PR review caught it still doing so.** It used to re-sync `FINISH_CHIME_STORAGE_KEY` to `settings.finish` on *every* call, a `master`-only change included — so opening Sound options, turning `master` on and back off without ever touching "Heat Finish" left the legacy flag `'on'` (since `finish` defaults `true`), and the fallback above kept chiming despite the operator's own explicit "turn it off". That is #871's coupling again, one level removed: a control the operator believes is off was still steering another one's storage through a key neither of them displays. `writeSoundSettings` now writes only `SOUND_STORAGE_KEY`; the legacy flag is frozen wherever a pre-#1074 device (or a manual edit) last left it, which is exactly the continuity the fallback exists to preserve — no code path in this app writes it any more.

**Sound options gates everything now, and the two systems' independence from #871 lives entirely inside the panel.** Before [#871](https://github.com/dknowles2/trusty-track/issues/871), checking any single effect inside the panel silently flipped `master` to `true` too, which meant every *other* effect already left checked in storage — award fanfare, the record-break fanfare — started actually sounding, unasked. Each toggle still only ever writes its own field (`SoundSettingsSection.tsx`'s `handleMasterChange`/`handleEffectChange`); don't reintroduce the coupling by making one checkbox's `onChange` reach into another's.

### What is on the track right now

`heatSession(trackId, heatId)` merges the heat row (schedule, and results once saved) with the `TimerManager`'s pending lane times, and reports a `phase` — `NO_HEAT`, `NOT_READY`, `WAITING`, `RUNNING`, `RECORDED`. The rule is `domain/heat_session.py`; the resolver loads the two sides and calls it.

Two things it settles, because they were getting it wrong in a render function:

- **A recorded heat ignores the timer.** Anything still pending belongs to a run that has already been superseded, and showing it would contradict the standings.
- **`pending` is a field.** A time from the timer is not in the database and an abort still loses it, so the screen must not present it as final.

`phase` is *not* the timer's state (`ARMED`, `FAULT`…), which is about the device and is still reported separately as `timerState`.

Also a subscription. It watches **two** channels — `timer_state:{track_id}` for lane times and arming, and `race_state:{race_id}` for a result being saved, which is what turns `RUNNING` into `RECORDED` and never comes from the timer. `pubsub.subscribe` takes several channels for this.

`RaceExecution.tsx` renders from it and merges nothing (issue #7). **`phase` is the answer to "what is this heat doing", not `timerState`** — a recorded heat whose timer has not caught up must not show as racing. Screens read `HeatSession` / `LiveLane` from `features/racing/types.ts`; the stored `heat.lanes` are what *edits and skips write against*, since those change the record rather than the live view.

Don't reintroduce a merge on the client; extend `domain/heat_session.py` instead.

**The current heat and On Deck show the same kind of picture** (#608). Both panels of `RaceExecution.tsx` render `LaneAvatar` (`features/racing/components/LaneAvatar.tsx`) — never split, one showing faces while the other showed cars, the way On Deck once did on its own (falling back to a gold roundel carrying the car number, which is gone for good). They sit side by side on one screen, and the audience display's own lane cards (`Observation.tsx`) were already faces throughout; the split was On Deck's alone. The operator screen is not a public surface (see "Name display" in [`terminology-and-names.md`](terminology-and-names.md)), so this is unrelated to `shouldShowRacerPhoto`'s gating.

**Which kind is a per-device toggle, not a fixed answer, and car is the default** ([#1075](https://github.com/dknowles2/trusty-track/issues/1075)). #608 picked faces outright, reasoning that "a face is what the person calling racers to the start line needs" — true of an announcer, but this screen's main reader is the operator staging heats out of parc fermé, a job of matching a car in hand against a picture of a car, not a child. `features/racing/lanePhoto.ts` holds the storage (`readLanePhotoPreference`/`writeLanePhotoPreference`, the same per-device `localStorage` shape as the chime and sound settings) and the pure picker `pickLanePhoto(preference, { racerImageUrl, carImageUrl })`: the preferred picture if there is one, the other picture if not, initials if there is neither — never the removed roundel. `LaneAvatar` calls it and renders a car photo as a rounded rect (`isCarPhoto` lives beside the picker rather than as a `kind === 'car'` literal in the `.tsx` file, since that literal would otherwise sit inside `terminologyGuard.test.ts`'s `>...<` scan the same way `PrintDecor.tsx`'s artwork-key map does — see that file's allowlist entry). The control itself sits behind the same **⚙** popover in the heat header as **Sound options** and **Auto-advance** ([#1157](https://github.com/dknowles2/trusty-track/issues/1157) moved all three off the row and into one preferences popover, out of the action row's own way) — not a race-level setting, since an operator's laptop and an announcer's tablet on the same race legitimately want different answers. It is a two-button radiogroup (`lane-photo-picker`, with `lane-photo-option-car`/`lane-photo-option-portrait` children) rather than a switch ([#1245](https://github.com/dknowles2/trusty-track/issues/1245)) — the preference is a choice between two named things, not a boolean, and a switch's unlabelled "off" state read as "no photos" rather than "the other kind".

### What the operator screen does between heats

Issue #13. `RaceExecution.tsx` used to encode the race-day flow as six `useEffect`s guarding each other with mirror state, two refs, a derived boolean and an `eslint-disable react-hooks/exhaustive-deps`. It is now one machine in `features/racing/raceFlow.ts`, with `useRaceFlow.ts` as the only wiring.

**`phase` is an input to this machine, not a state of it.** The issue originally proposed a client machine reading `IDLE → PREPARING → ARMED → RUNNING → RECORDED`, but that is the *heat's* state and the server has owned it since #7. What is left is genuinely local — a countdown to the next heat, and whether a round summary is up:

```
WATCHING ──recorded, times, a next heat, auto-advance on──> COUNTING_DOWN(n)
COUNTING_DOWN ──n reaches 0──> ADVANCE_TO_NEXT_HEAT, back to WATCHING
any ──a round's field is decided──> ROUND_SUMMARY ──dismissed──> WATCHING
```

The test for whether something belongs in `raceFlow.ts` rather than on the server: **it does not survive a refresh.**

**The screen stays on the heat it is showing; advancing is the toggle's job or the button's** (#130). `RaceControl` pins `selectedHeatId` to whatever the fallback landed on, adjusting it *during render* rather than in an effect — an effect would show the unpinned heat for a frame and then correct it, which is the flicker the `activeExecutionHeat` memo was written to avoid. It converges in one pass and is self-healing: a pinned heat that stops existing sends the memo back to the fallback, which then gets pinned.

Without that pin the fallback — "the first heat still to be run" — slid forward the moment a result landed, because recording a heat changes which heat that is. Three consequences, none of them obvious from reading the component:

- the recorded heat's **Edit** button went with it, leaving **Re-Run** — which *clears* the result — as the only route back to a mistyped time;
- **Next Heat** and **Cancel** were unreachable;
- and `raceFlow.ts` never observed the active heat as `RECORDED`, so `COUNTING_DOWN` was unreachable and **`autoAdvanceHeat` did nothing in either position** while the screen advanced regardless.

`raceFlow.test.ts` dispatches events directly and `RaceExecution.test.tsx` is handed a fixed heat, so neither could see it — this needs a real backend moving the data underneath, and it is pinned by two tests in `raceDay.spec.ts`.

`reduce` returns commands (`PREPARE_HEAT`, `ADVANCE_TO_NEXT_HEAT`) rather than performing them, which is what makes race-day behaviour assertable without rendering — `raceFlow.test.ts` dispatches event sequences and touches no DOM. Put a *rule* there and its *I/O* in `useRaceFlow.ts`; if you find yourself writing an `if` about the race in the hook or the component, it is in the wrong file.

Two things it settles that were previously accidents:

- **Cancelling a countdown is sticky, scoped to the heat.** Nothing the server can see changed when the operator clicked, so a machine that re-decided purely from the observation would start counting again on the next payload. Moving to another heat gets a countdown back.
- **A summary's presence and its id are separate fields.** `AdvancementStatus.roundId` is optional, so `hasRoundSummary` and `roundSummaryId` cannot be collapsed into one nullable number.
- **The race summary needs the same key, and the docstring that said otherwise was wrong** ([#916](https://github.com/dknowles2/trusty-track/issues/916)). `raceFlow.ts` latched "already shown" for the race on a bare boolean, reasoning that a race cannot decide a second, different one. It can: a championship round added mid-event through **Add Round** — as opposed to the wizard, which pre-creates one — can go from placeholders to fully recorded between two refetches, so the schedule jumps from "6 heats, all done" straight to "10 heats, all done" with no rendered incomplete state in between. `hasRaceSummary` never dips, so the boolean latch suppresses the second, genuinely different completion. `raceSummaryKey`/`shownRaceSummaryKey` mirror `roundSummaryId` exactly, and `raceCompletion.ts` fingerprints the completed schedule by heat id so one completed schedule can be told from another.

  The general rule, since this is now the third place it has bitten: **an "already shown" latch keyed on a boolean is only safe if the boolean is guaranteed to dip.** Nothing in this app guarantees that — the client sees snapshots, not transitions, and two states either side of a refetch can both be `true`. Key the latch on what actually changed.

`roundCompletion.ts` is the matching piece for `RaceControl.tsx`: there is no event for "a round's field was just decided", so it is recovered by comparing one query result against the last. `seen === null` means "first look", where every decided round is history rather than news.

**`roundSummary` and `raceJustCompleted` reset when the thing they name stops being true, not only at their own two explicit call sites** ([#856](https://github.com/dknowles2/trusty-track/issues/856)). Re-running the *active* heat and dismissing via **Next Heat** each clear `roundSummary` directly, and the modal's own "×" (`flow.dismissSummary`) clears neither `roundSummary` nor `raceJustCompleted` at all — it only hides the modal, by design, so a dismissed summary does not spring back on the next payload (see "Cancelling is sticky" above). None of those three cover a *correction*: editing an earlier prelim result through Override (`handleUpdateResult`) resets a later championship round's field to placeholders (`.claude/rules/advancement-and-awards.md`), or clears the whole race's completeness, and that path never touched either flag. Confirmed reachable on a real backend, not merely theoretical: `raceDay.spec.ts`'s `a round summary can be raised again once its round is decided a second time` and `clearing a result un-completes a race whose summary was already shown` both provoke it end to end.

The fix is two lines, each adjusted **during render**, the same "adjust state while rendering" pattern `RaceControl` already uses to pin `selectedHeatId` and open the hand-pick picker — not inside an effect, which trips `react-hooks/set-state-in-effect` for exactly the reason given under "Edit race opens..." in [`frontend-screens.md`](frontend-screens.md): a bare `if (condition) setState()` in a `useEffect` fires on every render where the condition still holds. Both compare the *current* `race.rounds`/`race.heats` against the flag's own stored value and clear it once it is stale — they never *set* either flag (that stays the two completion-detecting effects' job), so dismissal remains sticky exactly as before. `Observation.tsx`'s intermission highlights reel (`.claude/rules/displays.md`'s "Intermission highlights", #177 stage 3) resets its own `highlightIndex` the identical way — comparing a `${intermissionActive}:${highlightClips.length}` key against what was last seen, rather than a `useEffect` keyed on the same two values, which would play one frame of the previous break's stale index first.

**The `roundSummary`-is-never-cleared failure mode is subtler than a stale line-up on screen, and is why the regression test re-decides the round rather than just invalidating it once.** Even without this fix, `RaceControl`'s own completion-detecting effect *does* raise a fresh `roundSummary` object the next time the round is decided — it tracks `seenAdvancedRounds` independently and does not care what `roundSummary` currently holds. The actual break is one level down, in `raceFlow.ts`'s `haveSummarised`/`summarisedRoundId`: those only reset when `hasRoundSummary` (`!!roundSummary`) is observed to go *false*. If `roundSummary` never becomes falsy in between — because nothing cleared it — `hasRoundSummary` never dips, so a round that un-decides and is later re-decided is read by the guard as "the same summary I already showed" (same `roundSummaryId`) and the modal never reopens, even though `roundSummary` itself did get a fresh value. Fixing only "the content looks stale" and not "the flag genuinely returns to falsy" would leave this failure in place.

**Reproducing this on a real backend needs a live refetch of `race.rounds`, and `updateHeatResult` alone does not give you one.** `useRaceStateChanged` treats a `HEAT_RESULT` event carrying a `heat` payload as mergeable (#12) — the one heat's own fields update in the normalized cache, but nothing about the *round's* `advancementStatus` is in that payload, and no refetch fires. That is enough to keep `isRaceComplete` (a plain fold over `heat.lanes`) accurate live, which is why writing every heat through raw `updateHeatResult` calls is fine for provoking the `raceJustCompleted` half of this bug. It is not enough for `roundSummary`, which reads `race.rounds[].advancementStatus` — a field no per-heat merge ever touches. Two things do force the refetch that actually refreshes it: `handleUpdateResult`'s own explicit `reExecute({ requestPolicy: 'network-only' })` after a same-tab Edit/Override save, and the timer's own result path (`TimerManager._record_results` → `_publish_race_state(race_id)` with no `kind`, which defaults to `OTHER` and is never mergeable). The docs screenshot spec's `race-day.spec.ts` already leans on the second of these — see its own comment about writing results "behind the client's back" and reloading before reading the screen again. `raceDay.spec.ts`'s regression test for this issue does the same: every heat but the last is written raw, and the last is run through the fake timer on screen specifically so the round's own decided-or-not status is something this client actually observes.

**"Every heat that exists has run" is not "the race is over"** ([#874](https://github.com/dknowles2/trusty-track/issues/874)). `isRaceComplete` is exactly that plain fold, and a race built one round at a time from the **Add Round** dialog has no championship round at all the moment its sole preliminary finishes — the round wizard's own pre-created placeholder heats are the only reason the wizard-built races above never tripped this. Tightening the trigger — only announce completion once a round drawing its field from another round's standings (`advancementSource` set) exists — was tried and reverted: `raceDay.spec.ts`'s own `clearing a result un-completes a race` test races a **prelims-only** schedule (`createSchedule` with no championship argument) through the wizard and expects the summary to fire anyway, and that race produces the identical stored shape — one general round, fully raced, no advancement source — as one that is not done yet. There is no event, and no stored fact, for "the operator does not intend to add another round"; that is a plan in someone's head, not a database row, and the two cases cannot be told apart from what is stored. `hasTerminalRound` in `raceCompletion.ts` is the function that tried and failed at this as a gate — its docstring carries the fuller story.

**The fix is honesty, not suppression.** The modal still opens exactly when it always did (`isRaceComplete` unchanged), but `RaceControl` also computes `hasChampionshipRound` (`hasTerminalRound(race.rounds)`) and passes it down; `RaceExecution.tsx`'s summary modal reads it to choose between two framings. With a championship round already in the schedule, it is titled **"Race Complete!"** exactly as before. Without one, it is titled **"No More Heats Scheduled"**, the body copy says so rather than implying finality, and an **"Add a Championship Round"** link (to the Schedule tab) is offered ahead of — never instead of — the standings/awards/print links that always apply, since a prelims-only race really is done here and this modal cannot tell the two cases apart. `raceDay.spec.ts`'s regression test for #874 builds exactly the Add Round shape, checks the softened title and the extra link, then adds and races a championship round live and checks the modal reverts to the ordinary "Race Complete!" framing with the extra link gone.

### The action row, the preferences popover, and the phone layout

[#1157](https://github.com/dknowles2/trusty-track/issues/1157), [#1152](https://github.com/dknowles2/trusty-track/issues/1152), [#1140](https://github.com/dknowles2/trusty-track/issues/1140). Five controls in the header's own `justify-content: space-between` row — Skip Heat, Override, a car-photo toggle, Sound options, Auto-advance — were squeezed to their minimum content width at ordinary desktop widths (the card's own column is a fraction of `race-execution-layout`'s 1000px cap, not the full viewport), which wrapped a two-word label onto two lines inside its own button. The header also said a heat's state three ways at once: a phase pill, a separate `TimerStatusBadge` pill, and a "Waiting for Timer…" box standing in for the primary action before a result existed.

**Footer for actions, header for one status line and one ⚙.** `data-testid="race-execution-action-row"` moved from the header to a footer under the lane list — left holds the secondary actions for the current state (Skip Heat/Override or Enter Results before a result; Edit/Re-Run after), right holds the single primary action, **Next Heat**. The header keeps only the phase pill plus `TimerStatusBadge` rendered with `variant="muted"` (plain text, no second pill — `TimerStatusBadge.tsx`) and, while `RUNNING`, the elapsed-seconds counter beside it. The "Waiting for Timer…" box is gone outright; nothing replaces its slot because there is no longer a slot with nothing in it.

**Next Heat is always in the DOM, disabled until `isCompleted && nextExecutionHeat` — never conditionally rendered.** This is a trap for any test or spec written against the old shape: `getByRole('button', { name: /^Next Heat/ }).toBeVisible()` used to mean "the heat is done", because the button did not exist before that. It resolves the instant the page loads now, `disabled` or not, so a helper that waits for visibility and then does something *other* than `.click()` on that same locator (Playwright's own actionability wait covers a same-locator `.click()`, since it retries until the element is enabled) — a `page.keyboard.press(' ')`, a `page.goto()` elsewhere — runs too early. `shortcuts.spec.ts`'s `runCurrentHeat` and two spots in `activityLog.spec.ts` hit exactly this; the fix is `toBeEnabled()` (or `getByTestId('next-heat-button')`, which exists for this reason) instead of `toBeVisible()`.

**Show car photos, Sound options and Auto-advance moved behind one ⚙ popover in the header**, reusing the outside-click-closes shape `IntermissionControl.tsx`'s compact mode already uses (`preferencesOpen` state, a ref, a `mousedown` listener added only while open). Every e2e or component test that used to find `sound-effects-modal-trigger`, `lane-photo-picker` (`lane-photo-toggle` before [#1245](https://github.com/dknowles2/trusty-track/issues/1245) turned it from a switch into a radiogroup) or `auto-advance-toggle` directly now has to open `race-execution-preferences-trigger` first — they render only while the popover is open, not merely hidden.

**Keyboard hints stay inside their buttons, hidden by CSS under a coarse pointer, not moved outside.** `index.css`'s `@media (pointer: coarse)` block (from [#1146](https://github.com/dknowles2/trusty-track/issues/1146)) gained `[data-testid='race-execution-action-row'] kbd { display: none; }`; jsdom has no `window.matchMedia`, so `RaceExecution.test.tsx` pins the invariant that rule depends on instead — every `<kbd>` lives inside the action row — rather than the media query itself.

**Testing "did a button's label wrap" cannot use `boundingBox().height`, because every button here already carries an explicit inline `height: '36px'`** (unrelated to this issue — it always sized these buttons). A wrapped label renders its second line past that fixed height rather than growing the box, so the bounding-box height reads identically whether or not the label wrapped. Confirmed by deliberately reintroducing the pre-#1157 shape (every control a flat sibling of one `nowrap`/`space-between` row) in `raceTabActionRow.spec.ts`'s own mutation testing: three of four buttons visibly wrapped and `boundingBox().height` stayed 36 on all of them. A `Range` over the *whole* button's content and its `getClientRects()` looked like the fix and was itself a false positive the other way — it also covers the icon `<svg>` and the `<kbd>`, whose boxes sit a pixel or two off the label's own `top` from ordinary `align-items: center` rounding, so it flagged "Next Heat" and "Edit" as wrapped on the real, already-fixed page. Walking only the button's own text nodes and checking each one's rects share a single `top` avoids both failure modes.

**`.race-execution-lane-row` is two lines under 600px** (`useNarrowViewport()`, not a CSS breakpoint, since the row's flex layout genuinely restructures rather than just resizing) — lane badge, photo and the *full* name on one line, time and place right-aligned on the next — rather than the one-line layout that ellipsised the name while the thumbnail, car number, time and place badge all kept their own width. On Deck's avatars drop from 60px to 32px the same way. **Previous Heats** (`RaceControl.tsx`, below the `RaceExecution` card — not part of it, but the same tab) collapses to one summary row per heat (winner, time, Re-Run) under the same breakpoint, expanding on tap to the full lane list it always showed at desktop width; `expandedPreviousHeatIds` is local `RaceControl` state, reset by nothing — a heat leaving the list because it is no longer "previous" just drops out of the set with no cleanup needed.

**`RaceControl.tsx`'s own page header drops the "Race Control" heading under 768px, and the tab strip becomes the first row instead** ([#1148](https://github.com/dknowles2/trusty-track/issues/1148)) — a different breakpoint (`useNarrowViewport(768)`) from the 600px one above, since this is about the bottom tab bar (`Navigation.tsx`'s own `MOBILE_BREAKPOINT`) already naming the page as "Control", not about the lane row's own layout. The Schedule/Race/Free Race pill drops each button's icon and tightens its padding at this width — with the icon and the desktop padding on all three, the pill does not fit one line beside the header's own `⋯` overflow at 390px and wraps to two, which is the doubled-height chrome the issue is about. That overflow (`race-control-overflow`) is where **Edit race** goes instead of a standalone pill — see `frontend-screens.md`'s own note on this. `ReadinessStrip` gained a `hideWhenReady` prop for the same page: its one-line "Ready to race" summary (`isCompact`, i.e. `overallLevel(items) === 'OK'`) is chrome ahead of the heat card once everything actually is ready, where the list form — something genuinely needs attention — is exactly what a phone still has to show; `RaceControl` passes `hideWhenReady={mobileChrome}`, so every other caller is unaffected.

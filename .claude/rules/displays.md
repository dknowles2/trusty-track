# Audience displays

Part of the Trusty Track agent guide; the index is in [`CLAUDE.md`](../../CLAUDE.md). Read this before touching `domain/displays.py`, `services/displays.py`, `Observation.tsx`, or the Displays panel.

---

### Telling an audience display what to show

Vocabulary in `domain/displays.py`, presence in `services/displays.py`, the operator's list at **Race Control → Displays** (#174).

**A display registers by *subscribing*, and that is forced rather than chosen.** A screen holds no PIN and is a `VIEWER`, and a `VIEWER` may make no mutation at all (#15) — so presence cannot be announced by calling one. The constraint produces the right shape anyway: the display is the thing being told, not the thing asking. `displayAssignment` connects on entry and disconnects in a `finally`, because a browser tab closing arrives as cancellation.

**Presence is in memory, not the database.** A display is a browser tab that is open right now; a row saying a screen was on a gym wall last March describes nothing that still exists, and nothing would ever delete it. Assignments go with it, and losing them on a restart is not a gap — an unassigned display falls back to its own URL, which is what every display did before this existed. That fallback is why the whole feature needs no migration.

**`assigned` is a separate flag from the assignment**, and collapsing them breaks the fallback. Every connected display receives an opening payload carrying *an* assignment, so a client that treats "I have a payload" as "I have been told something" overrides the URL on every screen in the room the moment it connects. The end-to-end spec caught this; no unit test could, because each side was individually correct.

**A screen that goes quiet stays listed.** It is how the operator finds out the projector at the back has dropped off the wifi, and nothing but a person can tell a switched-off screen from a dead network — so `forgetDisplay` is the only way a row leaves.

**The photo slideshow is a sixth view** (#175), not a subsystem: `SLIDESHOW` in the same enum, rules in `features/observation/slideshow.ts`. It goes in **car number order rather than shuffling** — the audience is families watching for their own child, and under a shuffle nobody can tell whether they have missed them; in order everybody comes round once per cycle. Racers with no photograph are skipped rather than shown blank, and *loading* is distinguished from *nothing to show*, because the empty state otherwise fires during the first fetch and a projector announces "No photos yet" to the room on its way to the photographs.

**`STANDINGS_ONLY` is a seventh view** (#663): the leaderboard alone, full-screen, with the Now Racing / On Deck / After That panels left out entirely — for a pack whose standings do not fit alongside them. The view lives in the same closed enum on both ends, `backend/domain/displays.py::DisplayView` and its frontend mirror `features/observation/displayView.ts`, the same as every other view here; adding it to only one side would let the operator pick something the server refuses. It needs no conditional offer the way the ceremony does (`viewOptionsFor`) — there is always a leaderboard to show, even an empty one, so it is offered unconditionally.

**Getting through a list longer than one screen is a second, orthogonal choice: `ScrollBehavior`** (`PAGING` or `SMOOTH`), carried on the assignment the same way `cycle_seconds` is — set once, and it survives a screen being switched away from `STANDINGS_ONLY` and back (`DisplayRegistry.assign` preserves whichever of the two the caller does not supply, the same pattern the cycle interval already uses). It rides on the same `assignDisplay` mutation and the same subscription payload as everything else here, rather than a display-specific mutation of its own — one door, the same reasoning `assign_display` already follows for view and interval together.

**The paging/scrolling arithmetic is a pure function of *elapsed wall-clock time*, not a counter a `setInterval` increments** (`features/observation/standingsScroll.ts`: `pageForElapsed`, `scrollOffset`, plus `pageCount`/`pageSlice`). A counter drifts the moment a tick is delayed or a background tab throttled — miss five ticks and the page is five pages behind where it should be. A function of elapsed time self-heals: whatever instant the next tick actually lands on, it computes the answer a fresh page load would give for that same instant, so a projector left running for an hour neither drifts nor needs to catch up. `StandingsOnlyView.tsx` only has to keep calling these on a regular tick (1s for paging, 50s for a visibly smooth scroll) and clean the interval up on unmount — the same split `raceFlow.ts` and `slideshow.ts` use between the rule and the React wiring that drives it. Page size and scroll distance are measured off the container's own `clientHeight` via `ResizeObserver`, with a `window.innerHeight`-based guess only until the first real measurement lands.

**A break takes it over exactly like every other view** (#592) — `intermissionActive`'s check in `Observation.tsx` runs before the `STANDINGS_ONLY` branch, the same as it already did for the standard, slideshow and projector renders. A break is a fact about the race, not about which view a display happened to be assigned, and nothing about a screen dedicated to the leaderboard is an exception to that.

**`CHECKIN` is an eighth view** ([#612](https://github.com/dknowles2/trusty-track/issues/612)) — who has checked in and who has not, grouped by racing group, for the entrance or the gym wall while check-in is under way. The operator's own roster already answers this (#204's `CheckInProgress`), but it sits behind the check-in desk's PIN on one laptop; nobody in the room can see it, which is the actual shape of the "are there any more Wolves who haven't checked in?" problem this closes. `CheckInDisplayView.tsx` renders it; `features/observation/checkIn.ts`'s `summarizeCheckIn` does the grouping and counting, pure and unit-tested, reusing `groupRacersByRacingGroup` rather than a second copy of the roster's own bucketing rule that could disagree about which bucket an unassigned racer lands in.

**No photographs on this view, deliberately.** Every other audience surface leans on a racer's portrait; this one is names and car numbers only, because the question it answers ("is my car on this list yet") needs neither, and a grid of portraits does not scale to a sixty-car pack on one screen the way a grid of numbers does. `nameDisplay` still applies to every name it prints — this is a public surface exactly like the rest of `Observation.tsx`, so `nameDisplayGuard.test.ts` carries it on the abbreviating list.

**`Assignment.show_checked_in` is `CHECKIN`'s own rider, the same shape `scroll_behavior` is for `STANDINGS_ONLY`** — set once, carried regardless of `view`, and preserved by `DisplayRegistry.assign` across a screen being switched away and back. Default `True`: DerbyNet's own kiosk lists everybody, and a pack small enough to fit is the common case. A pack that is not can switch a screen to pending-only on its row in the Displays panel, which drops an already-checked-in racer's row entirely rather than fading it — the point is screen room, and a faded row still costs a line.

**It de-emphasizes once racing begins; it does not hide, and nothing here could make it.** A car can still be admitted after the first heat (#172), so the screen has a reason to keep working — and there is no lever to hide it with anyway: a display holds no PIN and is a `VIEWER`, so nothing client-side can call `assignDisplay` to switch itself off (#15), and this feature does not add an operator-facing auto-switch either. "Racing has begun" is read off `timingStats`' own payload (`!!lastHeatResults` in `Observation.tsx`) rather than a new query — the same signal the Last Heat's Times tab already has, at no extra cost — and once true the view shows a small note that latecomers can still check in and shrinks its own type, the visual equivalent of the room's attention having moved on.

**`QRCODE` is a ninth view** ([#614](https://github.com/dknowles2/trusty-track/issues/614)) — a large, high-contrast scannable code, with the address printed underneath, for a gym crowded enough that shouting an IP address or walking a laptop around does not reach everybody. It leans on #414's voting-QR machinery end to end rather than duplicating it: `services/printables.url_png` renders the code, `networkAddresses` still works out the one address a phone off this machine can reach, and `features/core/shareAddress.ts` — moved out of `features/awards/` since it now has two callers with no single natural owner, the same `displayName.ts` reasoning — still substitutes a LAN address for `localhost`. `QRCodeDisplayView.tsx` is the render; `features/observation/qrCode.ts` holds the two pure rules (which path a target opens, and the derived headline when the race has not set its own).

**`Assignment.qr_target` decides which page the code opens — `STANDINGS` (this race's own Live page, the default) or `VOTE` (the ballot) — never an arbitrary URL.** Same rider shape as `show_checked_in` and `scroll_behavior`: set once, carried regardless of `view`, preserved across a screen being switched away and back. A closed choice between two pages rather than a free-text address, because a display holds no PIN (#15) and turning this into "point a kiosk at anything" is not a control a `VIEWER`-reachable screen should be handed. `backend/api/main.py::voting_qr` (still named for the feature it shipped with first, `/vote-qr`, deliberately not renamed — the churn to two existing callers and their tests bought nothing a docstring update did not already cover) enforces the same closed set server-side: its guard used to check the URL contained `/race/{id}/vote` and now checks either that or `/race/{id}/observation`, which is what "widen a guard deliberately" looks like rather than loosening it to anything race-scoped.

**`Race.qr_headline` and `Race.qr_wifi_note` are the one pair of settings this view reads, both nullable, both race-scoped only — no organization-level default the way terminology or name-display have one.** A headline naming a specific award ("Scan to Vote for Best in Show!") or a specific building's wifi is a fact about *this event*, not a install-wide default worth inheriting, so the dual-scope layering `resolve_terminology` uses was deliberately not built here. Empty string is how an operator clears a previously-set value back to the derived default — neither field has a legitimate empty-string value of its own, so unlike `weight_limit_oz` there is no separate `clearX` boolean: `update_race`'s existing "absent means leave alone" rule already does the rest, since a blank string is a value, not an absence.

**The Awards page's Voting panel gets a `Project QR code` shortcut**, and the race-day checklist deliberately does not — `BallotShare.tsx`'s new button opens a fresh display window (`displayIdentity.ts`'s `qrCodeWindowUrl`, sibling to `newDisplayWindowUrl`) already carrying `?view=qrcode&qr_target=vote` in its URL, which is what `displayView.ts`'s ordinary URL fallback reaches for on a screen nobody has assigned — no `assignDisplay` call needed before the code is already right. The readiness strip's `displaysItem` (`features/racing/readiness.ts`) is a *summary* surface (a count, not a set of controls) with no `raceId` in its own input at all; giving it a working shortcut button would mean threading a new parameter through a pure function for one caller's convenience, disproportionate to what the checklist is for. Reachable from the Displays panel either way.

**`OVERLAY` is a tenth view** ([#616](https://github.com/dknowles2/trusty-track/issues/616)) — a transparent broadcast graphic for an OBS Studio Browser Source, for packs streaming the event. It is the first view whose consumer is streaming software rather than a person in the room, and that changes what "correct" means for it in two ways every other view here does not have to answer.

**Its root paints no background at all — not even the theme's own.** Every sibling full-screen view sets `background: 'var(--display-bg-color)'` on its root; `Observation.tsx`'s `OVERLAY` branch sets `background: 'transparent'` instead, deliberately not reading the Display theme for that one property, so a camera feed OBS composites underneath it shows through everywhere the view is not actively drawing a panel of its own. The rest of the Display theme's tokens still apply beneath it (`...displayThemeStyle` is still spread onto the same root) — a filled badge (the Exhibition tag, the live status dot borrowed whole from `TimerStatusBadge` rather than reimplemented) still uses `--display-accent-color` / `--display-on-accent-color`, because that pairing's contrast is self-contained regardless of what is behind either colour.

**Plain text cannot lean on the theme's text/background pairing, because there is no background to pair it against.** `--display-text-color` is calibrated to read against *that theme's* `--display-bg-color`; over unknown video (a sunny gym, a dim church basement, a bright jersey) that calibration means nothing. `BroadcastOverlayView.tsx` answers this the way broadcast graphics always have: every piece of text sits on its own small, deliberately opaque panel (`SCRIM`, a fixed near-black — not a theme token) with fixed near-white text and a `textShadow` for the rare case the scrim itself sits over something equally dark. Chosen once rather than resolved per theme, because the whole point is that it has to read the same regardless of which of the seven themes is active or what the camera is pointed at.

**No racer photographs anywhere in this view, deliberately** — a broadcast lower third is text-first by convention, and every image loaded here is one more thing that can stutter mid-stream for a gain nobody watching from across a gym on a camera feed would notice. Names still go through `formatDisplayName` (#552, `nameDisplayGuard.test.ts` carries `BroadcastOverlayView.tsx` on the abbreviating list) — a stream reaches further than a gym wall, which makes name privacy *more* load-bearing here, not less.

**`Assignment.show_standings_ticker` is `OVERLAY`'s own rider**, the same shape as `show_checked_in` and `qr_target`: set once, carried regardless of `view`, preserved by `DisplayRegistry.assign` across a screen being switched away and back. Default `True` — a lower-third bar alone leaves the screen blank between heats, and the compact top-5 ticker is what fills it; a streamer who wants the bar and nothing else turns it off deliberately. The ticker itself hides when there are no standings yet regardless of the setting, the same "no blank card" rule the slideshow and check-in views already follow.

**The finish banner reuses the Projector view's own `observeHeatResult` edge-detector rather than a second copy of it, and lingers for twice as long.** `Observation.tsx`'s "sync results overlay state" block already gates on `isProjectorMode`; it now gates on `isProjectorMode || behaviour.overlay`, sharing the same `showResultsOverlay`/`overlayData`/`seenHeatResult` state — one `seen === null` rule for "is this the subscription's opening snapshot" rather than two. The linger duration is the one place the two diverge: ten seconds for `OVERLAY` against the Projector overlay's five, because a viewer joining a stream mid-heat has had none of the lead-up someone standing at the track has had, so the banner needs more time to actually be read.

**A screen's default name is derived from its own id, not drawn at random** (`domain/display_names.py`, #495). Presence is in memory, so a random name would be re-invented every restart — survivable for `Display 3`, which nobody used as a handle, and not for a name the operator has been saying out loud all morning ("put the standings on Plucky Puffin"). Seeding the draw from `display_id` — which the browser keeps in `localStorage` (`displayIdentity.ts`) — buys the same-screen-same-name property with no storage on the server at all. **Collisions are resolved on the animal, not the whole name**: `Brisk Badger` and `Bright Badger` are worse than `Display 1` and `Display 2`, because the noun is what gets read at a glance and shouted across a room, so `whimsical_name` walks its seeded candidates until it finds an animal nobody else in the race is using, and falls back to a numbered suffix only once the pool is exhausted — the walk must terminate, and the fallback is for the pathological case, not the expected one.

**A computer can drive more than one screen, and `localStorage`'s one id per machine could not say which** ([#590](https://github.com/dknowles2/trusty-track/issues/590)) — two monitors, or a projector next to an operator's own preview tab, all sharing the identity the previous paragraph describes meant assigning one moved every tab on that machine at once. `displayIdentity.ts` resolves three ways, tried in order, documented in full at the top of that file:

1. `?displayId=` in the URL always wins, and is copied into `sessionStorage` so an in-app redirect that drops the query string — Observation to the awards ceremony, on an `AWARDS` assignment — still resolves to the same screen.
2. Failing that, `sessionStorage` already holding an id for *this tab* wins — `sessionStorage` survives a reload of that tab and nothing else, which is exactly "a reload keeps a screen's id, a new tab does not inherit it."
3. Failing that, the tab claims the shared `localStorage` device id if nothing else currently holds it, or mints a fresh session-only id if something does.

**The claim is a heartbeat in `localStorage`, not a lock, and it is renewed from a `useEffect` rather than from inside `displayId()` itself.** `startDeviceClaimHeartbeat(id)` is a no-op unless `id` is the device id this tab actually claimed, and otherwise refreshes a timestamp every few seconds for as long as some page on the tab keeps calling it — wired from `Observation.tsx` and `AwardCeremony.tsx`, so it stops the moment the tab navigates away for good or closes, the same way every other `setInterval` in this tree is owned by React's effect lifecycle rather than left running. `BroadcastChannel` would resolve a collision precisely with an async round trip; a heartbeat answers synchronously off storage instead, which is what `displayId()` needs, since it has to hand back a value the instant a page mounts — before its own subscription can even ask the server who it is. The cost is a several-second window after a genuine holder closes during which a brand new tab mints a fresh id rather than reclaiming the device id — survivable, since the fresh id still works as its own screen.

**Race Control's Displays panel offers a way around the ambiguity entirely: "Open a new display window."** `newDisplayWindowUrl(raceId)` bakes a freshly minted id into the query string, so the new window opened with it (`noopener`, so it starts with no `sessionStorage` inherited from the tab that opened it) is unambiguously a second screen from the moment it loads, with nothing to contend and nothing for the operator to type.

**Identify is an event, not a state, the same shape as the ceremony's steps and for the same reason.** `Display.identify_seq` is bumped by `identifyDisplay` and carried on every payload; the screen flashes its name when the seq it receives is higher than the one it already had, and **ignores the seq it arrives holding** — an opening payload is a reconnection, not an instruction, and a screen that obeyed it would flash its name on every wifi hiccup. That is `roundCompletion.ts`'s `seen === null` rule, applied in `identifyOverlay.ts` exactly as `AwardCeremony` already applies it to `slide_seq`.

**The rename form's reroll asks the server** ([#521](https://github.com/dknowles2/trusty-track/issues/521)). It used to draw from a twelve-item list hand-copied onto the frontend, filtered only against the name being edited — so it knew nothing about any *other* row on screen and could, and did, hand the operator a name a second display was already using, defeating the whole point of `whimsical_name`'s per-race uniqueness. `suggestDisplayName(displayId, avoid)` goes through `DisplayRegistry.suggest_name`, which runs the same walk `_auto_name` runs on first connect, against the same taken set — so there is one animal vocabulary and one collision rule, not two. `avoid` carries the draft currently in the input, because the walk is otherwise seeded from `displayId` alone and would hand back the identical word on every press; the frontend passes its current draft each time so "give me another" means that. Operator-only, enforced the same way as `auditLog` — `_require_operator_role`, since the role policy only guards mutations and this changes nothing, so it is a query.

**The ceremony can be driven from the operator's list, and the command is a *step*, never a slide number** (`advanceDisplay`). The display owns the index — it is the only thing that knows which trophy is up, and it holds no PIN to report one back (#15) — so an absolute index would need the server to be the sole driver, which kills the presenter remote at the projector. A step composes with both: `Display.slide_delta` is applied to wherever the ceremony has actually got to, and `Display.slide_seq` is what makes it an event rather than a state, since two Nexts carry the same delta. `AwardCeremony` ignores the seq it *arrives* holding — an opening payload is a reconnection, not an instruction, and obeying it would jump a trophy on every wifi hiccup; that is `roundCompletion.ts`'s `seen === null` rule again. Applied during render rather than in an effect, for the same reason `RaceControl` pins its heat that way.

**A view that leaves the observation page must take the subscription with it.** The ceremony is its own route, so an `AWARDS` assignment *navigates* the screen there — and the first version let that navigation close the `displayAssignment` subscription, which is both the screen's presence and its leash: the row dropped to "Not connected" and the screen could never be told anything again, the one state the feature promises cannot happen. `AwardCeremony` therefore holds the same subscription and navigates back to the observation page when an assignment names any other view — gated on `assigned`, the same flag lesson as the opening payload, or a hand-opened ceremony would march off to the standings the moment it connected. `displays.spec.ts` round-trips it end-to-end, which unit tests cannot: the failure is a socket closing across a route change.

**The ceremony is offered as a view only when the race has an award** (`displayView.viewOptionsFor`). Choosing it for a race with none sends the screen to a page whose only content is a line saying there is nothing to announce, and most races never define any — an option that can only disappoint is worse than one that is absent. Two things about it: the option is **kept when the screen is already showing it**, because a select whose current value is missing from its own list renders with nothing chosen and the row then says nothing about what the screen is doing (reachable by deleting the last award mid-ceremony); and it is an **offer, not a permission** — the server still accepts the assignment and the ceremony page still speaks for itself, rather than the rule getting a second copy to keep in step. The panel reads the count `cache-and-network` on every visit to the tab, which is what makes an award added a minute ago on another page show up.

**A full-screen view hides the app's chrome through `ChromeContext`, not the URL.** `Navigation` used to read `?projector=true`, which stopped being sufficient the moment a view could be *assigned*: an operator switching a screen to Projector from across the room got projector mode with the navigation bar across the top, because no URL had changed. Rewriting the display's URL on assignment is the tempting fix and is worse — the URL is the fallback the assignment overrides, so writing to it makes a reload flash the previous view.

`Display` is **keyed on `displayId`** in graphcache, not embedded: `assignDisplay` returns one and the panel's list has to recognise it as the row it is already holding. `CUSTOM_KEYED_TYPES` in `api/graphqlClient.ts` exists for it, and `graphqlClient.test.ts` requires every id-less type to be in exactly one of the two lists.

### Scenes: configuring every screen at once

`domain/scenes.py` for the vocabulary, `db/models.py::Scene`/`SceneAssignment` for storage, `crud.py`'s scene functions for the persistence I/O, `api/schema.py`'s scene types and mutations for where a scene's stored rows and the registry's live state actually meet — the same split `assignDisplay` already draws ([#613](https://github.com/dknowles2/trusty-track/issues/613)). An operator moving from check-in to racing to an intermission to the ceremony used to reassign three to six screens one row at a time, under time pressure, with the wrong screen an easy mistake. A scene is that handful of clicks saved: one name (or one built-in button) that reconfigures every screen in the room at once.

**A scene entry is a whole `Assignment`, never the view alone.** The tempting shape is `screen → view`, matching what `assignDisplay`'s own `view` argument looks like in isolation — and it is wrong, because `view` alone is not what "put this screen into a known state" means once a view has riders. An Awards scene that only set `view=QRCODE` and left `qr_target` as whatever the screen happened to be showing before would sometimes point the code at the voting ballot and sometimes at the live standings depending on history nobody can see from the scene's name; a Racing scene that only set `view=STANDINGS_ONLY` would inherit whatever `scroll_behavior` the screen last had rather than the one the scene means to specify. `assignDisplay` itself already treats an *omitted* rider as "keep the current one," which is right for an incremental, single-screen edit and wrong for "recall this exact named state" — so a `SceneAssignment` row carries `view`, `cycle_seconds`, `scroll_behavior`, `show_checked_in`, `qr_target` and `show_standings_ticker` together, the same six fields `Assignment` itself holds. `updateSceneDisplay` (the one mutation that edits a single entry) is the one place omission still means "keep what this entry already had" — matching `assignDisplay`'s own shape lets the scene editor reuse the same per-display controls the live Displays panel already offers — but what gets *stored* and *applied* is always the whole six-field state, never a bare view.

**A saved scene is stored; a built-in preset is not — because one is data an operator created, the other is code.** `Scene`/`SceneAssignment` are ordinary tables, race-scoped and cascade-deleted with the race exactly like `RacingGroup` and `Award`. That is a deliberate departure from `Display`'s own live `Assignment`, which stays entirely in memory (this file's very first section) because presence has no natural end but a socket closing and a row describing a screen from last March describes nothing that still exists. A scene is a different kind of fact: an operator spent real time composing which screen shows what, wants to reuse it for the rest of *this* event, and a server restart mid-event (a real possibility on a Pi in a gym) losing that work would be the opposite of what the feature promises. The four built-in presets (`domain/scenes.PRESETS` — Check-In, Racing, Intermission, Awards, adapted from DerbyNet's own defaults) need no row at all: `ScenePreset` is a `str` enum and each preset is a short, ordered list of `Assignment`s ("roles"), applied live against whichever displays `DisplayRegistry.for_race` currently returns, in that function's own connected-first-then-by-name order. There is nothing here for a restart to lose, because nothing here was ever the operator's own data.

**Applying a scene is best-effort, not all-or-nothing, and says which entries it could not reach.** Presence is best-effort by design — a screen going quiet is the ordinary case this whole file's second section is about — so a saved scene naming a display that has since gone quiet, or one the process has simply forgotten to a restart, must not block the other five screens from being reconfigured. `applyScene`/`applyScenePreset` return an `ApplySceneResult` (`sceneId`, a `SceneApplyOutcome` per display named, `appliedCount`, `skippedCount`) rather than a bare success — `SceneAssignment.display_name` is what lets a skipped entry still say *something* ("Lobby — not connected") rather than showing a bare opaque id nobody recognises. This is the same "degrade rather than fail" shape a lane outage or a withdrawn racer already follow elsewhere in this app, applied to presence instead of a roster.

**`display_id` on `SceneAssignment` is not a foreign key.** A `Display` is presence, held only in `services/displays.py`'s in-memory registry — there is no row in the database it could reference, the same reason `LaneOutage` and `HeatLane` *do* get real foreign keys (they name rows that exist) while this deliberately does not.

**A scene is created by capturing what the screens are already showing, not by building one from a blank form.** `createScene(raceId, name)` snapshots every display `DisplayRegistry.for_race` currently knows for that race — connected or not, name and `Assignment` both — into a new named row. The operator composes the room by hand once, with the ordinary per-screen controls this file's earlier sections describe, and saves the result under a name rather than repeating those clicks for the rest of the event; `updateSceneDisplay`/`removeSceneDisplay` are the small edit surface for a scene that needs one screen's entry adjusted or dropped afterwards (the issue's stage 4, "customize scene mappings for custom venue setups") — there is no separate scene-building editor, because the live panel already is one. A scene with nothing connected yet is still created, empty, so a name can be reserved ahead of an event and filled in as screens arrive.

**Scene mutations sit beside the display mutations in every classification, not beside the race's own record.** `OPERATOR_ONLY_MUTATIONS` in `api/auth.py` and the "stays reachable on a locked race" list in `api/race_lock.py` both put `createScene`/`renameScene`/`deleteScene`/`updateSceneDisplay`/`removeSceneDisplay`/`applyScene`/`applyScenePreset` next to `assignDisplay` and its siblings, for the reason each of those files already gives that group: a scene is a saved way to call the display mutations in bulk, not a different kind of authority, and an operator wrapping up a finished, locked race can still want its screens switched back to a plain standings layout without unlocking the record to do it.

# Audience displays

Part of the Trusty Track agent guide; the index is in [`CLAUDE.md`](../../CLAUDE.md). Read this before touching `domain/displays.py`, `services/displays.py`, `Observation.tsx`, or the Displays panel.

---

### Telling an audience display what to show

Vocabulary in `domain/displays.py`, presence in `services/displays.py`, the operator's list on the race navigation row's own **Displays** page (#174; moved there from a Race Control sub-tab by #958, below).

**A display registers by *subscribing*, and that is forced rather than chosen.** A screen holds no PIN and is a `VIEWER`, and a `VIEWER` may make no mutation at all (#15) — so presence cannot be announced by calling one. The constraint produces the right shape anyway: the display is the thing being told, not the thing asking. `displayAssignment` connects on entry and disconnects in a `finally`, because a browser tab closing arrives as cancellation.

**A phone that scans the QR code is a spectator, not a display, and the opt-out is the same mechanism as registration itself** ([#1182](https://github.com/dknowles2/trusty-track/issues/1182)). Since a display registers by subscribing, not subscribing is what keeps one out — `qrTargetPath('STANDINGS', raceId, { spectator: true })` (`features/observation/qrCode.ts`) carries `?spectator=1`, and `Observation.tsx` reads it to pause the `displayAssignment` subscription outright, skip `startDeviceClaimHeartbeat`, and not render `IdentifyPresence`; `data-spectator="true"` marks the root element so a test (or a reader of the DOM) can tell which mode a given load is in. Keyed on **how the tab arrived**, not on `phoneTier`'s viewport width, because an operator may still genuinely want a phone as a real display (#1144's own point, above) — a width check cannot tell "a parent's phone, invited by the code" from "a phone the operator carried over and opened the address on by hand." `ConnectDisplayAddress.tsx` — the Displays panel's own "type or scan this to connect a screen" affordance, a different component with the opposite purpose — passes `{ spectator: false }`, since that address exists precisely so a phone or tablet scanning it *does* register. `spectator` is a **required** argument, not a default: `qrTargetPath` has exactly these two callers, with opposite answers, and a default would hand a future third caller one of them silently — see the function's own doc comment. Get this backwards and either every spectator clutters the operator's list again, or nobody can ever connect a new screen through the panel's own QR code.

**Presence is in memory, not the database.** A display is a browser tab that is open right now; a row saying a screen was on a gym wall last March describes nothing that still exists, and nothing would ever delete it. Assignments go with it, and losing them on a restart is not a gap — an unassigned display falls back to its own URL, which is what every display did before this existed. That fallback is why the whole feature needs no migration.

**`assigned` is a separate flag from the assignment**, and collapsing them breaks the fallback. Every connected display receives an opening payload carrying *an* assignment, so a client that treats "I have a payload" as "I have been told something" overrides the URL on every screen in the room the moment it connects. The end-to-end spec caught this; no unit test could, because each side was individually correct.

**A screen that goes quiet stays listed.** It is how the operator finds out the projector at the back has dropped off the wifi, and nothing but a person can tell a switched-off screen from a dead network — so `forgetDisplay` is the only way a row leaves.

**Forgetting a screen that is actually still open must not strand it** ([#758](https://github.com/dknowles2/trusty-track/issues/758)). `forget_display` used to pop the row with no connectivity check; the still-open `displayAssignment` subscription then found `registry.get` returning `None` on every future check, and every other display mutation is gated on the display existing in the registry, so nothing would ever publish to that display's own channel again — the generator hung forever, the screen froze on its last view, and it vanished from the operator's list with nothing server-side able to reach it again. Chosen fix, of the two the issue named: **the subscription notices and re-registers**, not a refuse-or-confirm. `forget_display` now publishes to the display's own `display_assignment:{id}` channel (the one every other display mutation already uses) as well as the list channel; the subscription's loop, finding the row gone, calls `registry.connect` again right there and carries on — landing on a fresh, unassigned payload, exactly the state a screen is in on a genuine first connect. This is a smaller change than teaching the mutation to check connectivity (no new refusal path, no client-side confirm dialog) and it is more in keeping with "an unassigned display falls back to its own URL" above: a forgotten-but-open screen re-registering *is* that fallback, not an exception to it.

**The photo slideshow is a sixth view** (#175), not a subsystem: `SLIDESHOW` in the same enum, rules in `features/observation/slideshow.ts`. It goes in **car number order rather than shuffling** — the audience is families watching for their own child, and under a shuffle nobody can tell whether they have missed them; in order everybody comes round once per cycle. Racers with no photograph are skipped rather than shown blank, and *loading* is distinguished from *nothing to show*, because the empty state otherwise fires during the first fetch and a projector announces "No photos yet" to the room on its way to the photographs.

**`STANDINGS_ONLY` is a seventh view** (#663): the leaderboard alone, full-screen, with the Now Racing / On Deck / After That panels left out entirely — for a pack whose standings do not fit alongside them. The view lives in the same closed enum on both ends, `backend/domain/displays.py::DisplayView` and its frontend mirror `features/observation/displayView.ts`, the same as every other view here; adding it to only one side would let the operator pick something the server refuses. It needs no conditional offer the way the ceremony does (`viewOptionsFor`) — there is always a leaderboard to show, even an empty one, so it is offered unconditionally.

**An elimination-only race's leaderboard is never empty for lack of racing, and `Observation.tsx` has to know the difference** ([#1020](https://github.com/dknowles2/trusty-track/issues/1020)). The prelim-scoped `leaderboard` subscription that `STANDINGS_ONLY`, the standard mode's own Standings tab, and the `RaceFinishedOverlay` (#869) all read stays empty for the whole of a race whose only round is `ELIMINATION` — `services.scoring._scoring_heats` excludes elimination heats from that scope by design (see `scoring.md`'s Run-off/elimination notes), so "empty" there means "wrong aggregate", not "nothing has happened yet". `features/stats/eliminationScope.ts`'s `isEliminationOnlyRace`/`defaultEliminationRound` — the same pure pair `Leaderboard.tsx` uses to default its own round selector — decide whether a race is shaped this way; `Observation.tsx` then fetches that round's own `leaderboard(roundId: ...)` through a one-shot query (the same shape the championship-round result already uses, since there is no `roundId`-scoped subscription channel) and re-fetches it on `raceStateChanged` rather than riding a subscription that was never going to carry it. All three surfaces — the live tab, `STANDINGS_ONLY`, and the finished takeover — read the same fallback, labelled in losses rather than a time, so a projector, a wall display, and the operator's own Standings page never disagree about which round's result an elimination-only race is actually showing.

**Getting through a list longer than one screen is a second, orthogonal choice: `ScrollBehavior`** (`PAGING` or `SMOOTH`), carried on the assignment the same way `cycle_seconds` is — set once, and it survives a screen being switched away from `STANDINGS_ONLY` and back (`DisplayRegistry.assign` preserves whichever of the two the caller does not supply, the same pattern the cycle interval already uses). It rides on the same `assignDisplay` mutation and the same subscription payload as everything else here, rather than a display-specific mutation of its own — one door, the same reasoning `assign_display` already follows for view and interval together.

**The paging/scrolling arithmetic is a pure function of *elapsed wall-clock time*, not a counter a `setInterval` increments** (`features/observation/standingsScroll.ts`: `pageForElapsed`, `scrollOffset`, plus `pageCount`/`pageSlice`). A counter drifts the moment a tick is delayed or a background tab throttled — miss five ticks and the page is five pages behind where it should be. A function of elapsed time self-heals: whatever instant the next tick actually lands on, it computes the answer a fresh page load would give for that same instant, so a projector left running for an hour neither drifts nor needs to catch up. `StandingsOnlyView.tsx` only has to keep calling these on a regular tick (1s for paging, 50s for a visibly smooth scroll) and clean the interval up on unmount — the same split `raceFlow.ts` and `slideshow.ts` use between the rule and the React wiring that drives it. Page size and scroll distance are measured off the container's own `clientHeight` via `ResizeObserver`, with a `window.innerHeight`-based guess only until the first real measurement lands.

**What a small screen drops (#1073 part 2).** The measuring-and-paging half of the paragraph above used to belong only to `StandingsOnlyView`; `features/observation/useMeasuredPages.ts` pulls the React wiring (the `ResizeObserver`, the ticking effect, the guess-then-measure state) out into a hook both that view and the standard mode's own Standings tab call, so a roster too long for one screen pages there too rather than growing the page underneath it — nobody scrolls an audience display **above the phone tier** (below, #1144's own exception), which is exactly what the Standings tab used to require: at a small viewport it simply cut rank 9 onward below a fold nobody was ever going to reach for. `features/observation/displayDensity.ts`'s `densityFor(viewportWidth, viewportHeight, laneCount)` is the other half — a pure, table-tested rule for what a narrow *or short* screen, showing a track of this lane count, may afford to drop, and how much room the row above the table may ever take, before paging even enters into it: below 1024px wide (the XGA floor), the racing-group division under a name (on the Standings tab and the heat cards) and a car's own name on the Timing tab disappear, while the primary columns `docs/observation-displays.md` promises (rank, racer, score, runs) never do. **Lane count is an input alongside width and height, not an afterthought** (#1073's own follow-up review): an 8-lane track — `Track.lane_count`'s own ceiling — needs a denser heat-card tier than a 6-lane one at the identical viewport, since the same row's worth of avatars is split across two more columns. The first version of this budget was tuned and gated only against a 6-lane seed, and a track configured for the data model's actual maximum broke the Standings tab's own guaranteed row count at 1280×720 — reproduced with a dedicated 8-lane/32-racer case in `displayResolutions.spec.ts`, alongside the original 6-lane one. `useDisplayDensity(laneCount)` is the thin `window.innerWidth`/`innerHeight`-watching hook over it — `laneCount` is the caller's own, since it is not something the hook can read off the window — read once in `Observation.tsx` off the race's own `track.laneCount` (defaulting to 4, `TrackInput`'s own default, before that field has answered) and passed down the same way `nameDisplay` and `laneColors` already are.

**Below 600px wide, a screen is a phone rather than a wall display, and this is the one tier that may scroll (#1144).** The QR code on the Displays panel and the standings-only view's own QR view both send a parent's phone to the Live page (`qrTargetPath('STANDINGS')` → `/race/:raceId/observation`), and the vmin-sized, fixed-viewport-budget layout every tier above shares — right down to the SVGA floor — was never tuned for that screen: at 390×844 it found 9px heat-card names, 26px/8px-text standings rows, a three-column check-in board at 7.8px names, and a standings-only header at 7.8px with the identify badge covering "Runs". `displayDensity.ts`'s `phoneTier` (`isPhoneWidth`, `< 600px` — beneath `PROJECTOR_HEAT_CARDS_SIDE_BY_SIDE_MIN_WIDTH_PX`'s own 700px floor for a portrait *tablet* held up to preview the projector view, this issue's phone is narrower still) is the one flag every affected view reads:

- **The standard Live view** (`Observation.tsx`'s standard-mode render) switches to a `rem`-sized, single-column layout that scrolls rather than budgeting `heatCardsMaxHeightVh`: Now Racing as a 2-column lane grid (wrapping, not a fixed row of however many lanes the heat holds), On Deck below it when `onDeckDepth` allows one, then the Standings table at ≥14px names — no paging, no "After That", and no **Launch Projector Mode** button, since a phone invited by the QR code has no use for it.
- **The check-in view** (`?view=checkin`) drops the `auto-fit` grid for one den per row, stacked, also scrolling.
- **The standings-only view** switches its header and row text from `vmin` to `rem` for a readable (≥12px) header, and the identify badge — ordinarily `position: fixed` in the top-right corner, which is exactly where it collided with the "Runs" column at this width — moves into the document flow above the title instead; `StandingsOnlyView.tsx` itself does not know about the badge at all, since `Observation.tsx` is the one caller that renders `IdentifyPresence` beside it.
- **The awards ceremony** (`AwardCeremony.tsx`, `/race/:raceId/awards/present`) stops centering its slide as one absolutely-positioned block — that is what let the recipient's own `(#205)` run under the fixed footer — and stacks title → artwork → name → footer in the ordinary document flow instead, with the footer's own `position: absolute` swapped for `marginTop: auto` so it is a sibling in flow rather than an overlapping layer. The footer's "Click or press → for the next award" becomes "Tap or press → for the next award" under `pointer: coarse` specifically (`index.css`'s existing `@media (pointer: coarse)` block, #1168) rather than the phone tier's own width — a touchscreen kiosk wider than 600px still taps, not clicks — via two always-rendered spans (`.ceremony-footer-hint-mouse`/`.ceremony-footer-hint-touch`) CSS toggles between, not a `matchMedia` read.
- **Whether a phone registers as a display was left untouched by this issue** — #1144 called it out as a separate, undecided question rather than something its own layout fix should quietly resolve. [#1182](https://github.com/dknowles2/trusty-track/issues/1182) is that question, decided: see "A phone that scans the QR code is a spectator" below. `phoneTier` (viewport width) still decides none of it — only how the flag's decision, keyed on how the tab arrived, plays out is on this page.

`usePhoneTier()` (`useDisplayDensity.ts`) is the bare boolean for a caller with no lane count of its own to hand `useDisplayDensity` — `AwardCeremony.tsx` has no track loaded at all by the time it first renders a slide. `Observation.tsx` reads `density.phoneTier` off the `useDisplayDensity(trackLaneCount)` it already holds and passes it down to `CheckInDisplayView`/`StandingsOnlyView` as a plain prop, rather than either of those components reading the window for themselves — the same "resolve once, pass down" shape `nameDisplay` and `laneColors` already use on that page.

**The heat cards row above the table gets a fixed share of the viewport's own height, `heatCardsMaxHeightVh`, so the table underneath always keeps a real, guaranteed minimum of rows — not just "whatever is left".** `heat-cards-layout` carries `maxHeight: '<n>vh'` and `overflow: hidden`; that is a *ceiling*, not a target, because the cards are sized to sit comfortably under it in the first place (below). `onDeckDepth` is the other lever on the same budget: `0` (just "Now Racing", below `ON_DECK_MIN_HEIGHT_PX`, the SVGA floor's own height) hands the whole row's width to one card, which is what actually buys height back — a card sharing the row with a sibling is a *narrower* card, and a long name wraps to more lines inside a narrower column at the identical font size; `1` (adds "On Deck") once width clears `SECONDARY_TEXT_MIN_WIDTH_PX` but not `AFTER_THAT_MIN_WIDTH_PX`; `2` (adds "After That") once three 340px-wide cards (the `minWidth` floor plus a card's own padding) and two 20px gaps actually fit the row without wrapping onto a second line of *cards* — 1100px, not the 1024px `heat-cards-layout` itself first assumed, once each card's own padding was counted, and the constant is deliberately conservative rather than exact: it uses the least-compact tier's padding (≤2 lanes) as the per-card floor, where the busier tested tiers (6 and 8 lanes) have a much smaller floor and so sit well clear of the 1100px line regardless. `AFTER_THAT_MAX_LANE_COUNT` (6) is a second lever on the same depth: above it, three cards at even `heatCardCompactness`'s own densest tier still cost enough of the budget to starve the table's own guaranteed rows, so depth drops back to `1` even where width and height alone would allow `2` — text cannot shrink further without crossing the legibility floor, so the budget drops a card instead, the same height-for-width trade `ON_DECK_MIN_HEIGHT_PX` already makes, applied a second way. The Standings tab's own row (`renderHeatCard`'s racer grid) is the matching half of the same fix: a *fixed* column count equal to the heat's own lane count (never `auto-fit`, which is what used to wrap a six-lane heat onto two or three rows of avatars — the actual density bug), with `minmax(0, 1fr)` letting a column shrink past its own content's width so a long name wraps *within* its column instead; the avatar, font and padding sizes are tiered by the **track's own configured lane count** (`heatCardCompactness`, four tiers: `0` at ≤2 lanes through `3` above 6), not by how many lanes happen to share a row in any one heat — every card is sized as if it were full, the conservative and consistent assumption, rather than a card's own sizing changing heat to heat as lanes fill and empty.

**The Standings tab's own table row, the heat cards, and the chrome around both (the top bar, the tab buttons, the page's own padding) are all sized to guarantee at least five Standings rows fit at the SVGA floor, for both a busy six-lane schedule and an eight-lane one — measured directly against `displayResolutions.spec.ts`'s own 24-racer and 32-racer seeds, not derived from first principles.** The outer container is `height: 100vh` (not `minHeight`) with `box-sizing: border-box` — the default `content-box` would add the page's own padding *on top of* 100vh, which is exactly 40px this page never needed to account for before `overflow: hidden` made it matter — and `display: flex, flexDirection: column`, but **only while the Standings tab is showing**: the chrome above the table (`flexShrink: 0`) keeps its natural size, and the table's own wrapper (`flex: 1, minHeight: 0, overflow: hidden`) always gets a real, CSS-guaranteed remainder rather than a JS measurement of one — no more falling back to `overflow: visible` when the heat cards leave too little room, because the viewport budget above now guarantees there is always enough. The Timing tab was never asked to guarantee a row count (its own row count is bounded by the track's lane count, not the whole roster) and keeps the original `minHeight: 100vh` — the page scrolls if it ever needs to, same as before this issue.

**A standings row never formats a racer's raw score without first checking `heatsCompleted`** ([#1145](https://github.com/dknowles2/trusty-track/issues/1145)). Every scoring strategy's aggregate starts at `0` before anything has been recorded — the fastest possible `TIMED`/`CUMULATIVE_TIME` average and the best possible `POINTS` total — so a checked-in racer who has not completed a heat yet reaches every standings surface as `score: 0, heatsCompleted: 0`, and `formatScore` alone cannot tell that apart from a genuinely fast result. The operator's own `Leaderboard.tsx` always guarded this; `Observation.tsx` (both the standard mode's Standings tab and the projector's own two render sites — the tab and its "Current Standings" panel), `StandingsOnlyView.tsx` and `BroadcastOverlayView.tsx` did not. `scoringStrategyText.ts`'s `scoreCell(entry, format)` is the one guard now, printing `NO_SCORE` ("—") in place of a fabricated result — it takes the resolved formatter as a plain callback rather than a `scoringStrategy` directly, because more than one caller here does not simply call `formatScore`: an elimination round's own standings substitute a bare `Math.round` for a loss count, both on the operator's page and on the projector's own panel. The backend already ranks a zero-heat entry last under both strategies (`domain.scoring.rank_key` sorts `heats_completed == 0` to `float('inf')` regardless of score), so this is a rendering-only fix — the ranking these entries land at was never wrong, only what they printed.

**Projector Mode stacks instead of splitting into two columns below an aspect ratio of 1** ([#1143](https://github.com/dknowles2/trusty-track/issues/1143)) — `displayDensity.ts`'s `projectorStacked`, read off `useDisplayDensity`'s own viewport tracking the same way every other density field is. The ordinary two-column layout (`.projector-grid`, heat cards at 65% width beside a `.projector-right-col` standings panel at the remaining 35%) assumes a landscape screen; on a portrait tablet propped on the check-in table, the left column's heat cards refuse to shrink below their own content width and are never given the chance to, pushing the right column off-screen (820×1180 measured `.projector-right-col`'s own `right` at 978 against an 820px-wide viewport). Gated on aspect ratio rather than a plain width threshold — the issue's own suggestion, "below ~1000px wide, or whenever aspect-ratio < 1," would also catch 800×600, this file's own tested SVGA floor for the *landscape* kiosk layout, since 800 < 1000 regardless of its aspect ratio being nowhere near portrait. Stacked, heat cards go on top with their own fixed `vh` ceiling (`projectorHeatCardsMaxHeightVh`, the stacked layout's counterpart to the standard mode's `heatCardsMaxHeightVh`) — Now Racing and On Deck side by side above `projectorHeatCardsSideBySide`'s own 700px floor (the same width `index.css`'s narrow-screen fallback already draws its own line at, so both of this issue's portrait-tablet cases keep them side by side), stacked below it — and Current Standings takes the CSS-guaranteed remainder underneath, `useMeasuredPages` (the same hook the standard mode's own Standings tab already uses) turning that measured height into however many rows actually fit rather than a fixed Top 5: "Current Standings," unlike a "Top 5" panel, has no reason to leave a portrait screen's own generous height unused.

**`.projector-left-col` needed `minWidth: 0` regardless of the stacking fix above, and finding that out is what explains the off-screen bug in the first place.** A flex item's automatic minimum size defaults to its content's own size on the *main* axis too, not only the vertical one this file's other `minHeight: 0` comments already cover — so the left column, lacking it, refused to shrink to its allotted 65% share whenever a heat card's content (a long name, at a narrow-enough width) was wider than that share, growing the column instead and pushing `.projector-right-col` out past it. Landscape viewports wide enough for the existing tested seed's names never reached this in practice, which is why it went unnoticed; 1180×820 — landscape, and deliberately *not* switched to the stacked layout by the aspect-ratio rule above, since it sits at aspect ratio 1.44 — did, once a realistic 24-racer roster's longer surnames were the ones on screen rather than a placeholder seed's short ones. Fixed once, on the column itself, rather than only inside the new stacked branch: the two-column layout keeps using it too, and it is a no-op wherever the column's content already fit its own share.

**Heat-card and standings text inside the projector view is sized in `vh`, not `vmin`, wherever the legibility floor checks it** — the racer name, lane badge, car number and racing-group division on a heat card, and the rank, name and score on a standings row (`renderProjectorRacers`, `renderProjectorStandingsRow`, both in `Observation.tsx`). `displayResolutions.spec.ts`'s own legibility floor is `2%` of the viewport's **height**, and every landscape viewport this file tests has width ≥ height, which is exactly when `vmin` (the smaller of the two dimensions) and `vh` are numerically identical — so this reads as a no-op for every landscape rendering these viewports already covered. On a portrait tablet, though, `vmin` instead follows the now-much-smaller *width*, and a coefficient tuned to clear the height-based floor in landscape reads far under it in portrait purely from the unit disagreeing with what the floor is actually measured against — not from anything about the stacked layout's own proportions. `vh` stays tied to height regardless of orientation, which is what the floor itself assumes.

**A break takes it over exactly like every other view** (#592) — `intermissionActive`'s check in `Observation.tsx` runs before the `STANDINGS_ONLY` branch, the same as it already did for the standard, slideshow and projector renders. A break is a fact about the race, not about which view a display happened to be assigned, and nothing about a screen dedicated to the leaderboard is an exception to that.

**Identify still works during a break, and the ceremony route honours a break too — neither did, for a while** ([#1071](https://github.com/dknowles2/trusty-track/issues/1071), [#1072](https://github.com/dknowles2/trusty-track/issues/1072)). `Observation.tsx`'s break branch used to return the `IntermissionOverlay` alone, omitting `IdentifyPresence` entirely — the operator's one tool for working out which physical screen is which, at exactly the moment (mid-break, reshuffling the room for the next phase) there is time to use it. Worse, that omission unmounted whichever `IdentifyPresence` instance the previous view had rendered, so its `seen`/`showConnectBadge`/`showFlash` state reset: a screen that had never disconnected re-badged itself as freshly connected once the break ended, and an Identify sent during the break was read as history rather than flashed. The fix is `useIdentifyOverlay` (`features/observation/useIdentifyOverlay.ts`) — the same `seen`-tracking state `IdentifyPresence` used to hold itself, now called once at the top of whichever page renders it (`Observation.tsx`, `AwardCeremony.tsx`), so it survives every branch that page's own render logic can switch to, break included; `IdentifyPresence` itself is now purely presentational, taking the already-computed `name`/`showConnectBadge`/`showFlash` as props rather than an `assignment` to derive them from. Don't reintroduce a per-branch `useState` inside `IdentifyPresence` — that is exactly the shape that broke.

**`AwardCeremony` had no break handling at all**, which showed up two ways: a display already on the ceremony carried on showing the trophy slide straight through a break, and applying a scene that reassigned a display *to* or *away from* the ceremony while a break was up acted immediately — `Observation`'s own `navigate(behaviour.redirectTo)` effect and `AwardCeremony`'s own "go back to Observation" effect were both unconditional, so an assignment change navigated a screen off whichever overlay it was mid-break, dropping the countdown the instant the payload arrived. Both routes now share `useLiveIntermission` (`features/core/hooks/useLiveIntermission.ts`, the same tick/derivation `Observation.tsx` used to keep to itself) and gate their own navigation effects on `!intermissionActive`, with `intermissionActive` itself in each effect's dependency array so the deferred navigation fires the moment the break actually ends rather than waiting for the assignment to change again. `AwardCeremony` renders the same `IntermissionOverlay` Observation does when a break is live, in place of the ceremony slide.

**`CHECKIN` is an eighth view** ([#612](https://github.com/dknowles2/trusty-track/issues/612)) — who has checked in and who has not, grouped by racing group, for the entrance or the gym wall while check-in is under way. The operator's own roster already answers this (#204's `CheckInProgress`), but it sits behind the check-in desk's PIN on one laptop; nobody in the room can see it, which is the actual shape of the "are there any more Wolves who haven't checked in?" problem this closes. `CheckInDisplayView.tsx` renders it; `features/observation/checkIn.ts`'s `summarizeCheckIn` does the grouping and counting, pure and unit-tested, reusing `groupRacersByRacingGroup` rather than a second copy of the roster's own bucketing rule that could disagree about which bucket an unassigned racer lands in.

**No photographs on this view, deliberately.** Every other audience surface leans on a racer's portrait; this one is names and car numbers only, because the question it answers ("is my car on this list yet") needs neither, and a grid of portraits does not scale to a sixty-car pack on one screen the way a grid of numbers does. `nameDisplay` still applies to every name it prints — this is a public surface exactly like the rest of `Observation.tsx`, so `nameDisplayGuard.test.ts` carries it on the abbreviating list.

**`Assignment.show_checked_in` is `CHECKIN`'s own rider, the same shape `scroll_behavior` is for `STANDINGS_ONLY`** — set once, carried regardless of `view`, and preserved by `DisplayRegistry.assign` across a screen being switched away and back. Default `True`: DerbyNet's own kiosk lists everybody, and a pack small enough to fit is the common case. A pack that is not can switch a screen to pending-only on its row in the Displays panel, which drops an already-checked-in racer's row entirely rather than fading it — the point is screen room, and a faded row still costs a line.

**It de-emphasizes once racing begins; it does not hide, and nothing here could make it.** A car can still be admitted after the first heat (#172), so the screen has a reason to keep working — and there is no lever to hide it with anyway: a display holds no PIN and is a `VIEWER`, so nothing client-side can call `assignDisplay` to switch itself off (#15), and this feature does not add an operator-facing auto-switch either. "Racing has begun" is read off `timingStats`' own payload (`!!lastHeatResults` in `Observation.tsx`) rather than a new query — the same signal the Last Heat's Times tab already has, at no extra cost — and once true the view shows a small note that latecomers can still check in and shrinks its own type, the visual equivalent of the room's attention having moved on.

**`QRCODE` is a ninth view** ([#614](https://github.com/dknowles2/trusty-track/issues/614)) — a large, high-contrast scannable code, with the address printed underneath, for a gym crowded enough that shouting an IP address or walking a laptop around does not reach everybody. It leans on #414's voting-QR machinery end to end rather than duplicating it: `services/printables.url_png` renders the code, `networkAddresses` still works out the one address a phone off this machine can reach, and `features/core/shareAddress.ts` — moved out of `features/awards/` since it now has two callers with no single natural owner, the same `displayName.ts` reasoning — still substitutes a LAN address for `localhost`. `QRCodeDisplayView.tsx` is the render; `features/observation/qrCode.ts` holds the two pure rules (which path a target opens, and the derived headline when the race has not set its own).

**`Assignment.qr_target` decides which page the code opens — `STANDINGS` (this race's own Live page, the default) or `VOTE` (the ballot) — never an arbitrary URL.** Same rider shape as `show_checked_in` and `scroll_behavior`: set once, carried regardless of `view`, preserved across a screen being switched away and back. A closed choice between two pages rather than a free-text address, because a display holds no PIN (#15) and turning this into "point a kiosk at anything" is not a control a `VIEWER`-reachable screen should be handed. `backend/api/main.py::voting_qr` (still named for the feature it shipped with first, `/vote-qr`, deliberately not renamed — the churn to two existing callers and their tests bought nothing a docstring update did not already cover) enforces the same closed set server-side: its guard used to check the URL contained `/race/{id}/vote` and now checks either that or `/race/{id}/observation`, which is what "widen a guard deliberately" looks like rather than loosening it to anything race-scoped.

**`Race.qr_headline` and `Race.qr_wifi_note` are the one pair of settings this view reads, both nullable, both race-scoped only — no organization-level default the way terminology or name-display have one.** A headline naming a specific award ("Scan to Vote for Best in Show!") or a specific building's wifi is a fact about *this event*, not a install-wide default worth inheriting, so the dual-scope layering `resolve_terminology` uses was deliberately not built here. Empty string is how an operator clears a previously-set value back to the derived default — neither field has a legitimate empty-string value of its own, so unlike `weight_limit_oz` there is no separate `clearX` boolean: `update_race`'s existing "absent means leave alone" rule already does the rest, since a blank string is a value, not an absence.

**The Awards page's Voting panel gets a `Project QR code` shortcut**, and the race-day checklist deliberately does not — `BallotShare.tsx`'s new button opens a fresh display window (`displayIdentity.ts`'s `qrCodeWindowUrl`, sibling to `newDisplayWindowUrl`) already carrying `?view=qrcode&qr_target=vote` in its URL, which is what `displayView.ts`'s ordinary URL fallback reaches for on a screen nobody has assigned — no `assignDisplay` call needed before the code is already right. The readiness strip's `displaysItem` (`features/racing/readiness.ts`) is a *summary* surface (a count, not a set of controls) with no `raceId` in its own input at all; giving it a working shortcut button would mean threading a new parameter through a pure function for one caller's convenience, disproportionate to what the checklist is for. Reachable from the Displays panel either way.

**`OVERLAY` is a tenth view** ([#616](https://github.com/dknowles2/trusty-track/issues/616)) — a transparent broadcast graphic for an OBS Studio Browser Source, for packs streaming the event. It is the first view whose consumer is streaming software rather than a person in the room, and that changes what "correct" means for it in two ways every other view here does not have to answer.

**Its root paints no background at all — not even the theme's own.** Every sibling full-screen view sets `background: 'var(--display-bg-color)'` on its root; `Observation.tsx`'s `OVERLAY` branch sets `background: 'transparent'` instead, deliberately not reading the Display theme for that one property, so a camera feed OBS composites underneath it shows through everywhere the view is not actively drawing a panel of its own. The rest of the Display theme's tokens still apply beneath it (`...displayThemeStyle` is still spread onto the same root) — a filled badge (the Exhibition tag, the live status dot borrowed whole from `TimerStatusBadge` rather than reimplemented) still uses `--display-accent-color` / `--display-on-accent-color`, because that pairing's contrast is self-contained regardless of what is behind either colour.

**Plain text cannot lean on the theme's text/background pairing, because there is no background to pair it against.** `--display-text-color` is calibrated to read against *that theme's* `--display-bg-color`; over unknown video (a sunny gym, a dim church basement, a bright jersey) that calibration means nothing. `BroadcastOverlayView.tsx` answers this the way broadcast graphics always have: every piece of text sits on its own small, deliberately opaque panel (`SCRIM`, a fixed near-black — not a theme token) with fixed near-white text and a `textShadow` for the rare case the scrim itself sits over something equally dark. Chosen once rather than resolved per theme, because the whole point is that it has to read the same regardless of which of the seven themes is active or what the camera is pointed at.

**No racer photographs anywhere in this view, deliberately** — a broadcast lower third is text-first by convention, and every image loaded here is one more thing that can stutter mid-stream for a gain nobody watching from across a gym on a camera feed would notice. Names still go through `formatDisplayName` (#552, `nameDisplayGuard.test.ts` carries `BroadcastOverlayView.tsx` on the abbreviating list) — a stream reaches further than a gym wall, which makes name privacy *more* load-bearing here, not less.

**`Assignment.show_standings_ticker` is `OVERLAY`'s own rider**, the same shape as `show_checked_in` and `qr_target`: set once, carried regardless of `view`, preserved by `DisplayRegistry.assign` across a screen being switched away and back. Default `True` — a lower-third bar alone leaves the screen blank between heats, and the compact top-5 ticker is what fills it; a streamer who wants the bar and nothing else turns it off deliberately. The ticker itself hides when there are no standings yet regardless of the setting, the same "no blank card" rule the slideshow and check-in views already follow.

**The finish banner reuses the Projector view's own `observeHeatResult` edge-detector rather than a second copy of it, and lingers for twice as long.** `Observation.tsx`'s "sync results overlay state" block already gates on `isProjectorMode`; it now gates on `isProjectorMode || behaviour.overlay`, sharing the same `showResultsOverlay`/`overlayData`/`seenHeatResult` state — one `seen === null` rule for "is this the subscription's opening snapshot" rather than two. The linger duration is the one place the two diverge: ten seconds for `OVERLAY` against the Projector overlay's five, because a viewer joining a stream mid-heat has had none of the lead-up someone standing at the track has had, so the banner needs more time to actually be read.

**A screen's default name is derived from its own id, not drawn at random** (`domain/display_names.py`, #495). Presence is in memory, so a random name would be re-invented every restart — survivable for `Display 3`, which nobody used as a handle, and not for a name the operator has been saying out loud all morning ("put the standings on Plucky Puffin"). Seeding the draw from `display_id` — which the browser keeps in `localStorage` (`displayIdentity.ts`) — buys the same-screen-same-name property with no storage on the server at all. **Collisions are resolved on the animal, not the whole name**: `Brisk Badger` and `Bright Badger` are worse than `Display 1` and `Display 2`, because the noun is what gets read at a glance and shouted across a room, so `whimsical_name` walks its seeded candidates until it finds an animal nobody else in the race is using, and falls back to a numbered suffix only once the pool is exhausted — the walk must terminate, and the fallback is for the pathological case, not the expected one.

**A computer can drive more than one screen, and `localStorage`'s one id per machine could not say which** ([#590](https://github.com/dknowles2/trusty-track/issues/590)) — two monitors, or a projector next to an operator's own preview tab, all sharing the identity the previous paragraph describes meant assigning one moved every tab on that machine at once. `displayIdentity.ts` resolves three ways, tried in order, documented in full at the top of that file:

1. `?displayId=` in the URL always wins, and is copied into `sessionStorage` so an in-app redirect that drops the query string — Observation to the awards ceremony, on an `AWARDS` assignment — still resolves to the same screen.
2. Failing that, `sessionStorage` already holding an id for *this tab* wins — `sessionStorage` survives a reload of that tab and nothing else, which is exactly "a reload keeps a screen's id, a new tab does not inherit it."
3. Failing that, the tab claims the shared `localStorage` device id if nothing else currently holds it, or mints a fresh session-only id if something does.

**The claim is a heartbeat in `localStorage`, not a lock, and it is renewed from a `useEffect` rather than from inside `displayId()` itself.** `startDeviceClaimHeartbeat(id)` is a no-op unless `id` is the device id this tab actually claimed, and otherwise refreshes a timestamp every few seconds for as long as some page on the tab keeps calling it — wired from `Observation.tsx` and `AwardCeremony.tsx`, so it stops the moment the tab navigates away for good or closes, the same way every other `setInterval` in this tree is owned by React's effect lifecycle rather than left running. `BroadcastChannel` would resolve a collision precisely with an async round trip; a heartbeat answers synchronously off storage instead, which is what `displayId()` needs, since it has to hand back a value the instant a page mounts — before its own subscription can even ask the server who it is. The cost is a several-second window after a genuine holder closes during which a brand new tab mints a fresh id rather than reclaiming the device id — survivable, since the fresh id still works as its own screen.

**Race Control's Displays panel offers a way around the ambiguity entirely: "Add a second screen on this computer"** (renamed by [#1249](https://github.com/dknowles2/trusty-track/issues/1249) from its original, more literal wording, which also demoted it to a `secondary-btn` beside **Open Live here** — this is the rarer of the two setups, not its equal). `newDisplayWindowUrl(raceId)` bakes a freshly minted id into the query string, so the new window opened with it (`noopener`, so it starts with no `sessionStorage` inherited from the tab that opened it) is unambiguously a second screen from the moment it loads, with nothing to contend and nothing for the operator to type.

**Identify is an event, not a state, the same shape as the ceremony's steps and for the same reason.** `Display.identify_seq` is bumped by `identifyDisplay` and carried on every payload; the screen flashes its name when the seq it receives is higher than the one it already had, and **ignores the seq it arrives holding** — an opening payload is a reconnection, not an instruction, and a screen that obeyed it would flash its name on every wifi hiccup. That is `roundCompletion.ts`'s `seen === null` rule, applied in `identifyOverlay.ts` exactly as `AwardCeremony` already applies it to `slide_seq`.

**The rename form's reroll asks the server** ([#521](https://github.com/dknowles2/trusty-track/issues/521)). It used to draw from a twelve-item list hand-copied onto the frontend, filtered only against the name being edited — so it knew nothing about any *other* row on screen and could, and did, hand the operator a name a second display was already using, defeating the whole point of `whimsical_name`'s per-race uniqueness. `suggestDisplayName(displayId, avoid)` goes through `DisplayRegistry.suggest_name`, which runs the same walk `_auto_name` runs on first connect, against the same taken set — so there is one animal vocabulary and one collision rule, not two. `avoid` carries the draft currently in the input, because the walk is otherwise seeded from `displayId` alone and would hand back the identical word on every press; the frontend passes its current draft each time so "give me another" means that. Operator-only, enforced the same way as `auditLog` — `_require_operator_role`, since the role policy only guards mutations and this changes nothing, so it is a query.

**The ceremony can be driven from the operator's list, and the command is a *step*, never a slide number** (`advanceDisplay`). The display owns the index — it is the only thing that knows which trophy is up, and it holds no PIN to report one back (#15) — so an absolute index would need the server to be the sole driver, which kills the presenter remote at the projector. A step composes with both: `Display.slide_delta` is applied to wherever the ceremony has actually got to, and `Display.slide_seq` is what makes it an event rather than a state, since two Nexts carry the same delta. `AwardCeremony` ignores the seq it *arrives* holding — an opening payload is a reconnection, not an instruction, and obeying it would jump a trophy on every wifi hiccup; that is `roundCompletion.ts`'s `seen === null` rule again. Applied during render rather than in an effect, for the same reason `RaceControl` pins its heat that way.

**That "two Nexts carry the same delta" is exactly why this channel's transport must never drop one** ([#881](https://github.com/dknowles2/trusty-track/issues/881)). `slide_delta` is overwritten on the registry row, not accumulated, and the client applies it once per distinct `slide_seq` it observes — so the *only* record that two steps happened, rather than one, is that the subscriber received two separate wake-ups. `display_assignment:{id}`'s `pubsub.subscribe` call opts out of the ordinary bounded, drop-oldest queue (`api/pubsub.py`'s `MAX_QUEUE_SIZE`) for exactly this reason: a channel most subscriptions treat as disposable snapshots is, on this one, a sequence of events with no compensating "newest supersedes the rest" property. Don't reintroduce the default bound here without re-solving this.

**A view that leaves the observation page must take the subscription with it.** The ceremony is its own route, so an `AWARDS` assignment *navigates* the screen there — and the first version let that navigation close the `displayAssignment` subscription, which is both the screen's presence and its leash: the row dropped to "Not connected" and the screen could never be told anything again, the one state the feature promises cannot happen. `AwardCeremony` therefore holds the same subscription and navigates back to the observation page when an assignment names any other view — gated on `assigned`, the same flag lesson as the opening payload, or a hand-opened ceremony would march off to the standings the moment it connected. `displays.spec.ts` round-trips it end-to-end, which unit tests cannot: the failure is a socket closing across a route change.

**The ceremony is offered as a view only when the race has an award** (`displayView.viewOptionsFor`). Choosing it for a race with none sends the screen to a page whose only content is a line saying there is nothing to announce, and most races never define any — an option that can only disappoint is worse than one that is absent. Two things about it: the option is **kept when the screen is already showing it**, because a select whose current value is missing from its own list renders with nothing chosen and the row then says nothing about what the screen is doing (reachable by deleting the last award mid-ceremony); and it is an **offer, not a permission** — the server still accepts the assignment and the ceremony page still speaks for itself, rather than the rule getting a second copy to keep in step. The panel reads the count `cache-and-network` on every visit to the tab, which is what makes an award added a minute ago on another page show up.

**A full-screen view hides the app's chrome through `ChromeContext`, not the URL.** `Navigation` used to read `?projector=true`, which stopped being sufficient the moment a view could be *assigned*: an operator switching a screen to Projector from across the room got projector mode with the navigation bar across the top, because no URL had changed. Rewriting the display's URL on assignment is the tempting fix and is worse — the URL is the fallback the assignment overrides, so writing to it makes a reload flash the previous view.

**Live was a race-row destination that behaved like a launch point, and Displays lived two clicks from where an operator actually stands** ([#958](https://github.com/dknowles2/trusty-track/issues/958)). Clicking **Live** in the race navigation row used to replace the operator's own page with the audience display — still wearing the operator's chrome (race row, version, Settings) — while its other half, launching Projector Mode, sat on that same page; meanwhile the Displays panel was a Race Control sub-tab, unreachable from the row an operator lands on first. Two changes, not one flag: **Displays now occupies the race row's own sixth slot**, in the exact position Live used to hold (`Navigation.tsx`'s `links`, and `frontend-screens.md`'s "One row of race navigation") — Control keeps only Schedule / Race / Free Race. **Opening Live is a button, not a route.** `DisplaysPanel.tsx`'s own **Open Live here** — the one primary action on the page — `window.open`s this same computer's Live page in a new tab, `noopener`, carrying no fresh `?displayId=`, because the point is putting *this* screen on air rather than contending with its own identity. `pageTitle.ts` lost its stale `/control/displays` → "Displays" mapping (that path now redirects, and the label would otherwise have named a page Control can no longer show) and gained one for the new top-level route instead.

**A third button offering the identical `window.open` with a view pre-picked was dropped** ([#1249](https://github.com/dknowles2/trusty-track/issues/1249)). #958 above originally gave this section three look-alike buttons — Open Live, a projector shortcut, and the second-screen escape hatch below — each with the same icon and the same weight, with nothing on the page saying how they differed. The projector shortcut was never a third concept: `?projector=true` is the URL fallback for the same **Projector** entry every row's own view dropdown already offers (`displayView.ts`), so the button was "Open Live" with one assignment step pre-done, reachable a second way from the Live page's own **Launch Projector Mode** button (`Observation.tsx`, unchanged by this issue) and a third way from the row dropdown itself. Two buttons, unequal weight, under headings that name what they're for (**This computer** / **Other devices**) replaced the row of three: **Open Live here** (`primary-btn`, the one action most operators want) and **Add a second screen on this computer** (`secondary-btn`, no icon, the rarer #590 case below) — see that issue for the full before/after and the caption wording.

**The operator chrome now hides on `/observation` unconditionally, not only for the full-screen views** (`isProjectorMode`, the slideshow, `STANDINGS_ONLY`, check-in, the QR code, the broadcast overlay). Almost every path onto this page is a display: the `displayAssignment` subscription registers the tab as one from the moment it connects, the shareable "type this address into a screen" address (`ConnectDisplayAddress`, which deliberately opts its own generated URL *out* of the spectator flag below) carries no query string, and even the ceremony's own `navigate('/race/:id/observation')` round-trip (this file's "a view that leaves the observation page" paragraph) is one display handing off to another. There is no remaining path onto this route that is the operator's own operating page — which is exactly what removing Live from the race row was for — so a marker on the URL (`?display=1`, say) was considered and rejected: it would leave the primary, documented way a wall display is set up (typing or scanning the bare `ConnectDisplayAddress` URL) still wearing the chrome, which is the literal bug report. Don't gate this decision on a URL flag; gate it on nothing; the page hides its chrome, full stop — regardless of whether the tab behind it turns out to register as a display or, since [#1182](https://github.com/dknowles2/trusty-track/issues/1182), a spectator. This is unconditional for the *chrome* only — the body-scroll lock and the full-screen layout choice both still read the narrower `isFullScreenView`, since an ordinary tablet on Standings or Timing is meant to scroll.

**The QR code view's own target is the one exception to "the shareable address carries no query string"** — `?spectator=1` (below) is precisely a query string on this route, added after the paragraph above was written. It changes nothing about the chrome decision, which reads none of the URL; it only reaches the `displayAssignment` subscription this page also holds. Two independent gates share the one route, each reading a different signal — don't collapse them into one flag.

`Display` is **keyed on `displayId`** in graphcache, not embedded: `assignDisplay` returns one and the panel's list has to recognise it as the row it is already holding. `CUSTOM_KEYED_TYPES` in `api/graphqlClient.ts` exists for it, and `graphqlClient.test.ts` requires every id-less type to be in exactly one of the two lists.

### A camera is a display with a role (#177 stage 1a)

Backend half — the registry, the mutation, the upload/serve endpoints, and the retention rule. The frontend half — the `/camera` page, capture, `FakeCamera` and the display playback — is stage 1b, below.

**`domain.displays.DisplayRole`** (`DISPLAY`/`CAMERA`) is orthogonal to `DisplayView` — a role is a fact about the *device* (does it hold a camera), a view is a fact about what its screen currently shows. A device that is both camera and screen is still one connection, `CAMERA`, with "show the replay here" ticked on its own preview; it is not a second registration. **A camera registers through the exact same `displayAssignment` subscription an ordinary screen does**, with `role: CAMERA` on the connect argument — not a second subscription — so it appears in the operator's Displays list, answers Identify/rename/forget, and gets a whimsical name exactly like a screen. `services.displays.Display` carries `role`, `track_id` (which track's timer this camera listens to, set by the operator-only `setCameraTrack(displayId, trackId)` mutation — refused for anything that is not a `CAMERA`) and `last_clip_at` (an ISO timestamp, null until the first clip lands, stamped by `registry.record_clip` — what Race Control's own camera badge, 1b's job, will read to say "Finish line — connected, last clip 2s ago"). `role` is written on every connect, reconnect included, unlike `name`: a browser tab does not change what page it is between reloads, so there is no "keep the old one" case to defend the way there is for a rename.

**`Assignment.replays`** (default `True`) is the per-display toggle for whether a screen plays a heat's clip after its results overlay — the same rider shape as `show_standings_ticker`: set once on `assignDisplay`, carried regardless of `view`, omitted means leave alone. Default on because the happy path (per the issue) is a display already showing results also playing the replay; a display that never sees a clip (no camera at this event) simply never has anything to play.

**The clip key is `(heatId, recordedAt)` — the exact pair `resultsOverlay.ts`'s `observeHeatResult` already uses to decide "is this a new result".** `Heat.recorded_at` moves on every re-run (`crud.stamp_recorded`), so a clip captured against a result that has since been corrected is keyed to a value that no longer matches anything — `POST /replay/` refuses it with 409 rather than storing a clip for a run the record no longer holds. `heatReplay(raceId)`'s payload carries the same pair, and a display comparing it against the last one it acted on (never the subscription's own opening payload — an opening payload is a reconnection, not an instruction, the same `seen === null` rule as everywhere else in this file) is how a screen reconnecting mid-event avoids replaying a heat from ten minutes ago. This is 1b's job to apply; this stage only has to deliver the pair honestly.

**Retention is delete-after-next-heat, and nothing fancier — stage 2 is what changes that.** `services.replays.ReplayStore` is an in-memory index, `{(heat_id, recorded_at): [ReplayClip, ...]}`, over files under `DATA_DIR/replays/` (never `uploads/` — see `ops.md`'s backup section). `ReplayStore.discard_other_heats(race_id, keep_heat_id)` is called from two places, both meaning "this heat is no longer the one whose replay might still be shown": `updateHeatResult`/the timer's own result path (an *earlier* heat's clip is now stale — this heat's own clip has not been uploaded yet, so it is never what that call removes) and `prepareHeat` (the heat that just finished has had its turn). Nothing survives a restart: `sweep()` empties the directory at startup and after a restore, the same "index is process memory" shape `DisplayRegistry` uses for presence — except unlike a forgotten display row, a lingering clip file would actually cost SD card space on a Pi, so the directory is emptied rather than merely forgotten.

**`heatReplay(raceId)` is a snapshot channel, not a delta, and the default bounded pub/sub queue is the right one for it.** Every wake re-reads `ReplayStore.latest_for_race(race_id)` — the *current* clip set for whichever heat is the race's active one — rather than trusting the payload (always `None`) or accumulating anything client-side. Two cameras uploading close together publish two wake-ups; if the first is dropped for a full queue, the second still finds both clips already in the store, so nothing is lost the way `display_assignment`'s `slide_delta` would be (see `CLAUDE.md`'s pubsub paragraph — check any new subscription against it before assuming the default bound is safe, and this is the reasoning that makes it safe here).

**No PIN on `POST /replay/`, and that is the same auth story `displayAssignment` already has, not a new hole.** A camera is a display; a display holds no credential (#15). What actually guards the route is narrower but real: a caller has to already know a specific heat's *current* `recordedAt`, a value that only exists once that heat's result has just been recorded — not a fact a drive-by request can supply. Refused outright on the demo (`_refuse_on_demo`), the same as `POST /upload/`, since it writes a caller-supplied file to disk. `GET /replay/<name>` needs no credential either: the name is a UUID, the same access-control shape `/static/<filename>` already uses for a photograph (#552's reasoning extended to video — a video of the finish line is a video of children too), served `Cache-Control: no-store` because a clip can be deleted within seconds of being served.

### The camera page, capture, and playback (#177 stage 1b)

`/race/:raceId/camera` (`features/camera/pages/Camera.tsx`) registers exactly like a display, with `role: CAMERA` on the `displayAssignment` connect argument — the operator's own Displays panel shows a track picker and a "last clip" line in place of the view/riders an ordinary screen row offers, and Race Control gets a badge per camera (`CameraBadges.tsx`, reading the same `displays` data filtered to `role === 'CAMERA'` rather than a second query).

**Capture is WebCodecs, as the issue specifies — `VideoFrame`s → `VideoEncoder` → a keyframe-aware ring → a real WebM mux, with the `VideoFrame`s themselves sourced one of two ways (below).** An earlier version of this stage used `MediaRecorder` instead, reasoning that a `VideoEncoder` pipeline needed a muxer this tree did not have; a review caught a correctness bug in that version before merge, not just an accepted trade-off. `MediaRecorder` emits its container header only in the *first* timesliced `Blob` of a recording session, and the original `ring.ts` evicted that first chunk like any other once a session ran longer than the ring's own ~10s capacity — which every real capture does, since a camera is opened and aimed well before the first heat and left running for the length of the event. Every clip cut after that point was built from headerless fragments with nothing for a decoder to configure itself from: an upload that returned 200 OK and a file no `<video>` element could play, for nearly all real-world usage — reachable by no test in the PR that introduced it, because `FakeCamera`'s own capture path was a plain `fetch` of a canned file that bypassed the buggy pipeline entirely.

The fix, now in place: `capture.ts`'s `startCapture` forces a fresh keyframe roughly every second (`KEYFRAME_INTERVAL_US`), so the ring always holds a self-sufficient decode point from at most ~1s earlier, whatever has aged out; `ring.ts`'s `coveringFromKeyframe(fromMs, toMs)` is what a cut actually asks for — the most recent keyframe at or before the window starts (falling back to the earliest the ring still holds), through every chunk up to where it ends — rather than the raw `[fromMs, toMs]` window verbatim; and `mux.ts` (MIT `webm-muxer`) writes one correct, fresh WebM header for whatever chunks a cut hands it, every time, which is the property `MediaRecorder`'s blob-per-slice output never had and is what moves "does the container have a header" out of the ring's problem entirely. Both `ring.ts` and `capture.ts` carry the full account in their own headers.

**`FakeCamera` goes through this exact same pipeline, not a shortcut around it** — the previous version's own bypass is what let the header/eviction bug ship with `instantReplay.spec.ts` fully green. `capture.ts`'s `fakeCameraTrack` decodes `fake-camera.webm` through a looping, hidden `<video>` drawn to an offscreen `<canvas>` (`drawLoop`, below), captured off the canvas (`HTMLCanvasElement.captureStream`, standard and typed; `HTMLVideoElement.captureStream` is not) into an ordinary `MediaStreamTrack` — indistinguishable, from `startCapture` onward, from a real device's. `instantReplay.spec.ts`'s own post-eviction test proves this end to end: it waits past the ring's own 10s capacity before cutting a clip, then asserts the result is not merely uploaded (`200 OK`, which the buggy version also returned) but genuinely decodable — `readyState >= 2` and a finite, positive `duration` on the display's own `<video>` element.

**`VideoFrame`s come from `MediaStreamTrackProcessor` where it exists, and from a canvas where it does not — WebKit has never shipped that API, on iOS or on desktop** ([#1294](https://github.com/dknowles2/trusty-track/issues/1294)). The gate used to require both `VideoEncoder` *and* `MediaStreamTrackProcessor` (`browserSupport.ts`'s old `hasWebCodecs`), which refused every WebKit browser outright and told an iPhone user already in Chrome to "use Chrome, Edge or Safari 16.4+" — self-contradictory, and wrong regardless of which browser they tried next, since every browser on iOS is WebKit under its own skin (iOS Chrome's UA carries `CriOS`, not `Chrome`; iOS Edge's carries `EdgiOS`, which itself contains the substring `Edg` — neither survives the desktop-style "AppleWebKit and not {Chrome,Edge}" exclusion `isAppleWebKit` uses for desktop Safari, so iOS is checked on its own OS token instead, `isIOS`). `VideoEncoder` is now the only thing the gate genuinely requires (`hasVideoEncoder`, `cameraSupport`'s `message`); a missing `MediaStreamTrackProcessor` earns no message at all, because `capture.ts`'s `frameSourceFor` covers it. Two messages replace the old one: `IOS_NEEDS_UPDATE_MESSAGE` ("Instant replay needs a newer iOS — update iOS and try again in Safari") on iOS with no `VideoEncoder`, since naming a different browser there is never the fix; `WEBCODECS_MESSAGE` (the original wording, now honest again) everywhere else.

**`capture.ts`'s `canvasFrameSource` is the fallback frame source** — a hidden `<video>` plays `track`, `drawLoop` (the same redraw loop `fakeCameraTrack` uses, extracted rather than duplicated) redraws it onto an offscreen `<canvas>` on every decoded frame, and each draw becomes `new VideoFrame(canvas, { timestamp })`, timestamped off `requestVideoFrameCallback`'s own `mediaTime` (seconds, converted to the microseconds every other timestamp in this file uses). It feeds `startCapture`'s `pump` loop exactly as a processor's own reader would — same encoder, same keyframe cadence, same ring, mux and upload downstream; nothing past the frame source knows or cares which one produced what it is encoding. `frameSourceFor` picks it whenever `MediaStreamTrackProcessor` is absent, or when `Camera.tsx`'s `?noProcessor=1` forces it — the same one-shot-override shape `?fake=1`/`?ringMs=` already are, letting `instantReplay.spec.ts` exercise this path in Chromium (which does carry the processor) alongside a second case that deletes the global via `addInitScript`, proving the gate itself lets a genuinely-absent-processor browser through. **Neither test proves this works on a real iPhone** — both run inside Chromium, and what they change is only which frame source `capture.ts` picks, never WebKit's own implementation of `new VideoFrame(canvas, {...})`, which no CI runner can exercise.

**The RTT correction (`correctedT0Ms`) is latency compensation, not clock-skew correction, and `clipBounds.ts`'s own doc comment says so explicitly now.** It has no way to be the latter: there is no `(client_send, server_at, client_recv)` triple to derive a clock offset from, since `CAMERA_PING_QUERY` returns only `{ version }`. This matches issue #177's own prescribed method (half the measured round trip) and the magnitude a genuine skew could introduce is bounded by ordinary LAN/Wi-Fi RTT — smaller than the pre/post-roll margins already budgeted below — so it is a real but non-blocking gap, not a bug.

**The clip window is computed in `clipBounds.ts`, a pure module with no DOM or WebCodecs in it.** `t0` is the most recent `timerStatus(trackId)` transition to `RUNNING` (`latestRunningAt`), corrected as above — `CameraPingQuery` (`query { version }`, the smallest field in the schema) is timed every `PING_INTERVAL_MS` and a running median of the last `MAX_RTT_SAMPLES` samples is kept, robust to one stalled ping the way a mean would not be. The clip itself is `t0 − 1.5s` through `t0 + slowestLaneTime + 1.0s` (`timerSyncedBounds`, defaults adjustable via its own optional parameters). A `TimerType.NONE` track has no `RUNNING` transition to anchor to, so `noneFallbackBounds` instead skips back a fixed 4s from the instant the result landed — DerbyNet's own shape, named in the issue — and the camera's own status line says so ("no electronic timer — cutting a fixed clip around each result").

**The cut is triggered by the exact same `seen === null` edge-detector `resultsOverlay.ts` uses, reused rather than copied** — `Camera.tsx` calls `observeHeatResult` against `timingStats(raceId)`'s own payload, so a camera that has just reconnected treats the subscription's opening snapshot as history, not a heat to capture. **`t0_offset_ms` is recomputed against wherever the muxed clip actually begins, not the originally requested `bounds.startMs`** — a cut that had to start on an earlier keyframe (the common case) begins before the request asked for, and the offset sent on `POST /replay/` has to say so. `capture.ts`'s own `VideoFrame`/`EncodedVideoChunk` timestamps are microseconds against the track's own reference clock, not wall-clock epoch time, so `startCapture` fixes an `originOffsetMs` from the very first frame of each session (`Date.now() - firstFrame.timestamp / 1000`) and applies it to every later chunk before it ever reaches the ring — getting this wrong doesn't fail loudly locally; it surfaces as a silent GraphQL Int32 overflow on `heatReplay`'s own `t0OffsetMs` field once the clip's absolute-vs-relative timestamps disagree by an epoch's worth of milliseconds, found only by `instantReplay.spec.ts` running against a real browser's WebCodecs implementation rather than by any unit test.

**Playback is `Observation.tsx` subscribing to `heatReplay(raceId)` and applying the identical rule a third time** (`replayPlayback.ts`'s tests pin this explicitly, reusing `observeHeatResult` against `{heatId, recordedAt}` rather than a home-grown comparison) — a screen reconnecting mid-event must not replay a result from before it reloaded, and a purge (the next heat, or an earlier result changing) stops whatever is playing rather than leaving it frozen. A queued clip set waits for the results overlay (where the view has one) to clear first, so a display never shows both at once; multiple cameras play in `cameraId` order, back to back. `showings`/`rate` (2× at 50%, the issue's own defaults) are **per-display, client-side `localStorage`, not a server column** — `replayPlayback.ts`'s `readReplaySettings`/`writeReplaySettings` — because stage 1 has no operator-facing control for them; only the on/off `replays` rider lives on `Assignment` (above).

**`FakeCamera` is `/camera?fake=1`, not a separate component** — it bypasses both browser gates (no `getUserMedia` prompt, no secure-context requirement) and sources its `MediaStreamTrack` from `frontend/public/fake-camera.webm` rather than a device, per the paragraph above. That file is a 3-second, 320×220 VP8 clip made with `ffmpeg -f lavfi -i testsrc=size=320x220:rate=15:duration=3 -c:v libvpx -b:v 50k -crf 30 fake-camera.webm`, well under 300KB, looped so a test driving more than one heat has a source longer than the file's own 3s. `frontend/e2e/functional/instantReplay.spec.ts` and `frontend/e2e/docs/screenshot-instant-replay.spec.ts` are both built on it, since no CI runner has a camera.

**`?trackId=` is the other query parameter the page reads, beside `?fake=1`/`?ringMs=`/`?noProcessor=1`, and it is the only one of the four that is write-once rather than read-only** ([#1254](https://github.com/dknowles2/trusty-track/issues/1254)). It comes from `DisplaysPanel.tsx`'s own "Connect a camera" code — `cameraWindowUrl(raceId, trackId)` bakes it in beside a fresh `displayId`, the same fresh-identity shape `qrCodeWindowUrl` already uses for a screen, with the track resolved to the race's own track when the install has more than one and it is among them, else the first. `Camera.tsx` applies it exactly once: an effect guarded by a ref (never a plain condition, which a re-render or a reconnect would pass again) fires `setCameraTrack` the first time a real `displayAssignment` payload and the tracks list have both answered — and only then, never before, so an empty tracks array mid-load is never mistaken for "unknown track id." The ref flips true the instant there is enough to decide, whichever way the decision goes: the assignment already carrying a `trackId` (a reconnect, or an operator's own choice from the page's dropdown or the Displays row's picker) refuses the preset outright rather than overwriting it, and an id naming no track this install has is ignored silently. **The page's own dropdown and the Displays row's own picker have to keep winning after this runs, or a camera the operator has since repointed would snap back on its next reload** — the preset is only ever the *starting* value a fresh connect begins at, exactly the same relationship `?view=timing` already has with an `assignDisplay` call that has since overridden it (this file's "An assignment wins over the screen's URL," `reference/displays.md`'s own words for it).

### Stored clips: a retention setting, not a second pipeline (#177 stage 2)

Everything above this section is unchanged by stage 2 — the upload, the key, the auth story, the snapshot-channel reasoning for `heatReplay`. What changes is what happens to a clip *after* it would ordinarily be purged.

**`Organization.keep_replays` (default off) is the one switch, and the default keeps stage 1a's exact behaviour byte-for-byte.** Off, `services.replays.discard_or_retain` (the one door every purge call site — `api.schema._purge_older_replays`, `services.timer.manager`'s own result path — now goes through, rather than calling `ReplayStore.discard_other_heats` directly) does exactly what it always did: a clip is deleted the moment its heat stops being the current one. On, that call becomes a no-op — nothing about "this heat is no longer current" deletes a stored clip — and a separate rule, retention, decides what survives instead.

**Two independent, optional bounds, not one mode.** `replay_retention_heats` (last-N-heats) and `replay_retention_mb` (a total-size cap across the race) can be set together, either alone, or neither (genuinely unbounded — an operator's own choice, not a default this feature invents; a size cap alone protects the SD card regardless of how bursty an event's heat count is, and a heat-count cap alone is the one a mutation test can assert deterministically without needing to fabricate file sizes, which is why both are offered rather than picking one). `domain.replays.heats_beyond_count`/`heats_beyond_size` are the two pure rules, each taking a list of `HeatActivity` (heat id, its most recent `recorded_at`, its total bytes) and returning which heat ids fall outside the bound — no database, no filesystem, the same "pin the property with no I/O" shape `test_domain_scheduling.py` uses. `services.replays.enforce_retention` is the caller: applied once per upload (`POST /replay/`, immediately after `record_stored_clip`), not once per heat transition, because a bound on the whole stored set is a different question from which one heat is current.

**Retention is by *heat*, not by *clip* or by *run*.** A heat re-run while the setting is on keeps every `recorded_at` it was ever captured under, as long as the heat itself is inside the bound — a corrected result's clip is history worth keeping *alongside* the run it replaced, not a second heat competing for the same budget. `models.HeatReplay.recorded_at` is what makes the two runs distinguishable rows; `HeatActivity.last_activity` is whichever of a heat's own `recorded_at` values sorts latest, which is what the heat's own place in the last-N ordering is decided by.

**`models.HeatReplay` is the persisted half; `services.ReplayStore` stays the live half, and the two are kept in step rather than merged into one.** A row is written **only when `keep_replays` was on at the moment a clip landed** (`record_stored_clip`) — never retroactively — so `Heat.replays` (the GraphQL field a Schedule-tab ▶ reads, batched through `RequestLoaders.replays_for_heat` the same way `lanes` is) being empty and the setting being off are the same fact told two ways, with no separate read of the setting needed anywhere a ▶ might show. `heat_id` carries `ON DELETE CASCADE` (#125's rule, same as `heat_lanes`), so the *row* disappears for free when a heat does; the *file* does not, since SQLite cannot delete one for us.

**Every heat-deleting path calls `services.replays.discard_rows_for_deleted_heats` before the row goes, and the reset case is why "a heat with a stored clip can't be deleted anyway" is not a safe argument to skip that call.** `deleteHeat`/`deleteRound`/`deleteFreeRaceHeat`/`deleteRunOffHeat` and `generate_heats_for_round`'s `clear_existing` branch all refuse a heat that currently *has* results — but `crud.stamp_recorded` clears `Heat.recorded_at` back to `None` on a plain reset ("Re-Run"), with no effect on any `HeatReplay` row already written for that heat's earlier `recorded_at`. A reset heat therefore looks exactly like a never-run one to every one of those refusal checks, while still naming a real clip — which is what makes it deletable, and what makes skipping the cleanup call on the theory that "a heat with a clip always has results" the exact bug a reviewer of this stage reproduced. `discard_rows_for_deleted_heats(db, heat_ids)` (called with the heat id(s) about to be removed, always *before* the delete — after it, the rows are already gone to the DB cascade and cannot be queried) is the one helper every path routes through, collecting each affected `HeatReplay` row, unlinking its file, and forgetting it from `ReplayStore`; `services.replays.discard_clips_for_race` is the same function scoped to a whole race, called from `deleteRace` before `crud.delete_race` removes its heats. The reset itself is deliberately not a call site — see `discard_rows_for_deleted_heats`'s own docstring for why a reset's old clip stays as history rather than being purged at reset time.

**The serving guard is an index lookup now, not `is_relative_to` plus `is_file()` alone — the stage 1a review's own "worth revisiting with longer retention" note.** `ReplayStore.known_filename` is checked before `GET /replay/<name>` ever touches the filesystem; an unknown name is refused with no `stat` call at all, and `is_relative_to` stays underneath it as belt-and-braces. This matters more once retention exists to trim files the store no longer considers live, and more still once a restart can rebuild the index from a table that might disagree with what is actually on disk (next paragraph) — either divergence used to be silently served if a stale name happened to still resolve inside the directory.

**Startup rebuilds the index from the table instead of sweeping, exactly when `keep_replays` is on.** `ReplayStore.rebuild_from_db` reads every `HeatReplay` row (oldest `recorded_at` first, so `add`'s "last call wins" update of `_latest_key` lands on the genuinely most recent heat per race) and repopulates `_clips`/`_latest_key`/`_filenames` from it, touching no file — every name the table still holds is exactly the file that should still be on disk, since nothing else ever writes to `DATA_DIR/replays/`. Off, `sweep()` runs exactly as stage 1a always did. A **restore** always sweeps regardless of the setting, and also deletes every `HeatReplay` row outright: the archive's database snapshot can carry rows from whenever the backup was taken, but `ops.md`'s backup section is unchanged by this stage — `replays/` itself is still never archived — so those rows would name files that never made the trip. Left in place they would be broken links waiting to be discovered by a Schedule tab; deleted, the restored race simply has no stored clips, which is the truth.

**A heat re-run's clip re-keys, and the display side needed no change for it** — `(heat_id, recorded_at)` was always the pair `heatReplay` and `resultsOverlay.ts`'s `observeHeatResult` key a result by (this file's "The clip key" paragraph, above); stage 2 only changes how long an *old* key's row and file survive, not what the key is.

**The demo refuses `updateInitialConfig` wholesale already, which is what `keepReplays` needs — no new `demo_policy` entry.** See `InitialConfigInput.keep_replays`'s own docstring in `api/schema.py` for why this is a deliberate departure from `setDebugMode`/`setThemes` (#1079, #1080), which were split *out* of that bundle for the opposite reason: those two are harmless enough to offer a demo visitor despite the bundle's wholesale refusal, where turning stored clips on means a caller-supplied file lands on disk on every future upload — exactly the hazard the bundle's refusal already exists to block.

**Privacy follows the same rule as a racer's photograph, because there is no second rule to invent.** `GET /replay/<name>` is credential-free by the same reasoning `/static/<filename>` already is (#552, extended in stage 1a: a video of the finish line is a video of children too) — a non-enumerable name is the access control, on a `VIEWER`-reachable route, exactly like every photograph this app already serves with no gate beyond that. Stage 2 does not add a privacy *setting* of its own: a longer-lived clip is not a more exposed one — the name is exactly as non-enumerable a week later as it is a second later — so the actual mitigation is what already existed (backup exclusion, the non-enumerable name) plus the operator's own choice not to turn the setting on. Don't add a `keepReplays`-scoped credential or a second name-display-style gate here; if a future issue wants finer-grained control over who can fetch a clip, it is a new privacy primitive shared with photographs, not a replay-specific one.

### Intermission highlights (#177 stage 3)

`IntermissionOverlay` gains a second mode: instead of the faint next-up preview, a break can loop the current round's stored replay clips. Every idea this stage needed was already sitting nearby — the countdown machinery (`domain/intermission.py`), the stored clips themselves (stage 2, above), and `ReplayPlayer` — so this stage is mostly wiring, with four decisions worth recording.

**A fourth stored field on the break, not a display-side setting.** `Race.intermission_highlights` (`domain.intermission.State.highlights`) rides beside `ends_at`/`paused_remaining_seconds`/`label` — set by `startIntermission(…, highlights: Boolean)`, cleared by `end()`, carried through `pause`/`resume`/`extend` exactly like `label` is. It has to be race-scoped and stored for the identical reason the rest of the break is (this file's very first intermission paragraph): every screen watching the race, including the operator's own laptop on reload, has to agree on whether this break is showing clips. A per-display toggle was the alternative and is wrong for a different reason too — see the next paragraph.

**Refused, not silently downgraded, when it is not eligible.** `crud.start_intermission` raises rather than quietly serving `highlights: false` when `Organization.keep_replays` is off or the race has no stored clip yet (`crud.race_has_stored_replays`). `IntermissionControl.tsx`'s own checkbox is offered under the identical two conditions (`Race.replayCount > 0` and `initialConfig.keepReplays`), so the only way the mutation ever sees `highlights: true` outside them is a client that has drifted from the server's own rule — exactly the case a refusal is supposed to catch, the same reasoning `RacingGroup` range overlap and the run-off racer checks in other rule files give for refusing rather than degrading.

**Every display honours it the same way — highlights ignore the per-display `replays` toggle.** `Assignment.replays` (stage 1a, above) is about the *results flow*: does this screen play a heat's clip after its own results overlay. Highlights are the operator's explicit content for the break they just called, the same "a break takes it over exactly like every other view" rule (#592, this file's own section above) that puts `IntermissionOverlay` ahead of `STANDINGS_ONLY`. A screen with `replays` off during ordinary racing still shows highlights during a break it is assigned to — the two are different questions, and conflating them would mean a screen configured never to interrupt with a replay (a standings-only wall display, say) also going dark during the one moment highlights are the point.

**Ordering lives in exactly one place, and it is not the display it plays on.** `features/observation/highlights.ts` — `highlightRoundId` (the round of the last recorded heat, or the latest round with a clip if nothing has been recorded yet), `highlightOrder` (fastest winning time first, a heat with no timed winner last, bounded to the most recent `LAST_N_HEATS` (10) by heat number when a round holds more clips than that), and `highlightCaption` — is pure, taking plain heat/lane/clip values and returning what to play and what to say under it. **Two callers share it through one hook, not two copies of the wiring around it**: `features/observation/useIntermissionHighlights.ts` builds the reel from whatever heats/rounds/racers its caller already fetched, loops it (the same "adjust during render" pattern `RaceControl.tsx` pins `selectedHeatId` with, `race-day-ui.md`, rather than a `useEffect` that would show one stale frame first), and resolves the winner's caption — `Observation.tsx` and `AwardCeremony.tsx` both call it and both fetch the same heats/lanes/replays shape into their own race query for it to read. The ceremony route missed this the first time a highlights break was built — `AwardCeremony.tsx` rendered `IntermissionOverlay` with no `highlightClip` at all, so a screen assigned to the ceremony fell back to the ordinary next-up preview during a highlights break while every other display looped the reel, contradicting this file's own "every display honours it the same way" paragraph above and #1072's point that a break takes the ceremony route over exactly like every other display. **Multiple cameras on one heat → the first clip by `cameraId`** (`highlights.ts`'s `firstClip`) — the same "keep the loop short" reasoning stage 1's own clip-key paragraph gives for playing one clip at a time rather than every camera's.

Race Control's own summary line ("Highlights: 8 clips from Round 2", `IntermissionControl.tsx`) is **not** derived from `highlights.ts` — `Race.highlightsSummary` (`api/schema.py`'s `_highlights_summary`) is a small, separately tested duplicate of just the round-*selection* half of `highlightRoundId`, because a full heats+lanes+replays query re-fetched into every one of `IntermissionControl`'s three compact mounts (`RaceExecution.tsx`) to derive a single count and round name was measured against reusing the TypeScript rule and rejected. This is the same "a rule split across two languages has no single file either can import" tradeoff `domain.name_display.format_display_name` documents for its own Python/TypeScript split — see that function's docstring in `terminology-and-names.md` — applied to a much smaller rule than that one. The play *order* and the caption text stay exclusively in `highlights.ts`; only "which round, how many clips" is answered twice.

**The countdown stays visible, moved to a corner badge, while a clip plays** — `IntermissionOverlay`'s `highlightClip` prop switches the whole layout, not just swaps out the preview: the centered mascot-and-countdown becomes a small pill in the top-right corner (`intermission-overlay-countdown-corner`) so a room that glances over still knows how long is left, and the clip itself (`ReplayPlayer`, muted, normal rate — never the results-overlay's slow showings) takes the screen's attention instead. `highlightClip` is `null` — falling back to the ordinary layout — both when highlights are off and when they are on but nothing has been resolved yet (a break called before `Observation.tsx`'s own query has answered); the two read identically on screen, which is deliberate, since neither has anything to show.

### Finish frames, slow motion, and multi-camera ordering (#177 stage 4)

The last of #177's four stages — polish on top of the clip itself (stage 1), stored clips (stage 2) and highlights (stage 3), with no schema change: everything here lives in `features/observation/finishFrames.ts`, `services/displays.py`'s in-memory registry, and the resolvers that read it.

**A finish-frame mark is `t0OffsetMs + laneTime*1000`, and that arithmetic is the whole of it.** `finishFrames.finishMarks(clip, lanes)` places one mark per lane inside a clip — `clip.t0OffsetMs` (stage 1b's own "where the gate opened inside the clip") plus that lane's recorded time in milliseconds — sorted by when each happens. Three kinds of lane are excluded outright rather than shown with nothing to say: a DNF or an unset time (`time == null || time <= 0`, `formatLaneTime`'s own convention), a skipped lane, and — the one worth stating plainly — **a mark past the clip's own `durationMs` is dropped, never clamped to the last frame**. A clamped tick at the very end would claim a lane finished on camera when the picture never shows it; excluding it is the honest answer, and it is reachable in practice, not merely theoretical — see the capture-timing paragraph below.

**The clip's own post-roll turned out not to exist yet at cut time, and fixing that was this stage's one production change outside the marker/window code itself.** `Camera.tsx`'s cut effect used to read the ring the instant a result landed and mux whatever `coveringFromKeyframe(bounds.startMs, bounds.endMs)` found — but `bounds.endMs` includes the post-roll (`DEFAULT_POST_ROLL_MS`, 1s past the slowest lane), which is *future* footage relative to the instant a result is recorded (a result lands essentially the moment the slowest lane crosses the line). The ring cannot contain frames from a moment that has not happened yet, so every clip's actual muxed duration stopped within milliseconds of `t0OffsetMs` — no real post-roll, and so no lane's own finish mark could ever land inside the produced clip's `durationMs`, defeating this stage's own headline feature before a single line of marker code ran. The fix is `await`ing until `bounds.endMs` has actually passed (`waitMs = bounds.endMs - Date.now()`) before reading the ring — a `NONE`-timer clip's `bounds.endMs` is already in the past (`noneFallbackBounds` anchors to "now" minus a skipback), so this is a no-op for that fallback and costs nothing there. This delays every upload by roughly the post-roll's own length (about a second), which is consistent with, not a change to, the guide's existing "a few seconds after the result lands" wording.

**The timeline strip's interactivity reuses `ReplayPlayer`'s existing `controls` flag rather than a new prop.** `controls` already distinguished the auto-playing, hands-off overlay (`false`) from a clip somebody opened on purpose (`true`, the ▶ modal) — the same distinction "nothing clickable on the audience overlay" needs, so the strip's ticks render `disabled` (unclickable, unfocusable — a real DOM guarantee, not merely un-wired) whenever `controls` is `false`, with no second flag to keep in step with it. Clicking an enabled tick seeks the video to `mark.atMs / 1000`, calls `pause()`, and shows the lane's caption ("L3 Xander Brake 3.076 s") overlaid; clicking again (or pressing Space, or clicking anywhere in the player) resumes. `,`/`.` step one frame (`1/30`s — this app's own capture rate throughout #177) while paused. The caption itself renders as a small dark pill with fixed white text regardless of context, deliberately not `--display-text-color` — that token defaults to white at `:root` whether or not the player happens to be inside `Observation.tsx`'s own themed subtree, so reading it inside the ordinary light-background ▶ modal produced invisible white-on-white; a caption that supplies its own contrast (the same approach `BroadcastOverlayView.tsx` already takes, for the identical reason) reads correctly in both places.

**The caption updates on the frame it belongs to, not up to 250ms late.** `ReplayPlayer` prefers `requestVideoFrameCallback` (most Chromium/Safari builds) over `timeupdate` (jsdom, Firefox — `timeupdate`'s own granularity) for the per-frame sync that drives both the caption and the slow-motion rate — see `finishFrames.isWithinSlowMotionWindow`'s own call site in that component.

**Two marks close enough together stack onto a second row rather than overlapping** ([#1218](https://github.com/dknowles2/trusty-track/issues/1218)) — a covered mark is an unclickable mark. The strip used to place every mark on one row, in ascending-`atMs` DOM order, with no `z-index`; whenever two lanes finished within about a badge-width of each other, the later lane's button painted over the earlier one's and silently ate its hit area — an operator's real click landed on the wrong lane, and Playwright's own click-retry loop found the identical thing ("subtree intercepts pointer events"), retrying forever since the covered element genuinely was visible/enabled/stable. `finishMarkLayout.ts`'s `layoutFinishMarks` is the fix: a pure, DOM-free, greedy placement — sorted by `atMs`, each mark takes the lowest-numbered row whose own last-placed mark is at least `minGapPct` away, up to `MAX_ROWS` (3) before the overflow starts sharing the bottom row. The strip's own height grows with the row count (`rows * MARK_ROW_HEIGHT_PX`, the existing 28px per row).

**`minGapPct` is measured against the strip's own real width, not a constant tuned for one caller's reference frame** — a first pass shipped a flat `5`, reasoned from `LaneBadge`'s ~22px against the ▶ modal's own ~640px (22/640 ≈ 3.4%, rounded up for margin), and a review caught that this badly understates the audience overlay's narrowest real size: `OVERLAY_STYLE`'s `width: 80vmin; maxWidth: 90vw` resolves to ~312px at the phone tier `displays.md` documents elsewhere on this page (<600px), where a flat 5% is ~16px — under a single badge's own width, so two marks the layout calls "not colliding" could still visually overlap on that screen. `useElementWidth` (`features/core/hooks/`) measures the strip's own rendered width with a `ResizeObserver`-backed callback ref, and `ReplayPlayer.tsx` derives `minGapPct = (BADGE_PX / measuredWidth) * 100` from it; the old flat `5` survives only as `FALLBACK_MIN_GAP_PCT`, used before the strip has been measured (first paint) or in an environment with no `ResizeObserver` at all (jsdom, this project's own tests). A hover/focus `z-index` raise (`.replay-finish-mark` in `index.css`) is a second, smaller tie-break on top of the row split — **for the ▶ modal only**: the audience overlay's marks render `disabled` (`!interactive`), and a disabled `<button>` neither receives focus nor reliably triggers `:hover`, so the measured `minGapPct` and the row split are that surface's entire defence.

**The slow-motion window is one span, not the whole clip.** `slowMotionWindow(marks, durationMs)` — one second before the first finish through 200ms after the last, clamped to `[0, durationMs]` — is what `rate` (the auto-playing overlay's own `showings`/`rate` setting, `replayPlayback.ts`) now applies *inside*; outside it, and on any clip with no marks at all, playback stays at normal speed exactly as before this stage. This is what keeps a clip's lead-in and its final second of camera settling from being dragged out at half speed for no reason, and it is why `ReplayPlayer` needs the clip's own `durationMs` as a prop rather than reading `HTMLVideoElement.duration` — the server's own figure is authoritative and available immediately, where the video element's can read `Infinity` on a still-buffering WebM.

**Multi-camera ordering moved from the frontend to the registry, and `orderClipsByCameraId` is gone.** Stage 1 had no operator-facing ordering control, so `replayPlayback.ts` sorted a heat's clips alphabetically by `cameraId` on the client. `Display.camera_order` (default `0`, meaningless for a `DISPLAY` role — the same shape `track_id` already has) is the operator's own per-camera value, set through `setCameraOrder(displayId, order)` (`services.displays.DisplayRegistry.set_camera_order`, same refusal shape as `set_camera_track`: `None` for an unseen display or a non-`CAMERA` one). `api/schema.py`'s `_order_replay_clips` sorts by `(camera_order, camera_id)` — an in-memory registry lookup per clip, not a query, so it costs `test_query_counts.py` nothing — and both `heatReplay` and `Heat.replays` apply it before the clips ever reach a client. `Observation.tsx`, `HeatReplayModal.tsx`'s camera picker, and `highlights.ts`'s `firstClip` (stage 3, updated here) all now simply use the array order the server hands back rather than re-sorting it a second way; an untouched multi-camera race — nobody has ever pressed the Displays panel's new ↑/↓ — still gets a fully-determined, stable order (ties on `camera_order` break on `camera_id`), identical to what stage 1's own alphabetical rule always produced.

**The Displays panel's ↑/↓ reassigns the whole visible order to `0..N-1` on every press, rather than swapping two raw values.** Swapping only the pair being moved is a no-op whenever they are tied — which every pair of untouched cameras is, both at the default `0` — so the control would silently do nothing on the very first press of a fresh, never-ordered multi-camera race. `DisplaysPanel.tsx`'s `moveCameraOrder` instead re-derives the full sorted camera list with the move applied and calls `setCameraOrder` once per row whose new index differs from its stored value, which converges to a real, fully-ordered sequence regardless of what was stored before — including "everyone still at `0`."

**Precision is stated once, honestly, and shown wherever a mark is.** A mark's placement inherits stage 1b's own sync error — half the measured round trip, plus roughly a frame at 30fps — so `ReplayPlayer`'s timeline strip carries a `title` naming that ("Finish marks are placed from the timer's own times; expect them within a frame or two of the picture") and `docs/instant-replay.md`'s own "Finish Frames and Slow Motion" section says the same thing in the reader's own words. Neither claims frame-perfect placement; both say what "within a frame or two" actually means for a parent looking at the picture.

### Scenes: configuring every screen at once

`domain/scenes.py` for the vocabulary, `db/models.py::Scene`/`SceneAssignment` for storage, `crud.py`'s scene functions for the persistence I/O, `api/schema.py`'s scene types and mutations for where a scene's stored rows and the registry's live state actually meet — the same split `assignDisplay` already draws ([#613](https://github.com/dknowles2/trusty-track/issues/613)). An operator moving from check-in to racing to an intermission to the ceremony used to reassign three to six screens one row at a time, under time pressure, with the wrong screen an easy mistake. A scene is that handful of clicks saved: one name (or one built-in button) that reconfigures every screen in the room at once.

**A scene entry is a whole `Assignment`, never the view alone.** The tempting shape is `screen → view`, matching what `assignDisplay`'s own `view` argument looks like in isolation — and it is wrong, because `view` alone is not what "put this screen into a known state" means once a view has riders. An Awards scene that only set `view=QRCODE` and left `qr_target` as whatever the screen happened to be showing before would sometimes point the code at the voting ballot and sometimes at the live standings depending on history nobody can see from the scene's name; a Racing scene that only set `view=STANDINGS_ONLY` would inherit whatever `scroll_behavior` the screen last had rather than the one the scene means to specify. `assignDisplay` itself already treats an *omitted* rider as "keep the current one," which is right for an incremental, single-screen edit and wrong for "recall this exact named state" — so a `SceneAssignment` row carries `view`, `cycle_seconds`, `scroll_behavior`, `show_checked_in`, `qr_target` and `show_standings_ticker` together, the same six fields `Assignment` itself holds. `updateSceneDisplay` (the one mutation that edits a single entry) is the one place omission still means "keep what this entry already had" — matching `assignDisplay`'s own shape lets the scene editor reuse the same per-display controls the live Displays panel already offers — but what gets *stored* and *applied* is always the whole six-field state, never a bare view.

**A saved scene is stored; a built-in preset is not — because one is data an operator created, the other is code.** `Scene`/`SceneAssignment` are ordinary tables, race-scoped and cascade-deleted with the race exactly like `RacingGroup` and `Award`. That is a deliberate departure from `Display`'s own live `Assignment`, which stays entirely in memory (this file's very first section) because presence has no natural end but a socket closing and a row describing a screen from last March describes nothing that still exists. A scene is a different kind of fact: an operator spent real time composing which screen shows what, wants to reuse it for the rest of *this* event, and a server restart mid-event (a real possibility on a Pi in a gym) losing that work would be the opposite of what the feature promises. The four built-in presets (`domain/scenes.PRESETS` — Check-In, Racing, Intermission, Awards, adapted from DerbyNet's own defaults) need no row at all: `ScenePreset` is a `str` enum and each preset is a short, ordered list of `Assignment`s ("roles"), applied live against whichever displays `DisplayRegistry.for_race` currently returns, in that function's own connected-first-then-by-name order. There is nothing here for a restart to lose, because nothing here was ever the operator's own data.

**Applying a scene is best-effort, not all-or-nothing, and says which entries it could not reach.** Presence is best-effort by design — a screen going quiet is the ordinary case this whole file's second section is about — so a saved scene naming a display that has since gone quiet, or one the process has simply forgotten to a restart, must not block the other five screens from being reconfigured. `applyScene`/`applyScenePreset` return an `ApplySceneResult` (`sceneId`, a `SceneApplyOutcome` per display named, `appliedCount`, `skippedCount`) rather than a bare success — `SceneAssignment.display_name` is what lets a skipped entry still say *something* ("Lobby — not connected") rather than showing a bare opaque id nobody recognises. This is the same "degrade rather than fail" shape a lane outage or a withdrawn racer already follow elsewhere in this app, applied to presence instead of a roster.

**`display_id` on `SceneAssignment` is not a foreign key.** A `Display` is presence, held only in `services/displays.py`'s in-memory registry — there is no row in the database it could reference, the same reason `LaneOutage` and `HeatLane` *do* get real foreign keys (they name rows that exist) while this deliberately does not.

**A scene is created by capturing what the screens are already showing, not by building one from a blank form.** `createScene(raceId, name)` snapshots every display `DisplayRegistry.for_race` currently knows for that race — connected or not, name and `Assignment` both — into a new named row. The operator composes the room by hand once, with the ordinary per-screen controls this file's earlier sections describe, and saves the result under a name rather than repeating those clicks for the rest of the event; `updateSceneDisplay`/`removeSceneDisplay` are the small edit surface for a scene that needs one screen's entry adjusted or dropped afterwards (the issue's stage 4, "customize scene mappings for custom venue setups") — there is no separate scene-building editor, because the live panel already is one. A scene with nothing connected yet is still created, empty, so a name can be reserved ahead of an event and filled in as screens arrive.

**Applying a scene must not reach across to a display that has since moved to a different race** ([#756](https://github.com/dknowles2/trusty-track/issues/756)). `SceneAssignment` is keyed only by `display_id`, and `DisplayRegistry.connect` overwrites a known display's `race_id` whenever it reconnects — correct behaviour, and exactly what happens when a kiosk browser navigates from one race's `/observation` to another's while keeping its `localStorage` device id (see "A computer can drive more than one screen" above). `apply_scene_preset` never had this problem: it scopes through `registry.for_race(race_id)`, so a display belonging to another race is never in the list it builds assignments from in the first place. `apply_scene` used to call `registry.assign(display_id, …)` directly with no equivalent check, so a scene saved for race A could silently reconfigure a screen that had since moved to race B — race A's operator saw an ordinary success (`appliedCount: 1`) for a screen no longer in their own Displays list, and race B's screen was hijacked out from under its own operator with nothing saying why. `_apply_assignments` now takes an `expected_race_id`, checked against the display's *current* `race_id` before anything is touched; a mismatch is treated exactly like "not connected" — the same `SceneApplyOutcome(applied=False)` shape, since from the scene's own point of view a display that has moved on is equally unreachable. `apply_scene` passes the scene's own `race_id`; `apply_scene_preset` passes it too, belt and braces, even though `for_race` already made it redundant there.

**Scene mutations sit beside the display mutations in every classification, not beside the race's own record.** `OPERATOR_ONLY_MUTATIONS` in `api/auth.py` and the "stays reachable on a locked race" list in `api/race_lock.py` both put `createScene`/`renameScene`/`deleteScene`/`updateSceneDisplay`/`removeSceneDisplay`/`applyScene`/`applyScenePreset` next to `assignDisplay` and its siblings, for the reason each of those files already gives that group: a scene is a saved way to call the display mutations in bulk, not a different kind of authority, and an operator wrapping up a finished, locked race can still want its screens switched back to a plain standings layout without unlocking the record to do it.

### Naming what each view actually shows, on the panel itself ([#948](https://github.com/dknowles2/trusty-track/issues/948))

The per-display `<select>` in `DisplaysPanel.tsx` used to offer ten bare names with nothing saying what any of them looked like — "Standings" vs "Standings only" vs "Projector" could only be told apart by walking to the screen, the thing the panel exists to avoid.

**Each `VIEW_OPTIONS` entry carries a `description`, lifted from `docs/reference/displays.md`'s own words rather than written fresh** — one sentence, not the reference page's full paragraph, so the two cannot say different things about the same view; that page stays the one place the full explanation lives. A test in `displayView.test.ts` calls every entry's `description` and asserts it is non-empty, the same shape `test_every_mutation_is_classified` uses on the backend — a view added later with no description fails the build rather than shipping a blank line an operator finds on race day.

**`description` is a function of the resolved terminology words, even for the seven entries that ignore the argument.** Two of the ten mention the racing-group or vehicle word ("Racer photos": *headshot, car, name, number, den*; "Check-in progress": *grouped by den*), and a pure `.ts` module takes the resolved words as a parameter rather than importing `useTerminology()` itself — the same split `setupChecklist.ts`'s `checklistFor` draws. Every entry is the same shape `(words: TerminologyWords) => string` rather than a mix of plain strings and functions, so a test can call all ten identically and `DisplaysPanel.tsx` resolves `useTerminology()` once and passes it through.

**Grouping is data in `displayView.ts`, not markup in the panel.** Each entry also carries a `group: ViewGroup` — `'During racing' | 'Between heats' | 'Before racing' | 'After'`, the same four buckets and the same view assignment the issue names — and `groupedViewOptions` folds a (possibly `viewOptionsFor`-filtered) list into that fixed order, dropping a group that ends up empty rather than rendering an empty `<optgroup>` (reachable when the ceremony is filtered out of a race with no awards). Keeping the grouping as a pure data transform, rather than writing the four buckets out in JSX, is what makes it testable with no DOM involved and keeps there being exactly one list describing the views — `VIEW_OPTIONS`' own declaration order is untouched, so `viewOptionsFor`'s existing tests (offering everything to a race with awards, keeping the ceremony option for a screen already showing it) needed no change beyond expecting the panel's own rendered order to now be grouped.

**No thumbnails.** The issue marked a 96px preview image per view as optional; it is a screenshot-maintenance surface of its own (ten more images to regenerate on every visual change to a view) and out of proportion to what closes the actual gap, which is a sentence.

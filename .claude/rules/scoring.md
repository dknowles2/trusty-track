# Scoring, track records, scale speed, and lane colours

Part of the Trusty Track agent guide; the index is in [`CLAUDE.md`](../../CLAUDE.md). Read this before touching `domain/scoring.py`, `services/scoring.py`, ties, run-off heats, `services/records.py`, `domain/scale_speed.py` or `domain/lane_colors.py`.

---

### Scoring

Rules in `domain/scoring.py`, database wiring in `services/scoring.py`. `TIMED` averages heat times (a recorded `0.0` is treated as a 9.999s DNF penalty); `POINTS` sums placements. Both are lower-is-better. `get_leaderboard(db, race_id)` returns sorted standings.

**Standings cover preliminary rounds only** — rounds with no `advancement_source`. Settled in #17. A championship field is chosen *from* the standings, so folding championship results back in is circular: `record_heat_result` re-runs advancement on every result, so a final-round time could change who was supposed to be in the final. It also mixes populations, since a championship average is taken against the fastest cars rather than the whole field.

`get_leaderboard(db, race_id)` is prelim-scoped by default. Pass `round_id` for one round (this is how the UI shows championship results) or `scope=ALL` for the pre-#17 whole-race average. The `Race.leaderboard` GraphQL field takes `roundId` and `includeAllRounds` to match.

**A missing placement must never be a reward under `POINTS`** ([#225](https://github.com/dknowles2/trusty-track/issues/225)). `POINTS` sums, so a racer with fewer placements scores *better* — the failure #26 keeps arriving by new routes. Four routes are now closed, two ways: a lane outage mid-round (#171) and a latecomer (#172) set `Round.disrupted` and the round is dropped from `POINTS` standings; a **skipped lane** and a **DNF** (a recorded time ≤ 0, which the timer assigns no place) are scored as **last place in their heat** — the racers assigned, not the track's lane count. The penalty routes and the drop routes are different because they are different facts: a penalised lane *exists* and can classify last; a disrupted round has racers who were *scheduled fewer heats*, and there is no lane to penalise. `TIMED` needs neither for a skip — an average is scale-free — and keeps its 9.999 s penalty for a DNF. A lane with a real time but no place stays uncounted: that is a half-finished hand entry, not a scratch.

**A tie shares a rank** ([#226](https://github.com/dknowles2/trusty-track/issues/226)). `rank_key` still breaks ties by racer id so the *order* is deterministic, but `standings_ranks` stamps competition ranks (1, 1, 3) over it — otherwise a tie for a trophy or the last championship slot was resolved by registration order and no screen ever said so. Racers who have not raced keep strictly increasing positions; tying them would make a pre-race leaderboard a wall of rank 1. Advancement and awards still cut by position (`standings[:n]`, `standings[place-1]`), which is unchanged and now *visible*: the operator sees the shared rank and settles it with a race-off or a corrected time.

**`LeaderboardEntry.racingGroupDivision` is the racing group's category, riding along for branding** ([#298](https://github.com/dknowles2/trusty-track/issues/298)) — `RacingGroup.division` was assignable and stored since the app's first spec but shown nowhere. Named `racingGroupDivision` rather than `division`, because `rank` on a standings row already means the finishing position and the same collision would recur under any name sharing that row; the two would otherwise be mistaken for the same field on the same type. `Leaderboard.tsx`'s Racing Group column and `Observation.tsx`'s heat cards and live standings all read `racingGroupDivision`/`division` straight off the payload — no formatter, since the stored text already is the label.

**`RacingGroup.division` is free text, where it was a seven-value `Rank` enum** (`LION` through `ARROW_OF_LIGHT`) — [#496](https://github.com/dknowles2/trusty-track/issues/496) stage 2. Nothing server-side ever read the enum to decide anything, so nothing structural was lost making it text; the frontend's `RacingGroupManager` offers the traditional Cub Scout ranks as picker *suggestions* (`categoryPresets.ts`'s `CATEGORY_PRESETS`, the same "fill an ordinary field" pattern `awardTemplates.ts` uses for ready-made awards) rather than a constraint, so a school typing "3rd Grade" is exactly as valid as a pack picking "Wolf" from the list. The field's UI label is the fixed word **Category**, not a configurable term — narrower than the issue's open question about a third configurable vocabulary slot, resolved that way because the field is branding-only and a third term was judged not worth eight more columns. Migration `0030_racing_group_division` carries every stored enum code to the display string `rankLabel()` used to compute (`LION` to `"Lion"`); `rankLabel()` itself is gone, since a stored value is now already its own label. The downgrade reverses by exact label match and sends anything else to `OTHER` — lossy, and said so in the migration's docstring, the same tradeoff the enum-era `rankLabel()` made for a code it did not recognise.

### Racing without being ranked

A car can need to race and need not be ranked — a sibling or parent's car, the den leader's demonstration car, an outlaw-class entry sharing the track between dens ([#548](https://github.com/dknowles2/trusty-track/issues/548)). The only lever used to be check-in, and un-checking a car both removes it from the standings *and* vacates its lanes (#228) — right for a car that has left the building, wrong for one that is still on the track.

**`Racer.excluded_from_standings` is a plain flag, read in exactly one place**: `services/scoring.get_leaderboard` drops a flagged racer's lanes before calling `domain.scoring.score_heats`, so `domain/scoring.py` itself is untouched — this is about *which rows are supplied*, not about how they rank. Everything downstream inherits the exclusion for free rather than growing a second copy of the rule (#48's lesson, and #52's failure shape if it were not): `get_advancing_racers` and `services/awards.recipient_of` both read the standings, so a flagged car can neither advance nor win a `SPEED` award. `_elimination_leaderboard` is the one leaderboard shape that does not call `score_heats` at all, so it filters separately, for the same reason.

**Lanes are stripped *before* scoring, not merely dropped from the output rows** — deliberately, so `domain.scoring.drop_worst_status`'s "did every ranked racer have the same number of counted results" reasons about the ranked population only. Leaving a flagged racer's lanes in that population would let an exhibition car's own irregular heat count silently disable the modifier for everybody else. The accepted trade: under `POINTS`, a DNF or skip in the same heat as an excluded racer is now scored last among the *ranked* cars still in it rather than the true physical field size — a minor, deliberate cost, not an oversight. The same stripping is what keeps a tied cluster's tiebreak chain (#540) from including a car that was never a contender for the slot it is settling.

**They still race.** Heat generation, admission (#172), withdrawal (#228) and the live heat view all read check-in, not this flag, and none of them changes — a flagged car is scheduled, shown on the audience display, and has its times recorded exactly as before. Only ranking is different.

**Their times still set track records.** `services/records.py` is about the *track*, not the standings, and deliberately does not read this flag — the fastest car a track has ever seen is a fact about the track whether or not the driver was eligible for a trophy that day. Don't "fix" this; it is the one thing #548 asked to stay unfiltered.

**The Grand Finals half is the same mechanism, set by a different hand.** `Race.exclude_round_winners_from_qualifying_standings` is a per-race toggle: once a championship round is decided (`crud.is_round_complete`), its rank-1 winner(s) stop counting toward the standings of the round they qualified from — so a Grand Finals pack champion does not also keep their own den's trophy. Computed on every read like everything else here (#17): a correction to a final's time moves who is excluded on the very next read, and an undecided round excludes nobody. `services/scoring._grand_final_exclusions` matches the *exact* scope a championship round's field was drawn from — `round_id` for a `"ROUND:<id>"` source, or the aggregate prelim scope (`round_id=None`) for `"ALL"` and `"EACH_GROUP"` — the same scope `_standings_for` reads when it picks the field. A `"ROUND:<id>"` source therefore excludes the champion from *that round's own page*, not from the "Overall (qualifying rounds)" aggregate; the two agree only when the race has exactly one prelim round. Elimination rounds are skipped — their "winner" is whoever survives, not a rank-1 row, and #548 does not ask for that format to be covered. Off by default, so an upgraded install reads exactly as it did before this column existed.

**The bulk action is a new mutation; the single-racer edit rides on the existing one.** `updateRacer` already carries every field on `RacerInput`, so a form editing one racer needed nothing new. The roster's selection bar needed `bulkSetExcludedFromStandings` beside `bulkCheckIn` instead — six sibling cars set in one go — and it is deliberately *not* `bulkCheckIn`'s shape: it calls neither `_admit_late_racers` nor `_revalidate_timers`, because nothing about the schedule changes when this flag flips.

**Saying it out loud.** A flagged car needs to look flagged, or the operator will assume the app has lost it: the roster row carries a badge next to the check-in status, and the Standings page counts how many cars are racing but not ranked rather than silently showing a shorter list than the roster.

### Run-off heats

Rules in `domain/tiebreak.py` (the `RUN_OFF` resolution) and `domain/lanes.py`; database wiring in `crud.create_run_off_heat` / `crud.run_off_heats_settling` and `services/scoring.run_off_contested_rank`; storage is a `Heat` row (`kind = RUN_OFF`, migration `0039_run_off_heats`) — [#550](https://github.com/dknowles2/trusty-track/issues/550). [#540](https://github.com/dknowles2/trusty-track/issues/540) gave a shared rank a way to resolve automatically; this gives the operator a way to resolve it by racing the tied cars, which the docs had been promising ("settle it with a race-off, or by correcting a time") since before either issue existed.

**A run-off heat is a third `HeatKind`, not a flag on an official heat.** `round_id` stays null — the same shape a free heat already uses — rather than pointing at the round whose tie it settles, because every piece of code that rebuilds, renumbers, or counts a round's heats (`_reset_heats_in_place`, `invalidate_future_rounds`, `is_round_complete`, the #230/#311 runs-per-lane divisor, `delete_heat`'s renumbering) assumes a round's heats are exactly the ones it generated. Sharing `round_id` would pull a run-off into every one of those, silently. What round it settles is instead its own column, **`Heat.settles_round_id`** — null meaning the race's overall (prelim-scoped) standings, the same thing `get_leaderboard`'s own `round_id` parameter means when absent — `ON DELETE CASCADE`'d from `rounds`, the usual "deletion is the schema's job" rule (#125). The racers it is between need no column of their own: they are the heat's ordinary `HeatLane` rows, written through the one door (`set_heat_lanes`) like any other heat's.

**`models.official_heats` stays exactly `kind = OFFICIAL`, unchanged.** That is what makes `_scoring_heats`, `services/records.track_records`, and `services/stats.compute_race_stats` exclude a run-off automatically, with zero code changes to any of them — the same filter that already excludes a free heat's exhibition run excludes a run-off's scoped one, for a different reason each. The one deliberate exception is `models.scheduled_or_run_off_heats` (`kind != FREE`), which backs `crud.heats_in_running_order` — the one door `onDeck`/`currentlyRacing` both read through — because the audience is meant to see a run-off while it races. It sorts immediately after every heat of the round it settles (or after every round, if it settles the overall standings) via two sentinel values in `heats_in_running_order`, since it has no `round_id` of its own to sort by. `timingStats` needed no change at all: it already takes either kind, and a run-off heat "is the heat that just happened" the same way a free heat is (#59) — it is only excluded from `TrackRecordBreak`, alongside `FREE`, since its result must not credit or contest a record.

**It never feeds an aggregate score, defensively as well as by construction.** `_scoring_heats` filters out `kind = RUN_OFF` unconditionally, even though `crud.get_heats` (which it calls first) already excludes it via `official_heats`: the explicit filter is belt-and-braces against a future change to that function loosening the default, since this is the one rule the whole feature exists to protect.

**It resolves through the same door as everything else** ([#540](https://github.com/dknowles2/trusty-track/issues/540)'s `get_leaderboard` → `_resolve_ties` → `domain.tiebreak.tiebreak`). `tiebreak()` takes an optional `run_off` argument — a decided run-off heat's own lanes, matched by `_resolve_ties` to a same-score cluster by its *exact* racer-id set (`crud.run_off_heats_settling`, scoped to the standings view being resolved, then keyed by `frozenset` in `services.scoring._run_off_lookup`). When present and it separates anybody, it wins outright — the configured `race.tiebreaker` is never consulted for that cluster — and `TiebreakResult.resolved_by` reports `"RUN_OFF"` rather than the configured method, reaching `LeaderboardEntry.resolvedBy` exactly the way any other method does. `RUN_OFF` is deliberately absent from `domain.tiebreak.ALL_METHODS`: it is not a policy an operator picks in `RaceForm`'s Ties control, it is what happens when they hold one.

**Computed, never stored — the same rule as the standings (#17) and a `SPEED` award's recipient (#170).** The heat is the only thing written; what it decides is derived fresh on every read. `services.scoring.run_off_contested_rank(db, race_id, heat)` re-runs `get_leaderboard` for the heat's `settlesRoundId` and asks whether this heat's exact racer set is *still* the cluster sharing one rank — if a time recorded elsewhere in that round moved the standings since the run-off was created, the tie may have moved or vanished entirely, and this returns `None` rather than a rank that no longer means anything. `RunOffHeat.placement` (the mutation's own return type) and `Heat.runOffPlacement` (surfaced on the `Heat` type `onDeck`/`currentlyRacing` return, since those are the only two subscriptions that hand back a run-off as a plain `Heat`) both call it — a non-null value is simultaneously "this is a run-off" and "here is what to announce" for the audience display's "racing off for Nth place" banner (`features/racing/runOff.ts`'s `runOffAnnouncement`, a pure helper in the `awardText.ts`/`ceremony.ts` tradition).

**Auth is `OPERATOR`**, the same bucket as `updateHeatResult` and scheduling: a run-off changes what the standings say. `createRunOffHeat` validates through `crud.create_run_off_heat` — at least two racers, no more racers than usable lanes (`usable_lanes_for_race`, so a lane out of service is honoured the same way it is everywhere else) — and assigns lanes automatically in the order given, since the point is that these specific cars race each other once, not that anybody picks who stands where. `deleteRunOffHeat` is the operator's undo for one created by mistake, refused once it has results, and calls `_revalidate_timers` for the same reason `deleteHeat` does.

### Track records

`services/records.py`, carried on `raceStats` as `trackRecords` and shown on the Stats page. The fastest cars a track has ever seen: races carry `track_id`, so a track accumulates results across events. One entry per racer at their single best time, capped at five, best first — official heats only, `time_seconds > 0` only (a recorded 0.0 is a DNF marker), and a lane whose racer was deleted has no holder (`_vacate_lanes` cleared its time anyway).

**Computed on every read, never stored** — the same rule as the standings (#17): a corrected time must move the record, and a stored copy would be the first thing able to disagree with the heats it came from. The consequence is documented rather than fought: deleting a race deletes the records it set. The frontend marks entries whose `raceId` equals the current race ("set at this event"); the comparison is client-side, so the payload carries the race id, name and date of each entry. `test_track_records.py` pins all of it.

**Historical records are the one stored kind** (`models.HistoricalTrackRecord`, table `track_records`, migration `0023`) — hand-entered for events from before Trusty Track, which is the case the computed-never-stored rule does not cover: there are no heats to compute from, so the row is primary data, the audit log's distinction. Merged into the same list by time; `race_id` is null in the payload, so the "set at this event" badge never fires for one. Managed on the track's card in System Settings (`TrackRecords.tsx`), operator-only (`createTrackRecord` / `updateTrackRecord` / `deleteTrackRecord`), validation on the Pydantic schema surfaced as a sentence. `ON DELETE CASCADE` from tracks.

**Breaking the record is announced on the audience displays.** `timingStats` carries `recordBreak` (a `TrackRecordBreak`), and the projector's results overlay and the timing view both render it (`features/observation/recordBreak.ts` composes the one sentence both use). The rule that keeps it meaningful: the baseline is `track_records(..., exclude_race_id=<current race>)` — **the record as it stood before today** — so a first event with no history celebrates nothing rather than "breaking the record" on every fast heat. `records.broken_record` also refuses a tie (strict `<`) and DNF markers, and a free heat never fires it. Derived from state per payload, not remembered as an event (#248's shape). `test_record_break.py` pins each refusal. Note the docs screenshot suite trips it deterministically, and how it does so is the point: `screenshot-observation.spec.ts` races on a **track of its own** and seeds one historical record slower than any car it invents, so the banner in `observation/07` and `10` says the same thing on every run. It used to lean on the specs sharing `tracks[0]`, which made another spec's times the baseline — survivable while one spec ran at a time, and not once they run at once.

**The projector's results overlay needs the same edge detector as `roundCompletion.ts`, and got it late** (#335). `timingStats` delivers an opening payload on connect — the subscription's usual shape — so a projector opened or reconnecting mid-event was popping the "Heat Results" overlay for whichever heat happened to be last, possibly minutes ago: `seen === null` meant history, not news, and this subscription had no `seen` at all. `features/observation/resultsOverlay.ts` supplies it. Its key is `heatId` plus `recordedAt` rather than `roundName`-`heatNumber`: the latter is unchanged by a correction, so a re-recorded heat never re-triggered the overlay. `recorded_at` is exposed on the `TimingStats` GraphQL type for exactly this — it is otherwise the same field #59 already uses to rank official and free heats together.

### Scale speed

`domain/scale_speed.py` — `scale_mph(length_feet, time_seconds, scale=DEFAULT_SCALE)` (#610). `Track.length_feet` was collected and never read; the question every scout asks after a heat is how fast that was in *real* miles per hour, which is a plain unit conversion once a length and an elapsed time exist: `(length_feet / time_seconds) * (3600 / 5280) * scale`.

**`scale` is a parameter, not a constant.** `DEFAULT_SCALE = 25` is the standard BSA Pinewood Derby ratio — a ~7-inch car against a ~175-inch real one — but it is a fact about the *vehicle*, and this app's vehicle is configurable (see Terminology's `vehicle_singular`/`vehicle_plural`, #551). A Space Derby rocket or a Raingutter Regatta boat is not built to 1:25, so the ratio has to travel with the track rather than being baked into the arithmetic.

**A non-positive time is the DNF marker, same as everywhere else scoring reads a time** (see Scoring above) — it and a non-positive or missing length, and a non-positive scale, all resolve to `None` rather than a number nobody should read.

This is stage 1 of #610 — the pure rule only. A `tracks.scale_ratio` column, GraphQL wiring, the System Settings control, and rendering on the projector and timing views are later stages.

**Stage 2 (storage and API)** adds `Track.scale_ratio` (`float`, `NOT NULL`, default `DEFAULT_SCALE`, migration `0042_track_scale_speed`) and `Track.show_scale_speed` (`bool`, `NOT NULL`, default `true`), exposed as `scaleRatio`/`showScaleSpeed` on the `Track` GraphQL type and on `TrackInput` (so `createTrack`, `updateTrack` and the per-track entries in `updateInitialConfig`'s track list all carry them, the same one input three mutations already share). `show_scale_speed` is deliberately a plain flag rather than folded together with "`length_feet` is positive" — a track's length can be filled in after the ratio is set, and an operator running a format the ratio does not apply to needs one control to turn the whole idea off. Every later reader that decides whether to actually display a speed (stage 4) ANDs this flag with a positive `length_feet`; the column alone does not promise a length exists to compute from. `scale_ratio` is refused at zero or below in `schemas.TrackBase`, the same "sentence a volunteer understands" shape `lane_count`'s bounds already use.

**Stage 3 (the operator's control)** puts the checkbox and the ratio input on the track's own card in System Settings (`TrackCard.tsx`), beside Length (feet) — a track fact, like lane count and length, not a race-day one, so it saves with **Save Settings** rather than on click the way lanes-in-service and track records do. The ratio input is shown only while "Show scale speed" is on, and `firstProblem` (`sections.ts`) refuses a non-positive ratio client-side too, naming the track by number — the server refuses it in `schemas.TrackBase` regardless of the flag, so a value nothing could ever use should not reach Save either. The label reads the vehicle word through `useTerminology()` rather than saying "car" outright, the same rule `terminologyGuard.test.ts` holds every settings control to.

**Stage 4 (rendering) computes the number server-side and only formats it on the frontend** — the same "one rule, composed once" shape #552 already uses for a lane's display name. `Subscription.timing_stats` carries `TimingStatsLane.scaleMph`, one lane's own time converted through `domain.scale_speed.scale_mph`; `raceStats` carries `RaceStats.topScaleMph`, the fastest-heat highlight's time converted the same way, read off the highlight `services/stats.compute_race_stats` had already computed rather than rescanning the heats for the quickest time a second way. Both apply the AND stage 2 promised: null unless `Track.show_scale_speed` is on **and** `length_feet` is positive, on top of `scale_mph`'s own null for a non-positive (DNF) time. `formatScaleMph` (`frontend/src/features/observation/scaleSpeed.ts`) is the one place a number becomes "213 mph" — rounded to a whole number, since a hand-measured track length and a millisecond-precision timer do not support a decimal's worth of confidence — and it does not second-guess a null, since the server has already decided when there is nothing to show. `Observation.tsx`'s live timing view and its projector results overlay, and `RaceStats.tsx`'s Fastest Heat card, are the three places it renders; none of them says "car" — the surfaces render a number, not a rename of the vehicle word `useTerminology()` already owns.

### Lane colours

`domain/lane_colors.py` — `color_for_lane(lane_colors, lane)`, plus `STANDARD_4_LANE_COLORS`/`STANDARD_6_LANE_COLORS` and `preset_for_lane_count(lane_count)` (#611). Real tracks paint or sleeve each lane a different colour, and the room calls cars by it ("put car #12 in the blue lane"); Trusty Track has only ever known lanes by number. This is stage 1 of #611 — the pure rule only, following #610's shape (a pure conversion first, storage and rendering later). No migration, no GraphQL field, no UI control yet.

**A lane colour is keyed on the track's own lane number, the same number `HeatLane.lane` holds — never a position in a schedule.** `color_for_lane` takes `lane_colors` (a plain `Sequence[str]`, index 0 meaning lane 1) and a lane number, and returns `None` for a lane below 1, past the end of the sequence, or holding a blank string — "no colour configured", not an error, which is what lets a lane added by turning `lane_count` up, or a track that has never configured any colours at all, fall back to the plain numbered badge unchanged. It makes no assumption that `usable_lanes_for_race` is contiguous or that every lane is present — a colour is a fact about the physical lane, not about whether today's schedule is using it.

**`Track.reverse_lanes` (#553) needs no second translation here, and the module says why at length.** `TimerManager._translated_lane` mirrors a lane number only at the wire boundary — a device's own channel numbering becoming (or being built from) the track's own lane number, which is what `HeatLane.lane` already holds everywhere else in the app. A lane colour, looked up by that same track lane number, is already on the correct side of that mirror; adding a `reverse_lanes` argument to `color_for_lane` would un-cross what the timer manager crossed once. If a future caller reaches for one, that is a sign the number it is holding is not actually a track lane number.

**Storage shape decided now, so stage 2 does not re-litigate it**: a JSON array of hex strings, one per physical lane — not a comma-separated list, which is the shape issue #5 already spent a release removing from `LaneOutage`'s ancestor. `is_valid_lane_color` refuses anything that is not `#RGB` or `#RRGGBB`, including a bare CSS colour name — a preset's *name* ("Red") is for display, only its `hex` is what gets stored, so there is exactly one accepted shape for the column to validate against rather than a name-or-hex union.

**Presets carry a name alongside the hex, deliberately** — `LaneColor(name, hex)` — because a colour swatch alone fails anyone in the room who cannot distinguish the hues, the same reasoning the Clear Sight theme exists for (see Themes). `LANE_COLOR_PRESETS` only names 4 and 6 lanes, the two the issue calls the standard schemes; `preset_for_lane_count` truncates the smallest preset that covers a track's actual lane count (a 3-lane track gets red/white/blue) and returns `None` past six, where inventing a "standard" seventh colour is not this module's call.

**Lane colours are fixed, not theme-driven, and that is a deliberate answer the later stages should keep.** They represent real paint on a physical track, which does not change when an operator switches the Display theme from Field Uniform to Under the Lights — so, unlike everything in `theming/themes.ts`, a lane's configured hex is the same value on every surface and under every theme. What *does* have to respect a theme is how a colour is rendered next to it: the issue's own rule is a badge, a pill, or a left-accent border, never a background fill a theme's own text colour would have to fight — the same "discrete indicator, not a wash" constraint `PrintDecor` already follows for print decoration.

**Suggested remaining stages (from the issue, and this session's read of them):**

1. **Storage and API.** `Track.lane_colors` (JSON array of hex strings, default empty), exposed as `laneColors` on `Track` and `TrackInput`, the same one input `createTrack`/`updateTrack`/`updateInitialConfig`'s track list already share (see Scale speed's stage 2 for the shape). Validate each entry through `is_valid_lane_color`.
2. **The operator's control**: a preset-plus-per-lane-picker on the track's own card in System Settings, seeded by `preset_for_lane_count`. Land this only after the scale-speed and demo-timer changes already in flight on `TrackCard.tsx` have merged, to avoid three concurrent changes to the same card.
3. **A `LaneBadge` component** (frontend) rendering `color_for_lane`'s result as a dot/pill/left-accent border beside a lane number — one component, so the "discrete indicator, not a background fill" rule is enforced in one place rather than at every call site.
4. **Wire `LaneBadge` into RaceExecution, the projector/On Deck views, and the heat sheet printable** — the surfaces the issue names. The heat sheet already prints one column per *track* lane rather than per heat lane (see Printables), which is exactly the numbering `color_for_lane` expects.
5. **Docs**: `docs/reference/race-settings.md` and `docs/reference/displays.md`, the same two pages #610 updated in its own stage 5.

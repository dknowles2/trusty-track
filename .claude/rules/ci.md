# What CI checks, and the functional e2e specs

Part of the Trusty Track agent guide; the index is in [`CLAUDE.md`](../../CLAUDE.md). Read this before touching `.github/workflows/`, the release workflow, or `frontend/e2e/functional/`.

---

## What CI checks

Eight kinds of job on every pull request (`.github/workflows/ci.yml`), nine runners — two of them are matrices:

| Job | What it would catch |
| --- | --- |
| **Lint & Types** | `ruff check`, `ruff format --check`, `mypy backend` over the whole tree |
| **Backend Tests** ×2 | The suite on 3.10 *and* 3.12 — 3.10 is the floor a Pi's system interpreter gives you, and it has caught syntax that 3.12 accepts |
| **Frontend Tests** | `eslint`, `npm run typecheck` (`src` *and* `e2e`), `vitest` |
| **GraphQL Codegen** | A backend schema change that was not regenerated into `src/gql` |
| **Docs Build** | `scripts/build_site.sh` — the landing page and the guides assembled exactly as Cloudflare Pages assembles them, with `mkdocs build --strict` catching a broken link or a missing image before it deploys |
| **End-to-End** ×2 | The served page, the GraphQL round trip and the normalized cache, together |
| **Doc Screenshots** | The Playwright specs that generate the documentation's images still drive the app (#114). What they render is also compared against what is committed (#838) — but that comparison *reports* and never fails the job; see "The drift check is advisory" below |
| **Docker Build** | That the image builds *and starts*: it runs the container and waits on `/health` |

**`Doc Screenshots` compares pixels now, not just that the specs still run** ([#838](https://github.com/dknowles2/trusty-track/issues/838)). It used to prove only that the doc screenshot specs still drove the app and discard every image they produced — so [#830](https://github.com/dknowles2/trusty-track/pull/830), [#831](https://github.com/dknowles2/trusty-track/pull/831) and [#832](https://github.com/dknowles2/trusty-track/pull/832) all merged green within five minutes of each other while silently invalidating ~30 published images, and nothing said so until somebody diffed the tree by hand. `ci.yml`'s job now snapshots `docs/assets/screenshots/` right after checkout — before the specs overwrite it in place — runs the specs as before, and then runs `frontend/e2e/docs/compare-screenshots.ts` (pixelmatch, `includeAA: false`, its default) against that snapshot. Antialiasing detection is what makes a tight threshold survivable: it does not count an antialiased edge pixel as a mismatch on its own, and the residual left once font *selection* is fixed ([#821](https://github.com/dknowles2/trusty-track/issues/821)/[#825](https://github.com/dknowles2/trusty-track/pull/825), above) measured at exactly **zero** pixels, on every image but the excluded ones below, across four repeated clean runs *on the same host* — not "a dozen images differing by a few dozen pixels", which was the raw-byte-diff-era estimate before pixelmatch's own antialiasing model existed to filter it out. That zero does not hold *between* hosts: [#931](https://github.com/dknowles2/trusty-track/issues/931) found that two hosts selecting the identical bundled font can still rasterise it differently, glyph by glyph, at pixel-identical layout — see `.claude/rules/documentation.md`'s screenshot section for the evidence, and this job's new artifact-harvesting step below for why a baseline now has to come from this runner rather than from wherever it was regenerated. `50` px / `0.05%` is the chosen gate: comfortably above that measured zero, and comfortably below the smallest genuine content change measured while building it — a focus ring [#830](https://github.com/dknowles2/trusty-track/pull/830) added to every modal, ~1,700–4,000 px (0.17–0.41%) depending on the form.

**It was *meant* to fail the build, and for months it could not** ([#918](https://github.com/dknowles2/trusty-track/issues/918)). `#840`'s step piped the comparison into `tee -a "$GITHUB_STEP_SUMMARY"` so the pixel report would show up in the job summary, and GitHub's default shell for a `run:` block is `bash -e {0}` — **not** `-o pipefail`. A pipeline's exit status is its last command's, which is `tee`, and `tee` never fails, so `node compare-screenshots.ts ...`'s `process.exit(1)` was discarded on every run from the day this step was written. [#914](https://github.com/dknowles2/trusty-track/pull/914) is the proof: its own job log printed `51 exceeding the threshold` and the job reported `success`. Every "Doc Screenshots" green between #840 and #918 therefore meant only "the specs ran," exactly as it did before #838 — the pixel comparison existed and was computed correctly, but nothing acted on its answer. `ci.yml` now sets `defaults: run: shell: bash -eo pipefail {0}` at the workflow level, deliberately not only on this one step: a future step piping a check into `tee` for the same reason — writing to the step summary — would reintroduce exactly this bug with nothing to catch it, and this file's `run:` steps had exactly one `|` pipe in them when it was made the default, so nothing else changed behavior.

**The drift check is advisory now, and the baselines are regenerated after every merge instead** ([#982](https://github.com/dknowles2/trusty-track/pull/982)'s follow-up). Three days of the gate actually failing were enough to measure what it was failing *for*: of fourteen `Doc Screenshots` failures on 2026-09-11, eight were the mechanism working exactly as designed — a baseline may only come from this runner (#931), so every PR with a visible change had to fail once, be handed its `regenerated-screenshots-<shard>` artifact, and be pushed again — four were the harness racing its own pictures (#970, #977, #978, #986; three of them on `main` itself, where a first-run-fails-second-passes pattern is not available), one was a runner network error, and one a real spec break. Not one was an unintended visual regression, which is the case the gate existed for. So the comparison still runs, unchanged, with the same threshold and the same exclusion list, and its answer is still written to the step summary and uploaded as `screenshot-drift-<shard>` — but its exit status is recorded (`steps.drift.outputs.drifted`) rather than obeyed, and a sticky per-shard PR comment lists the images that moved, edited in place on later runs and only ever posted once a shard has drifted. **A spec that fails still fails the job**: that is a test, and the `'Add round'` strict-mode break and `screenshot-timers.spec.ts`'s element-not-found are exactly the kind of thing that should stay red.

What keeps the committed images matching what the app renders is `regenerate-doc-screenshots.yml`, which now also runs on every push to `main` and merges its own PR. Three things about it, each a way of getting it wrong, are set out in that file's own header comment — the `paths-ignore` on `docs/assets/screenshots/**` that stops it re-triggering on its own merge, the `concurrency` group that collapses a burst of merges into one run against the newest `main`, and the reason it has to *dispatch* CI onto its own branch: a PR opened with `GITHUB_TOKEN` raises no `pull_request` event, `main`'s ruleset requires nine checks by name, and `workflow_dispatch` is the one event that token can raise, which is why `ci.yml` now carries that trigger. Its check runs land on the branch's head commit, which is what the ruleset reads regardless of the event, and `gh pr merge --auto` does the rest. **What this gives up is stated plainly**: an unintended visual regression is no longer *blocked* — it is surfaced twice (the PR comment, then the regeneration PR's own image diff) and blessed if nobody objects. A harness flake shows up as churn in that regeneration PR rather than as a red build, so the exclusion list and the settled-content waits in `.claude/rules/documentation.md` still matter exactly as much as before.

**Turning that gate on for the first time is what found [#931](https://github.com/dknowles2/trusty-track/issues/931), and fixing it changed where a baseline is allowed to come from.** With the pipe finally able to fail, the job reported 84 of 104 images drifting — not real drift, but the checked-in baselines having been generated on a machine that rasterises text differently from `ubuntu-latest` (see `.claude/rules/documentation.md`'s screenshot section for the evidence). **A baseline generated outside CI can never pass a gate enforced inside it**, so `doc-screenshots` now hands its own output back rather than discarding it: a step after the specs run reads `git status --porcelain` against `docs/assets/screenshots` — which, taken right after the specs write into it, names exactly the files *this shard's own run* changed, never the files a sibling shard owns or a file this run left untouched — and uploads only those as a `regenerated-screenshots-<shard>` artifact, `if: always()` so a red run hands them back too; that is the only way to escape regenerating locally and hoping it matches. `playwright.screenshots.config.ts` also launches Chromium with `--font-render-hinting=none`, `--disable-font-subpixel-positioning` and `--disable-lcd-text`, narrowing the class of host-dependent rasteriser input — not eliminating it, so the artifact upload is the actual fix and the flags are a reduction alongside it.

Eight images are excluded outright rather than tolerated, because their run-to-run variance overlaps the size of a genuine small change and a threshold loose enough to cover them would cover that too: `settings/04-activity-log.png` (real clock times) and `printables/check-in-scanner.png` (camera viewfinder placement) were already documented above; `observation/08-displays-panel.png` and `observation/13-qrcode.png` trace to a randomly-minted per-browser-context `displayId` (`displayIdentity.ts`) picking a different whimsical name, and to the vote QR code's URL depending on this machine's own detected LAN address (`services/network.lan_addresses()`, "best-effort" by its own docs) — neither seeded by `TRUSTYTRACK_DEMO_SEED`. **`printables/car-sticker-{card,sheet}.png` and `printables/check-in-code-{card,sheet}.png` joined the list turning this gate on for the first time** (#918): both render a QR code through `barcodeSrc(racer.id)`, and `domain/printables.encode` draws the *raw* database id into the payload (`TT1:<race_id>:<racer_id>`, by design). The docs specs run as several files in parallel against one shared, freshly-created backend, so which spec's `createRace`/`createRacer` calls land first — and so which autoincrement ids this spec's race and racers get — depends on scheduling, not on anything committed. Reproduced twice, back to back, on an identical tree: four-image diffs up to 3.6% of pixels, from this alone. #840's own measurement had called these two cards "rasterisation noise, confirmed invisible to pixelmatch" — that measurement ran without a working gate behind it (see above), and did not hold up the first time one actually enforced the answer. Unlike the other four, a regeneration cannot make these two cards stable; the next run reshuffles the ids again, so exclusion is the fix, not a stopgap pending one.

A fifth cluster — `settings/01-lanes-in-service.png`, `settings/05-track-records.png`, `settings/06-fake-timer-selected.png` and `settings/07-no-timer-selected.png` — sat here too and is fixed rather than carried forward ([#841](https://github.com/dknowles2/trusty-track/issues/841)). It traced to `screenshot-timers.spec.ts`'s temporary proxy-mode track, and to the other specs that bring a track of their own and never delete it (`screenshot-race-stats`, `screenshot-observation`, `screenshot-free-race`, `screenshot-manual-entry`): `screenshot-timers.spec.ts`'s own header comment claimed it "sorts after screenshot-settings" on the strength of alphabetical file order, which is not a guarantee this config ever gave — files run in parallel across workers (`fullyParallel: false` only orders the tests *inside* one file) — so any of those tracks' cards could still exist when `screenshot-settings.spec.ts` took its locator-scoped screenshots of its *own* card. Locator-scoping was not enough on its own: a sibling card appearing or disappearing still changes the page's total height, which changes the fractional scroll position the card gets cropped at, nudging every capture by a pixel that has nothing to do with what it is a picture of. A `dependencies` edge forcing `screenshot-timers.spec.ts` into its own project, strictly after `screenshots`, fixes the ordering — and was tried — but a shard containing that project's single test pulls its entire dependency chain (all of `screenshots`) into the *same* shard, which emptied the other shard completely under `--shard=1/2`/`--shard=2/2` and defeats the two-way split `ci.yml` relies on for wall-clock time. The fix that survives sharding is in the specs themselves: both `screenshot-settings.spec.ts` and `screenshot-timers.spec.ts` now hide every `track-card-*` element but the one they are about to screenshot, right before they screenshot it — the layout each renders into is then the same on every run regardless of what else exists on the shared backend, and no cross-file ordering is needed at all.

**A sixth source was found — and pinned, not excluded — before the gate ever measured it** ([#843](https://github.com/dknowles2/trusty-track/issues/843)). Roughly fifteen images under `race-day/`, `race-setup/` and `race-stats/` were suspected of showing the navigation bar's race selector pill reading "Select a Race" on some runs, in place of the race's actual name, while genuinely standing on that race's own page. Confirmed mechanically (routing `GET_RACES_NAV` through an artificial delay reproduces it on demand) rather than by chasing it under parallel load, which several full local suite runs — matching the paired/full-run discipline [#842](https://github.com/dknowles2/trusty-track/pull/842) used — never caught on their own. It traced to `GET_RACES_NAV` having no dependency on whatever the rest of a page is waiting for, so its response can still be in flight once a page's own content, and the spec watching it, are ready — a window that widens as the shared backend accumulates races from every concurrently-running spec. Full detail, including the genuine (if brief) product-level incorrectness this exposed and not just a test artifact, is in `.claude/rules/documentation.md`'s screenshot section. **Zero images were added to the exclusion list** — the fix is a `data-testid` and a settled-content wait in `screenshots-setup.ts`, the same pattern the rest of this section already uses, plus a small `Navigation.tsx` change so the pill does not claim "no race selected" while it does not yet know.

**#843 was reopened once that fix had let the gate itself turn on** ([#918](https://github.com/dknowles2/trusty-track/issues/918)): with the pipefail bug and the rasterisation gap above both fixed, every one of the 40 images still failing drifted in the same one place — the pill again, confined to its own anti-aliased text, present even where the text is a static string that never changes. A hover-transition-timing fix (moving the pointer off-viewport and settling `document.getAnimations()` before every screenshot) was applied on the strength of that first evidence and did **not** close the gap: two bootstrap passes against fresh CI runs, each rebuilding the baseline from that run's own output, produced the same ~40-image signature both times with the total pixel count *growing* between passes (1,510 then 5,714) rather than converging toward zero.

**Neither did the alpha-compositing fix that followed it.** `Navigation.tsx`'s pill background, border and hover state moved from `rgba(255,255,255,0.1)`/`0.2` (blended at paint time onto the nav's opaque background) to `color-mix(in srgb, #ffffff <weight>%, var(--scouting-blue))` — an opaque, pre-resolved colour, computed once rather than composited under the glyphs on every paint. Three same-job two-run measurements (`compare-screenshots.ts`'s threshold-free mode, comparing one job's own two Playwright passes against each other) all found **zero** pill-attributable pixels with the change in place, run before and twice after bootstrapping a baseline from it. Each looked like confirmation. Bootstrapping that baseline and letting the real, sharded gate compare a subsequent, separately-provisioned CI run against it reproduced the same signature regardless: 40 of 208 gated images (27/104, 13/104 across the two shards), 32,632 total pixels, visually confirmed on multiple diffs as the pill and nothing else, provably with `color-mix` on both sides of the comparison (the two commits' `Navigation.tsx` diff empty) — a larger total than either pre-fix pass, not a smaller one.

**The pattern is same-job-clean / cross-job-fails, not fixed/unfixed** — three separate two-pass comparisons within a single job agree with themselves on the pill regardless of which colour formula is in play; the one comparison spanning two independently-provisioned runners, which is the only shape the real sharded gate ever uses, does not.

**That split is exactly what a hidden element's *box* moving with the git hash produces, and that is the actual mechanism** ([#938](https://github.com/dknowles2/trusty-track/issues/938)). `screenshots-setup.ts` neutralised the navigation bar's version stamp — built from the git hash, so it changes on every commit — with `visibility: hidden` alone, which hides the ink but keeps the rendered width of `v{version}` in a proportional font. That element sits in `Navigation.tsx`'s right-hand `flexShrink: 0` group, immediately beside the `flex: 1` container the race pill centres itself in, so the pill shifts by half of whatever the hidden string's width changed by on every commit. Two Playwright passes *within one job* check out the identical commit and so hide the identical width — hence the repeated, honest-looking "zero pill-attributable pixels" measurements above — while the real gate compares against a baseline committed on a *different* commit, and bootstrapping that baseline is itself a commit: every bootstrap pass invalidated the very thing it had just measured clean, which is why the pixel count grew pass over pass (1,510 → 5,714 → 32,632) instead of converging. Neither the hover-transition fix nor `color-mix` was wrong to try, and neither could have closed this — layout, not paint, was always the mechanism. The fix is `width: 0` plus `overflow: hidden` alongside the existing `visibility: hidden` in `HIDE_UNSTABLE`, so the element's box no longer varies with the string it hides. See `.claude/rules/documentation.md`'s screenshot section for the full record, including the two dead hypotheses (hover-transition timing, alpha compositing).

**Editing anything inside a macOS bundle after it is signed breaks the signature, and that is worse than not signing it.** `build-mac.sh` stamps the version into `Info.plist` after PyInstaller's BUNDLE step has already sealed it, so `codesign -dv` reported `Info.plist=not bound` and verification failed with "plist or signature have been modified". The step that would have repaired it was gated on `APPLE_SIGN_IDENTITY`, which no release has ever set — there is no Developer ID for this project. The consequence is not the mild one: a quarantined app with a *valid* ad-hoc signature gets the ordinary "unidentified developer" refusal that `install-mac.md` walks a reader past with **Open Anyway**, while a quarantined app with a *broken* one is called **"damaged and can't be opened"**, which macOS offers no way past — the only remedy is `xattr` in a terminal, which is not a thing to ask of a parent volunteer. It shipped in v1.1.1. The signing step is unconditional now (ad-hoc when there is no identity) and is followed by `codesign --verify --deep --strict`; `packaging.yml` asserts the same on every pull request, since every other check on that bundle passed while it was broken. **Notarization is still absent** and needs a paid Apple Developer account — with it, `build-mac.sh` already has the code path and only wants the four secrets.

**A job named in the ruleset may not be renamed — give it a gate job instead.** `main`'s ruleset requires status checks by exact name, and it names `End-to-End` and `Doc Screenshots`. Sharding renamed them to `End-to-End (1/2)` and so on, so those two contexts stopped reporting entirely and every pull request became unmergeable with nothing failing and nothing pending — `mergeStateStatus: BLOCKED`, an empty list of failures. `e2e-gate` and `doc-screenshots-gate` are one-line jobs that carry the required name and assert `needs.<job>.result == 'success'`, so the shard count can change without anybody editing repository settings. They need `if: always()`, or a failed shard *skips* the gate rather than failing it — and a skipped required check does not block.

**The backend suite runs `-n auto`, and both Playwright suites are sharded *and* parallel within each shard.** A pull request used to wait about three and three-quarter minutes; the three longest jobs were the two Playwright runs and the backend suite, and none had a single slow part to fix — they are 5,900 tests and 70 browser specs. The backend suite is split across processes, which depends on **nothing in it sharing state between tests** (in-memory database per test; the data directory is per xdist worker, which `conftest.py` had to be taught). The Playwright browser is cached on its version — 150 MB that never changes between runs, and a third of each of those jobs.

**A performance number belongs to the machine it was measured on, and CI is not that machine.** Three claims this session did not survive the trip. Zeroing the timer prober's settle was worth 17% locally at four workers, measured twice each way, and moved CI from 83 seconds to 84. Dropping the Playwright jobs to one runner made the *test phase* two to three times faster and the *job* four seconds faster. Removing the font install was predicted at 30–41 seconds and gave 54, some of which was a slow runner on the run before. A hosted runner has a fraction of the cores, a fixed setup cost that no amount of parallelism reaches, and enough variance that a single run proves little. Measure locally to find the cause; quote a CI number only from CI, and prefer the test *step* to the job when the job is mostly setup.

**Sharding and in-run parallelism compose, and both are needed.** They were briefly treated as alternatives, on the reasoning that a dependency project re-runs in full in every shard — which is true and is not a cost: **a shard is a separate runner with its own backend and its own data directory**, so the setup project a shard runs is the one that shard needs, and it takes about two seconds. Dropping to one runner was measured and barely moved the wall clock, because a job is not all test time: preparing a runner — checkout, `npm ci`, the browser and its system libraries — is around fifty seconds whatever happens inside, and no amount of parallelism reaches it. Parallelism cuts the test phase; sharding cuts what is left. The `End-to-End` and `Doc Screenshots` gate jobs carry the names the ruleset requires, so the shard count is free to change.

**Read a slow CI step's log before optimising it — the name is not the work.** `Install Playwright system libraries` cost 30–41 seconds on every Playwright job and looked like an obvious thing to cache. It installed no libraries: `ubuntu-latest` already carries every one Chromium links against, and the log says so of each. What it installed was nine font packages — Japanese, Chinese, Thai and Cyrillic — for an app that renders nothing outside Latin-1. Caching them would have recovered about a fifth of the cost, because the download is 2 seconds and `apt-get update` refreshing four mirrors is most of the rest. Removing the step took all of it. `--with-deps` stays on the cache-miss path, so a runner image that ever does drop a library is covered the next time the Playwright version changes.

Two things worth knowing:

- **The release workflow has its own test gate.** CI runs on pull requests and on `main`; a tag is neither, so without it, tagging any commit publishes it to GHCR and the release page whatever state it was in.
- **The release notes are drafted as the work lands, not reconstructed at the tag.** `.github/workflows/release-drafter.yml` keeps a draft release up to date on every merge to `main`, so the notes for the next version are visible — and correctable — before anybody cuts a tag; `release.yml`'s `create-release` runs the same drafter with the concrete tag, attaches the installers to that draft, and only then publishes it. Three things about it, each a way of getting it wrong. **The draft is filled in before the assets and published after them**, because `releases/latest/download/<asset>` is what every install guide links to ([#474](https://github.com/dknowles2/trusty-track/issues/474)) and a release page that appears without its assets is a broken link on the front page. **A category is a repository label**, so an unlabelled pull request heads the notes with no heading rather than falling off them — which is the right default here, since an unlabelled change is a change to the app itself. And the autolabeler matches only the three title prefixes this project actually uses (`docs:`, `fix:`, `fix(docs):`) — the titles are prose, not conventional commits, so a rule inferring a category from file paths would file half the features under Documentation, every change here carrying its own docs.
- **The e2e suite runs against a real backend, on ports and a data directory derived from the checkout** (`frontend/e2e/environment.ts`), so two worktrees can run it at once. It replaced a mocked one that had been failing silently — the mocks predated the normalized cache (#12) and answered without `__typename`, which graphcache cannot store, so the page rendered nothing. Nothing ran it, so nobody found out. If you add a browser test, add it there rather than mocking the API.

### Every issue carries a label

`.github/workflows/issue-labels.yml` runs on `issues: [opened, reopened]`. If the title starts with `docs:` (or `fix(docs):`) it applies `documentation`; if it starts with `fix:` it applies `bug` — mirroring the same two prefixes `release-drafter.yml`'s autolabeler already matches on pull requests, above. Anything else, or an issue that already carries a label, gets `needs-triage` if and only if it has no label at all. Removing `needs-triage` once a human has triaged the issue is a manual act — the workflow never removes it, so it never fights a maintainer who wants it left on alongside a real label.

**An unlabelled *pull request* is fine and stays that way — this asymmetry is deliberate.** `release-drafter.yml`'s own template puts uncategorized PRs first with no heading, because an unlabelled change is a change to the app itself and that is where the reader looking at a release wants to start. An issue has no equivalent "no heading" home: it sits in triage views and boards where "no label" reads as "nobody has looked at this yet" rather than as a deliberate category, which is why issues get a backstop and PRs don't.

**Label vocabulary for issues** (the full label set also covers `dependencies`, `github_actions`, `python:uv`, `javascript`, `needs-revision`, `needs-human`, `revision-1`, `revision-2` — release/PR-facing labels this workflow never touches):

| Label | When to reach for it |
| --- | --- |
| `needs-triage` | Applied automatically; nobody has classified this yet |
| `bug`, `documentation` | Applied automatically from a `fix:`/`docs:` title prefix; also fine to apply by hand |
| `enhancement`, `question`, `good first issue`, `help wanted`, `tech-debt`, `architecture`, `performance`, `security` | Ordinary human triage — pick the one that actually describes the issue, never guessed by the workflow |
| `icebox` | Parked by a human judgment call — blocked on hardware nobody has, a purchased certificate, or a real data file. The workflow never applies this; see `auth-and-demo.md`'s note on the public demo for the kind of thing that ends up here |
| `duplicate`, `invalid`, `wontfix` | Triage outcomes, applied by a human closing the loop |

The workflow degrades to a no-op on a fork or a repository missing one of these three labels — it logs a warning and moves on rather than failing the run, since a label set is repository configuration a fork is not guaranteed to have copied.

**Untested against a real `issues` event, and said so rather than implied.** Nothing available in this environment can fire a GitHub Actions `issues` webhook, so this has only been checked with `actionlint` and a read of the `actions/github-script` API — never a real run. The cheap way to check it: open a throwaway issue with a plain title (see `needs-triage` land), then one titled `fix: something` (see `bug` land), then close and reopen a labelled issue (see nothing change).

### A branch is deleted when its pull request merges

The repository's **Automatically delete head branches** setting is on, so GitHub removes a pull request's branch from `origin` the moment the PR merges. It was off for the project's first seven months, and on 2026-09-11 the remote held 317 branches — 309 of them for PRs that had already merged, and a local clone held 78 branches and 20 worktrees for the same work. Nothing was checking, because nothing *could*: every PR is squash-merged, so the branch's own commits are never in `main` and `git branch --merged` reports nothing. The only record that a branch is finished is the PR itself.

Four rules, each of which is a way of ending up back there:

- **The remote side is GitHub's job, not a step anyone runs.** Don't add a "delete the branch" line to a brief, a workflow or a script — the setting does it for every merge, including a bot's, and a step that people have to remember reaches only some of them (#48's shape, for branches). If a stale remote branch turns up anyway, the setting has been switched off; check `gh api repos/dknowles2/trusty-track --jq .delete_branch_on_merge` before cleaning up by hand.
- **The local side is whoever created the worktree.** GitHub cannot reach a clone. An agent that made a worktree for a PR removes it once the PR has merged — `git worktree remove <path>` and `git branch -D <branch>` — and a dispatcher that made one for an agent removes it when the agent is done. A worktree on a merged branch that outlives its PR is a directory holding a stale checkout, and twenty of them is where this section came from. `git fetch --prune` then shows the local branch as `[origin/…: gone]`, which is the tell.
- **Never push to a branch after its PR has merged.** The merge is the last thing anyone will look at that branch for; a commit pushed afterwards is invisible to the PR, to the release notes and to the auto-delete, and the cleanup above found exactly one — three headshot crops on `regenerate-racer-headshot-avatars`, pushed an hour after #577 merged and never in `main`. Open a new PR instead — that one was rebased, judged, and deleted.
- **A closed-without-merge PR is the case the setting does not cover.** GitHub deletes on *merge*; a branch whose PR was closed and superseded (the way #795 was by #830) stays until somebody deletes it. When you close a PR in favour of another, delete its branch in the same breath: `git push origin --delete <branch>`.

**To find what is stale, ask GitHub, not git.** `gh pr list --state merged --limit 1000 --json headRefName` is the list of finished branches; intersect it with `git branch -r`. For each candidate, compare `origin/<branch>` against the PR's `headRefOid` — a tip that has moved past the merged head is the third rule above, and is the one thing this procedure must not delete. Bot branches from `regenerate-doc-screenshots.yml` (`docs-screenshots/regen-<run id>`) have a PR when the workflow finished, and are handled by the setting when that PR merges; one with no PR is a run that stopped before opening it, and is a human's call.

### What the functional e2e specs are for

`frontend/e2e/functional/` holds two files and one shared `support.ts`: `roster.spec.ts` for the management side, `raceDay.spec.ts` for what happens once racing starts. Between them they cover generating a schedule, running a heat on the fake timer, standings arriving over the subscription, a championship field filling from the cascade, overriding a recorded time, skipping a heat, and reordering one.

They exist because every *rule* in those paths is already unit-tested and none of that says the answer survives the GraphQL round trip and the normalized cache. That gap is not hypothetical: writing `raceDay.spec.ts` found the subscription snapshot race below.

Three conventions, each learned from a failure:

- **Seed through GraphQL, drive the one step under test with the browser.** `support.ts` builds the race, roster and schedule. A spec that clicks its way through setup reports a break anywhere in the app as a failure of the thing it was testing.
- **One test per question.** The docs screenshot specs are a single long `test()` where each step depends on the last, and a break a third of the way through looked for months like a spec that ran (#114).
- **Drive dnd-kit from the keyboard, not a synthesised mouse drag.** `ScheduleManagement` registers `KeyboardSensor` alongside the pointer one: Space lifts, an arrow moves, Space drops. Leave a settle between the keys — dnd-kit animates the lift and the move, and three in one tick drop the item back where it started.
- **The specs share one backend and run at the same time on it**, so the same rules as `e2e/docs/` apply: unique race names, no assuming a race id, and nothing outside the setup project may touch the install's own settings. `configure.setup.ts` clears the first-run gate once, before anything else.
- **A track is global state; a race is not.** Each spec seeds its own race, so races cannot collide, and that made the convention above look sufficient. Tracks are shared: a spec that adds one puts a second row on System Settings for every other spec, which is how an unscoped `getByLabel('Timer Type')` started matching two elements. A spec touching the settings page **finds its own card by the name in its own input** and reads back through `initialConfig` — the source the page renders from — rather than `Query.tracks`, which need not agree on order. Never by index: `#track-timer-type-0` says nothing about which track it is once specs run together.

**The functional suite runs in parallel, and getting there meant naming what was global.** `fullyParallel: true` with a worker per core, against one backend — 123 seconds to about 30. Three things were in the way, and each is a rule now:

- **The first-run gate.** Seven workers open an unconfigured install together, every one of them submits `createInitialConfig`, one wins and the rest hang on a navigation that never comes. `configure.setup.ts` is a setup project every test depends on. Six tests were failing on their full two-minute timeout, and the error named `ensureConfigured` rather than anything that had gone wrong.
- **The timer is per track.** `TimerManager` is one per *track* (#9), so a race that arms a heat holds a device exclusively; two races sharing a track arm over the top of each other and the run is abandoned (#50). The setup project builds **one track per worker** and `seedRace` takes its worker's own. A track per *race* was the first attempt and was worse twice over: sixty `createTrack` calls cost 26 seconds serially, and a race inserted against a track committed microseconds earlier failed the foreign key about one run in ten under seven concurrent writers.
- **`timerModel.spec.ts` switched the shared track off the fake timer and never switched it back.** It has its own track now. That was latent debt rather than a new problem: it survived only because the file sorts near the end of an alphabetical, single-worker run, which is not a property anybody should have to know about.

**A test that asserts a client-side consequence and then navigates is racing its own mutation.** `raceDay`'s skipped-heat spec clicked Skip, waited for "Heat 2" — which `raceFlow` puts on screen by itself — and then called `page.goto`, a full document load that aborts whatever is in flight. Serially `updateHeatResult` always won; in parallel it did not, and the failure landed on an assertion three steps further on. It waits for the server to hold the skip before navigating. Look for this shape whenever a parallel run fails somewhere that reads correctly on its own.

**A subscription must register its queue before it sends its opening snapshot.** `pubsub.subscribe` registers on entry, so anything published earlier reaches no queue, and every payload these emit is a full snapshot rather than a delta — nothing catches up. `heatSession`, `timerStatus` and `freeRaceHeat` built the snapshot first and subscribed afterwards, and the operator screen arms the heat itself, so its own `prepareHeat` landed squarely in the window: the screen sat at "Waiting for Timer…" with the start button disabled while the timer was ARMED. `test_subscription_snapshot_race.py` pins all three by taking the opening payload and *then* publishing. The existing subscription tests could not catch it — they trigger concurrently after a 50 ms sleep, by which time the subscription has long since subscribed.
